# Независимое review TARGET 01–04

Дата: 14 октября 2026. Проверены четыре raw notes и общий brief, выборочно — первичные источники. Другой target review не читался. Это проверка определения эксперимента, без реализации и новых подсчётов. Итог: содержательная основа сильная, но **единого исполнимого протокола пока нет**. Нужен согласующий appendix; переписывать независимые raw notes ради искусственного единогласия не следует.

## 1. Главные расхождения и необходимые уточнения

**Высокий приоритет: target и maturity связаны.** В [01, «Что измеряем»](01-anchors.md) и [03, «Что именно оцениваем»](03-candidates.md) окно `(t,t+H]`; в [02, определение Y и случаи 1–2](02-purchase-target.md), [04, «Единица и границы»](04-training-negatives.md) — `[t,t+H)`. Это различные задачи, а не эквивалентные обозначения. Первая исключает покупки в anchor-секунду и включает правую; вторая делает наоборот. Для fixed-clock прогноза до группы `[t,t+H)` корректно: события в `t` ещё не наблюдались. Для action-context покупку той же секунды нельзя назвать последующим результатом просмотра.

Appendix должен определить cutoff `S`: при fitting разрешены только события `s<S`, конец доступного лога `T` также исключительный. Тогда:

| Target-окно | Полностью зрелый label к S | Зрелость к концу файла T |
|---|---|---|
| `[t,t+H)` либо `(t,t+H)` | `t+H≤S` | `t+H≤T` |
| `(t,t+H]` | `t+H<S` | `t+H<T` |

Следовательно, строгая правая граница 01 верна для её собственного target; условие 02/04 верно для их target. Опасность возникает при сборке: нельзя перенести `≤` на закрытый правый конец. На дневной сетке одна секундная неоднозначность может убрать целый последний anchor-день перед fitting. Для действий отдельно допустимо `(t,t+H)` с исключением обеих границ; выбранное окно должно присутствовать в protocol ID. Новые подсчёты покупок на границах отсутствуют.

**Высокий приоритет: момент выдачи и universe.** [01, протокол B](01-anchors.md) использует текущие views после закрытия секундного пакета, но сохраняет общий snapshot до всей группы. [03](03-candidates.md) определяет `U(t)` строго по событиям `<t`. Если view впервые раскрывает товар в `t`, contextual baseline из 01 не сможет поднять его внутри `C⊆U(t)`. Это не доказанная утечка raw notes, а несовместимость при их объединении. Appendix обязан выбрать: либо контекстный baseline строго ограничен прежним C и его исключения измеряются, либо отдельный action-protocol использует `U_action=U(t)∪I_view(q)` и разрешённые атрибуты текущих views. Никакие чужие события, cart/purchase или иные metadata той же секунды не подмешиваются. Main fixed-clock не получает такой контекст.

**Средний приоритет: альтернативы не являются общим выбором.** [01](01-anchors.md), [02](02-purchase-target.md), [04](04-training-negatives.md) предлагают 00:00 UTC, [03](03-candidates.md) — 12:00. [03, B](03-candidates.md) задаёт M=1000, [04](04-training-negatives.md) — M=200. Оба различия меняют эксперимент: время влияет на eligibility, maturity и labels; M — на recall, число positives и распределение negatives. Сохранить варианты как предложения. Для ablation нужен один query manifest и один candidate manifest, а не обучение на 200 с оценкой на 1000 под видом неизменного pipeline.

## 2. Что уже корректно и что appendix должен закрепить

[02](02-purchase-target.md) правильно строит distinct binary Y независимо от candidate set. [03, «Потери нельзя прятать»](03-candidates.md) сохраняет cold targets вне U, misses вне C и полный Y в знаменателях/IDCG. [04](04-training-negatives.md) не добавляет непокрытые positives в training pool по будущему label. Эти правила сохранить буквально. Ранее купленные товары не исключать автоматически; повторные строки не увеличивают бинарный gain. Статья [Li et al., §3.1](https://arxiv.org/html/2109.14233v2) подтверждает различие дневных корзин и реальных orders в разных датасетах, но не восстанавливает orders REES46 и не обосновывает наш H=24h.

Для каждого зрелого query нужны отдельные состояния: `Y=∅`; `Y≠∅,Y∩U=∅`; есть covered targets, но `Y∩C=∅`; есть retrieved positives; `C=∅`. Пустые queries сохраняются независимо от training loss. В основном отчёте — prevalence покупки, universe coverage, candidate recall и all-target качество среди непустых Y; условное качество retrieved positives только диагностическое. Если принят ноль для пустого Y, опубликовать и условную метрику, и конвенцию: одинаковый ноль не оценивает отказ от рекомендаций. [Krichene–Rendle](https://www.ijcai.org/proceedings/2021/0651.pdf) действительно показывают несогласованность sampled ranking metrics; фиксированный past-only retrieval pool описывает ограниченный pipeline, а не приближённый полный каталог.

[03, B](03-candidates.md) требует ещё короткую спецификацию генератора: grain и формула ItemCF, события/окно, fit cutoff, агрегация соседей истории, caps, порядок слияния квот, ties, дедупликация и добор. «Fallback по view при отсутствии покупок» должен уточнять, отсутствие чего имеется в виду: глобальных покупок, покупок товара или недостаток заполнения квоты. Это необходимо для воспроизводимого C, а не требование реализовать retrieval сейчас. Новые товары без вектора должны иметь явный fallback; snapshot на конце train не подходит ранним train anchors.

## 3. Loss и sampling: существенной ошибки в формулах нет

В [04, A](04-training-negatives.md) веса BCE корректны для предложенного риска `L=mean_q[Σ_{i∈Cq}ℓ(q,i)/|Cq|]` по **непустым C**. При uniform sampling без возвращения inclusion probability отрицательного `π=m/N`; вес `1/(|C|π)=N/(m|C|)`, позитивы сохраняются с `1/|C|`. Сумма весов каждой группы равна единице. При `N=0` деление не вычислять. Добавление class balancing или неравномерного hard-negative sampler изменит этот риск; потребуются новые вероятности/веса. Непокупатели дают BCE сигнал, даже если не дают ranking positives.

[04, B](04-training-negatives.md) также корректна: полный набор `pn` пар с `1/(pn)` или равномерные k пар с `1/k` задают среднюю потерю информативного query. Default automatic pairs без явной нормировки не гарантируют такую массу. Передавать пары и pair weights согласованно; не заменять их object weights. Официальные [ranking objectives](https://catboost.ai/docs/en/concepts/loss-functions-ranking) подтверждают отдельные веса пар, а [Pool](https://catboost.ai/docs/en/concepts/python-reference_pool) — смежность строк одной группы. Group ID должен включать protocol ID при нескольких anchor-схемах. Нулевые positives и all-positive C не дают пар; эти группы остаются в evaluation manifest.

Для [04, C](04-training-negatives.md) фраза «нормировать по числу позитивов» пока не определяет параметры. По формуле официального QuerySoftMax при `β=1` веса `w_i=1/p_q` для всех строк positive-bearing группы дают равный групповой вклад: общий множитель сокращается внутри softmax. При `p_q=0` такое деление запрещено, ранжирующего сигнала нет. Это математическое следствие формулы, не проверенный запуск CatBoost; default loss самостоятельно per-query нормировку не обещает. Не смешивать эти веса с отрицательным sampler BCE.

## 4. Компактный предлагаемый протокол и минимум решений

Предлагаю для обсуждения: fixed-clock до глобальной группы, ежедневно 00:00 UTC, eligibility любое событие за прошлые 7d, warmup семь суток, binary distinct purchases `[t,t+24h)`, повторные товары разрешены. Universe — prior-observed proxy; C фиксирован один раз по past-only генератору. M=200 и M=1000 оставить двумя бюджетными альтернативами; выбрать одну после измерения количества queries/coverage/cost, до сравнения признаков. Train labels зрелы `t+H≤S`; параметры fitted компонентов доступны до соответствующего anchor. Текущий контекст, 12:00 UTC и изменение retrieval — отдельные protocol IDs.

Сначала сопоставить weighted BCE и равновзвешенный по информативным queries PairLogit при одинаковых candidates/features/budget. Сохранять все зрелые queries, считать потери U→C→TopK, показывать доли групп без training signal. До обучения нужны пять решений: clock/action; H и оба конца окна; единый C/M; вес query/user и loss; split/maturity плюс предел бюджета. Все конкретные числа выше — предложения. Новых измерений пригодности labels, покрытия, качества или скорости эти четыре notes и данный review не дают.
