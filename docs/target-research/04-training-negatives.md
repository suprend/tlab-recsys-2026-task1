# Обучение purchase ranking: loss, группы и отрицательные примеры

Дата: 14 октября 2026. Независимый угол: обучение и семантика negatives. Это предложения для выбора протокола, не разрешение на обучение. Контекст данных взят из существующего плана проекта и переданных результатов EDA; количество пригодных групп пока не измерено.

## Единица и границы

Единица строки — `(user_id, anchor_time, product_id)`, группа ранжирования — `(user_id, anchor_time)`, а не пользователь целиком или `user_session`. Для конкретного пилота предлагаю ежедневный anchor в 00:00 UTC для пользователей с событием в `[t−7 суток,t)`, признаки по этой истории и `H=24 часа`. Это иллюстративный выбор: частоту и горизонт нужно утвердить вместе с остальным протоколом. Цель `P_q` — множество разных товаров, купленных в `[t,t+H)`; повторные покупки не увеличивают бинарную релевантность. События ровно в `t` входят только в target, история использует `<t`.

`C_q` — зафиксированный past-only генератором набор максимум 200 уникальных кандидатов, одинаковый для всех сравниваемых моделей. `y_qi=1[i∈P_q]` для `i∈C_q`. Позитив вне `C_q` остаётся промахом retrieval: добавление его по будущему label изменило бы задачу. История и кандидаты материализуются до присоединения labels. Группа созрела лишь после наблюдения всего `H`; перед началом validation в train допускаются только anchors с `t+H≤T_validation`. Аналогичное правило действует перед test.

## Три протокола

**A. Pointwise CatBoost Logloss / sampled BCE.** Обучать все зрелые anchors с непустым `C_q`, включая отсутствие покупок и отсутствие покрытых позитивов; пустой `C_q` не создаёт строк и учитывается отдельно. Базовый риск — среднее по anchors, внутри anchor среднее BCE по полному `C_q`. Если полный набор дорог, сохранять все позитивы, выбирать `m=min(50,N_q)` отрицательных без возвращения равномерно из `C_q\P_q`, где `N_q` — их количество. Вес позитивной строки `1/|C_q|`, отрицательной `N_q/(m|C_q|)` восстанавливает этот полный эмпирический риск в ожидании; при `N_q=0` отрицательных строк нет. Это математическое свойство предложенного sampler, не исправление неизвестной экспозиции.

BCE без весов оценивает распределение искусственно выбранных строк. Даже weighted BCE предсказывает наблюдаемую покупку среди кандидатов при данном anchor, а не вероятность покупки после показа рекомендации. Калибровку, если она нужна, проверять на отдельном зрелом временном validation с полным `C_q`, без балансировки классов. При обучении только будущих покупателей такую вероятность получить нельзя.

**B. Pairwise CatBoost PairLogit — рекомендуемый основной ranker.** Для групп с `p=|P_q∩C_q|>0` и `n=|C_q\P_q|>0` задавать пары «купленный в H товар выше некупленного в H». Начать с всех `pn` пар; вес каждой `1/(pn)` даёт одинаковую суммарную массу каждой информативной группе. При ограничении бюджета выбирать до 128 пар равномерно без возвращения и нормировать их суммарный вес к единице. CatBoost использует веса пар; веса объектов не заменяют их. Автогенерация пар идёт внутри группы по разным labels. Это соответствует идее относительного сравнения implicit feedback, хотя BPR не доказывает превосходство конкретного boosting loss. [CatBoost ranking](https://catboost.ai/docs/en/concepts/loss-functions-ranking), [Rendle et al., BPR](https://proceedings.mlr.press/r7/rendle09a.html).

Группы без покрытых позитивов либо без отрицательных не дают таких пар. Их исключение из ranker training документировать количественно; сохранять в общем наборе оценки и отдельно показывать отсутствие покупки, retrieval miss и информативную группу. PairLogit не учится оценивать вероятность покупки: одинаковая добавка ко всем score группы исчезает из разностей. Поэтому чисто пользовательский признак полезен здесь через взаимодействия с товаром.

**C. Listwise QuerySoftMax — следующая ablation.** На полном `C_q` оптимизировать `−Σ_i y_qi log softmax(s_q)_i`; нормировать вклад группы по числу позитивов. Нулевые labels всей группы дают нулевой числитель и никакого ранжирующего сигнала; весь batch без позитивов имеет вырожденную нормировку. Такой loss распределяет массу между товарами, но не моделирует независимую вероятность нескольких покупок. Для непосредственного акцента на top-K можно вместо него проверить `YetiRank:mode=NDCG;top=10`; документация ограничивает non-Classic режимы CPU. Это отдельный эксперимент с учётом стоимости. [Официальные objectives CatBoost](https://catboost.ai/docs/en/concepts/loss-functions-ranking). Строки одного `group_id` должны идти подряд. [CatBoost Pool](https://catboost.ai/docs/en/concepts/python-reference_pool).

## Sampling и опасные границы

1. «Не куплен в H» не означает disliked: нет impressions, товар мог быть неизвестен пользователю. Даже прошлый view без покупки не является доказанным отказом.
2. Товар, купленный через два дня, допустим как ноль при `H=24 часа`. Исключать только `P_q`; нельзя очищать negatives по позднейшему train, validation или test. Иначе sampler получает будущие сведения.
3. Удалять повторы candidate ID до sampling; дубли draw при sampling с возвращением требуют сохранения multiplicity либо корректных inclusion probabilities. В пилоте без возвращения это проще.
4. Hard negatives из past-only retrieval подходят для его reranker. Для заявлений о полном каталоге их support недостаточен; нужен sampler с положительной вероятностью для каждого допустимого товара и известными весами. Sampling correction не восстанавливает stock или exposure.
5. In-batch negatives других пользователей не бесплатны: популярные товары встречаются чаще, позитив текущей группы может попасть в отрицательные, будущий товар может отсутствовать в её as-of universe. Нужны маски, вероятность отбора и временная проверка. LogQ из sampled-softmax нельзя механически переносить в PairLogit. [Yi et al., 2019](https://research.google/pubs/sampling-bias-corrected-neural-modeling-for-large-corpus-item-recommendations/).

## Рекомендация и минимальные решения

P0: сравнить A и B на одинаковых anchors, candidates, признаках и бюджете; B — главный purchase-ranking baseline, A сохраняет сигнал групп без покупок. P1: C после проверки числа информативных групп. Сильный контраргумент B — обучение только на покрытых покупках может плохо переноситься на остальные anchors; поэтому выбор по общей временной оценке, с явными срезами coverage, обязателен. Долю таких групп ещё предстоит измерить.

До запуска утвердить anchor/H, генератор и размер `C_q`, binary target/dedup, веса anchors/пар, temporal maturity и вычислительный бюджет. Validation/test ранжировать по всему фиксированному `C_q`, без искусственного добавления позитивов и случайных negatives: sampled ranking metrics могут менять порядок моделей. [Krichene и Rendle, 2020](https://research.google/pubs/on-sampled-metrics-for-item-recommendation/). Это оценивает reranking выбранного retrieval, а не полный каталог и не causal lift рекомендаций.
