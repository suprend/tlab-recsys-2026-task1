# 01. Anchors: когда именно спрашиваем рекомендации

Дата: 14 октября 2026. Независимый угол: единица запроса и наблюдаемый контекст. Purchase ranking — основной кандидат, но изложенные параметры являются предложением, а не утверждённым экспериментом. Назначение записки: `docs/target-research/01-anchors.md`.

## Что измеряем

Anchor задаёт распределение ситуаций, на которых оценивается модель. Ежедневный прогноз для известных пользователей и прогноз после просмотра отвечают разным вопросам; сравнивать их итоговые метрики как качество одной задачи нельзя. Без impressions результат характеризует предсказуемость покупок в наблюдавшемся трафике, а не эффект рекомендаций. Авторы GRU4Rec также отделяют offline next-item evaluation от прямой оценки онлайн-эффекта: [авторская документация](https://github.com/hidasib/GRU4Rec#reproducing-results-on-public-datasets).

Для сопоставления предлагаю временный общий контракт: query `q=(user_id,t,protocol)`, история всех сущностей строго `[t-W,t)`, target `Y(q)={product_id: purchase пользователя при t<event_time≤t+H}`. Это множество различных товаров; повторная покупка ранее известного товара разрешена. Для пилота `H=24 часа`, `W=7 суток`; next-purchase потребует отдельного определения при нескольких товарах в одну секунду. Покупки в секунду `t` исключаются явно, а их доля публикуется отдельно: это консервативная потеря наблюдений, не восстановленный порядок.

Общий snapshot строится до **всей глобальной timestamp-группы**: никакие события других пользователей в `t` не обновляют популярности, каталог или embeddings до прогноза. Подготовленные модели и priors тоже должны быть доступны до `t`; одного фильтра личной истории недостаточно. Работа Ji et al. показывает, что нарушение глобальной временной шкалы меняет оценки и порядок моделей: [первичная статья](https://arxiv.org/html/2010.11060v4).

## Три реальных протокола

**A. Fixed UTC, основной кандидат P0.** Один query в `00:00:00 UTC` каждого дня для каждого пользователя с хотя бы одним событием любого типа в `[t-7 суток,t)`. Текущего товара нет. Eligibility не требует будущего визита, просмотра или покупки. Это прогноз на следующие сутки для недавно наблюдавшейся аудитории; он включает отсутствующих сегодня пользователей. Начало UTC-дня не означает начало локального дня покупателя. Первую неделю оставить warmup, чтобы eligibility и окно истории были полностью наблюдаемы внутри файла.

**B. Наблюдаемый вход в сессию, P1.** Ключ `(user_id,user_session)`. Anchor — первая наблюдаемая секунда ранее не встречавшегося ключа, если в ней есть `view`. Не требовать второго события, минимальной итоговой длины сессии или последующей покупки. Это «первый наблюдаемый просмотр сессии», не гарантированный реальный вход: лог не содержит отдельного page-entry события. История остаётся `<t`; отдельный context содержит только множество текущих просмотренных товаров и их атрибуты из view. Контракт предполагает выдачу после закрытия секундного пакета, без использования cart/purchase этого пакета. Target остаётся общим `(t,t+H]`, включая следующие сессии, а не ограничивается будущей границей текущей. Наблюдение текущего item согласуется с session-based подходом, использующим текущий input для предсказания следующего события; оно не доказывает полезность для purchase ranking: [Hidasi et al.](https://arxiv.org/abs/1511.06939).

**C. Qualifying view с ограничением частоты, P1.** Anchor на первой секунде с `view`, затем не раньше чем через 30 минут после предыдущего выбранного anchor пользователя. Решение использует только уже выбранные anchors и текущий view; session ID не требуется. Контекст и label-окно как в B. Такой cooldown ограничивает запросы активных пользователей и допускает обновление намерения внутри длинной сессии. Выбор «последнего просмотра перед покупкой» запрещён: он требует будущего результата. Cart-trigger допустим как отдельная условная задача, но не смешивается с view-trigger.

## Частота, нули и стоимость

Для A число queries равно `Σдень eligible_users(t)`, для B — числу подходящих первых секунд ключей, для C — результату последовательного cooldown. Fixed UTC не обязательно дешевле: грубая верхняя граница при всех 3 022 290 пользователях ежедневно — 93,69 млн queries за 31 день, до warmup и maturity. Фактические количества, доля пустых `Y` и runtime **не измерены**. Стоимость ранжирования приблизительно пропорциональна `queries × candidates`; следует отдельно измерить построение истории, retrieval и scoring.

При `H=24 часа` дневные окна A не перекрываются. В B/C одна покупка может размечать несколько queries: это прогнозы нескольких возможностей выдачи, а не независимые покупки. Публиковать кратность такого повторного покрытия и использовать неопределённость с группировкой по пользователю. Query без покупки сохраняется в манифесте. Долю `Y=∅` считать среди всех зрелых queries; метрики ранжирования по непустым queries маркировать как условные. Если используется нулевая полезность пустого query, явно зафиксировать эту конвенцию. Она не оценивает вероятность покупки или качество отказа от выдачи.

## Контроль, рекомендация и ограничения

Обязателен last-view baseline: товары из самой поздней прошлой view-секунды, затем предыдущие distinct views, остаток — strict-past popularity. Для B/C отдельно проверить вариант с текущим view-context впереди. При ties использовать заранее фиксированный порядок ID, не выдавая его за хронологию. Все модели получают одинаковые anchors и кандидатов. Простые session-методы способны конкурировать со сложными моделями: [Ludewig, Jannach](https://arxiv.org/abs/1803.09587).

Рекомендую A для первого исследования общего пространства пользователей/товаров; B — отдельная проверка чувствительности с тем же warmup. Сильный контраргумент: A создаёт много неактуальных запросов и разбавляет текущий интерес; если предполагаемая выдача происходит только при посещении, B лучше соответствует применению.

Пять обязательных edge cases: несколько views в `t` остаются множеством без порядка; purchase в `t` не попадает в target; два пропущенных session ID не склеиваются, B пропускает их с отчётом, C сохраняет; сессия на левой границе не объявляется новой реальной сессией; справа допускаются только anchors с `t+H<T_end`, где `T_end` — исключительная граница непрерывного доступного лога. Полнота истории внутри октября не делает её lifetime-историей.

Минимальные решения до обучения: выбрать A либо B/C как основную ситуацию выдачи; утвердить eligibility/cooldown и доступность текущего view; закрепить `H`, границы target и зрелость; выбрать weighting queries/users и политику пустых queries; определить warmup и бюджет по измеренному числу anchors.
