# Оценка purchase ranking: единицы, знаменатели и пределы вывода

Дата: 14 октября 2026. Независимый угол: evaluation. Предлагаемый будущий документ: `docs/target-research/05-evaluation.md`.

**Рекомендация:** основной эксперимент — ранжирование множества будущих покупок на одинаковых, выбранных по прошлому запросах; NDCG@20 и Recall@20 считать по всем целевым товарам, отдельно показывая покрытие и запросы без покупок. Это предложение, а не утверждённый протокол. Контекст проекта: октябрь REES46 содержит покупки, просмотры и корзины, но не показы рекомендаций, доступность каталога или order ID; окончательная цель ещё открыта.

## Три возможных протокола

**A. Ближайшая покупочная группа.** Запрос `q=(u,t)` создаётся независимо от будущего. Target — различные товары в первой секунде с покупками внутри горизонта H; отсутствие order ID не позволяет назвать такую группу заказом. Для единственного товара удобны Recall@K и MRR@K. Несколько покупок одновременно требуют set-target, иначе выбор строки создаёт искусственный порядок. Этот вариант исследует ближайший намеренный выбор, но игнорирует последующие покупки горизонта.

**B. Множество покупок за сутки — рекомендуемый основной вариант.** Например, один запрос в 00:00 UTC пользователю с наблюдавшимся событием за предшествующие семь суток; eligibility использует только прошлое. История имеет время `<t`, `Y_q` содержит различные купленные товары при `t<event_time≤t+24h`. События ровно в t отдельно учитываются как исключённые пограничные исходы; это явная конвенция, требующая утверждения. Горизонт зрелый только при полном наблюдении до t+24h. Основные метрики: NDCG@20, Recall@20; K=10 — заранее объявленный дополнительный срез. Такой вариант оценивает ежедневный список, а не восстановление уже показанной карточки.

**C. Фиксированный retrieval для сравнения признаков.** Те же запросы и labels B, одинаковый список C_q из M кандидатов, построенный исключительно по прошлому. Меняется только ранжирование. Публикуются Recall кандидатов и итоговые метрики по полному Y_q; targets нельзя принудительно добавлять. Улучшение retrieval — отдельный эксперимент со своим изменяемым C_q. Случайные негативы допустимы как явно отдельный диагностический benchmark: sampled-метрики могут менять относительное преимущество моделей даже в ожидании. [Krichene и Rendle, KDD 2020](https://research.google/pubs/on-sampled-metrics-for-item-recommendation/).

## Точные определения

Пусть L_q — ранжированный список различных товаров, r_j=1[L_q[j]∈Y_q], P_q(j)=Σ_{i≤j}r_i/j. Позиции начинаются с 1; за концом списка r_j=0. Для непустого Y_q:

- `Recall_q@K = Σ_{j≤K} r_j / |Y_q|`;
- `DCG_q@K = Σ_{j≤K} r_j / log₂(j+1)`;
- `NDCG_q@K = DCG_q@K / Σ_{j≤min(K,|Y_q|)} 1/log₂(j+1)`;
- `RR_q@K = 1/min{j≤K:r_j=1}`, либо 0, если попаданий нет;
- `AP_q@K = Σ_{j≤K}P_q(j)r_j / |Y_q|`.

MAP и MRR — средние AP и RR по объявленной совокупности запросов. Здесь AP@K сохраняет знаменатель всех targets; альтернативу `min(K,|Y_q|)` нельзя смешивать с ним. Ненайденные релевантные товары дают нулевой вклад. [Определение AP/MAP авторов Introduction to Information Retrieval](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html). Нормировка NDCG и обработка одинаковых scores должны быть заданы явно. [Официальная документация scikit-learn](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.ndcg_score.html).

При одном target Recall равен HitRate; AP@K=RR@K, поэтому MAP дублирует MRR. NDCG становится `1/log₂(rank+1)` при попадании. При set-target MRR учитывает только первое попадание, тогда как Recall/NDCG замечают остальные; поэтому MRR не основной критерий B.

## Пустые запросы, покрытие и усреднение

При Y_q=∅ Recall/AP/NDCG математически не определены. Предлагаю сообщать: долю зрелых непустых запросов p; условные метрики по ним; дополнительную all-query метрику с явно объявленным нулём для пустых. При одинаковом query-усреднении последняя равна p×условная. Она не измеряет калибровку вероятности покупки и не вознаграждает корректное воздержание от рекомендаций. Незрелые запросы исключаются с отдельным счётчиком, а не превращаются в отрицательные.

Пусть U_t — все товары, наблюдавшиеся до t, лишь proxy каталога. Показывать отдельно `|Y_q∩U_t|/|Y_q|`, `|Y_q∩C_q|/|Y_q|`, а также all-target и covered-target метрики. Товар вне C_q получает бесконечный ранг; в основной NDCG идеальный знаменатель всё равно использует полный Y_q. Covered-target вариант заменяет relevance на Y_q∩C_q и исключает пустое пересечение; это меняет задачу и может скрыть потери retrieval. Срез cold относительно U_t показывается отдельно; он не исчезает из all-target результата.

Основное среднее — macro по запросам. Дополнительно: сначала среднее внутри пользователя, затем macro по пользователям. Частые anchors иначе увеличивают вес активных пользователей. Eligibility «активен в прошлом» и выбор «активен в будущем» принципиально различаются.

## Надёжность, контроли и границы

Предлагаю парный bootstrap разности метрик: выбирать пользователей с возвращением вместе со всеми их запросами, пересчитывая исходный estimand; сообщать 95% интервал. Срезы по дням и раннему/позднему test нужны отдельно: пользовательская кластеризация не покрывает общий временной шок. Это план проверки, не уже измеренная устойчивость.

Обязательные контроли: популярность покупок за прошлые семь суток; последний просмотренный товар первым; различные недавние товары пользователя по давности, затем популярность. У всех одинаковы anchors, candidates и tie-break. Пять edge cases: пустой Y; target вне U_t; повторная покупка ранее купленного товара; несколько покупок в одну секунду; одинаковые scores либо список короче K. Повторы разрешены между запросами, но item встречается один раз внутри списка и set-target.

**Сильный контраргумент:** ежедневные anchors могут давать слишком мало покупок и плохо соответствовать реальному месту рекомендаций. Тогда сравнить B с наблюдаемым session-start на validation, сохранив явную условность оценки; не выбирать запросы непосредственно перед будущей покупкой.

Минимально утвердить: anchor/eligibility, H и границы, single/set relevance, U_t/C_q/M, K, пустые и cold targets, усреднение, chronology и лимит выбора на validation. Даже положительный результат означает предсказуемость наблюдавшихся покупок: без показов и механизма назначения воздействия он не доказывает causal lift рекомендаций. [Schnabel и соавторы, ICML 2016](https://proceedings.mlr.press/v48/schnabel16.html).
