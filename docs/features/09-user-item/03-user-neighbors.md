# User-user соседи: голоса о кандидате и цена слабого пересечения

Дата: 14 октября 2026. Независимая исследовательская записка; ниже предложения, результаты обучения отсутствуют. Предпочтительная проверка — purchase ranking; anchor, горизонт и split остаются открытыми. Контекст: [данные](../../data.md), [план](../../experiment-plan.md). В октябре 3 022 290 пользователей, медиана четыре события: перекрытие историй нужно измерять, а не предполагать.

## Семантика и время

Просмотр означает наблюдавшийся интерес, покупка — положительное действие; отсутствие события не означает неприязнь или известный отказ после показа. Частота действий и сила предпочтения различаются: это принципиальное свойство implicit feedback у [Hu, Koren, Volinsky](https://yifanhu.net/PUB/cf.pdf). Здесь нельзя интерпретировать соседский score как вероятность покупки.

Grain результата — `(user u, candidate i, anchor t)`. Начальный P0 использует общий снимок `s=floor_day_UTC(t)`, события `[s−W,s)`, предлагаемый `W=7 суток`. Это устаревающая, но strict-past история; `snapshot_age_seconds=t−s` и доступная длина окна обязательны. Ни событие при `s`, ни текущая группа одинаковых секунд не включаются. Для раннего октября окно обрезано началом наблюдения. Все snapshot-параметры вычисляются только из доступного прошлого; подбор W, K, λ выполняется на validation. Снимок конца train нельзя ретроспективно применять к ранним train anchors.

## P0: компактный соседский канал

Пусть `x_uj=1`, если u имел хотя бы один view/cart/purchase товара j в окне; `y_uj=1`, если имел purchase. Это distinct user–item индикаторы: десять покупок одного соседа дают один голос. Определим `d_u=Σ_j x_uj`, `n_uv=Σ_j x_uj x_vj`,

`a_uv = [n_uv/√(d_u d_v)] · [n_uv/(n_uv+λ)]`, при `d_u d_v>0`, иначе 0.

Первая часть — cosine; вторая — предлагаемый shrinkage за слабую поддержку, например стартовый λ=2. `N_u` — до K=50 пользователей v≠u с максимальным положительным a. Равенства разрешает фиксированный hash идентификатора; идентификатор не становится числовым признаком. Базовый принцип cosine-соседей и голосов их покупок описан авторами [Amazon Recommendations](https://www.cs.umd.edu/~samir/498/Amazon-Recommendations.pdf); конкретные окно и shrinkage здесь наши кандидаты.

Признаки:

- `neighbor_buy_share q_ui=Σ_(v∈N_u) a_uv y_vi / D_u`, где `D_u=Σ_(v∈N_u) a_uv`.
- `neighbor_buy_support c_ui=Σ_(v∈N_u) y_vi`: число разных проголосовавших соседей.
- `neighbor_buy_effective_support e_ui=(Σ a_uv y_vi)²/Σ a_uv² y_vi`; при отсутствии голосов 0.

q безразмерен, c/e измеряются в пользователях. D и число найденных соседей — user-only диагностическая поддержка, не personalized cross. При D=0 записываем q=0 и `neighbors_missing=1`; при D>0,c=0 q=0 означает отсутствие покупок у наблюдавшихся соседей. Нормировать только по купившим нельзя: бинарный голос тогда превращает любой ненулевой score в единицу. u исключается из поиска и голосов, иначе собственная покупка напрямую поддерживает повторную рекомендацию.

## P1/P2: популярность и проверка механизма

**P1.** Inverse-user-frequency подавляет общие массовые товары в сходстве — первичное обоснование у [Breese, Heckerman, Kadie](https://arxiv.org/pdf/1301.7363). Предложение: `f_j=log((N+1)/(df_j+1))`, `z_uj=x_uj f_j`; cosine(z_u,z_v) заменяет первую часть a, shrinkage остаётся. N — число пользователей с непустым x, df — distinct users товара в том же снимке. Это сглаженная адаптация, не точная формула статьи; веса обновляются только forward snapshots. При нулевой норме z сходство 0, причина отмечается отдельно.

Отдельно `p_i^(−u)=Σ_(v≠u)y_vi/(N−1)` при N>1: доля активных пользователей, купивших товар, не conversion. Сглаженный остаток `r_ui=(Σ a_uv y_vi+τp_i^(−u))/(D_u+τ)−p_i^(−u)`, τ>0 в единицах веса. При D=0 остаток 0, missing сохраняется; при N≤1 p/r missing. Он отделяет соседское превышение от популярности, но не устраняет exposure bias.

**P2.** Candidate-masked пересчёт: заменить для обоих пользователей `x_vj` на `x_vj·1[j≠i]`, заново найти N_u^(−i), затем считать прежние y_vi-голоса. Это проверяет, существуют ли общие интересы кроме самого кандидата. Перевзвешивание фиксированного исходного topK не эквивалентно новому поиску. Стоимость становится candidate-dependent; начинать только с диагностической выборки.

## Стоимость и крайние случаи

Использовать inverted postings `item→users`, sparse x/y и кэш соседей только для запрашиваемых `(u,s)`. Полный поиск через postings требует `O(Σ_(j∈H_u)df_j)` посещений; предвычисление всех пар — `O(Σ_j df_j²)`. Популярные товары могут доминировать. Dense U×U при 3 млн пользователей — около 36 TB float32 без накладных расходов.

Предлагаемый бюджет пилота: 10 000 user-snapshot, последние L=50 distinct товаров, максимум H=200 пользователей на posting, стабильная hash-выборка только из прошлого; ≤100 млн посещений, 8 GB RAM, один час как stop-limit, не обещание скорости. В пилоте x также ограничен L: d/n описывают усечённую историю; y сохраняет полное окно. После выбора соседей |C| кандидатов требуют `O(K|C|)` sparse lookup. Ограниченный поиск приблизителен: сохранять retained-posting share и сравнивать с точным поиском на малой выборке. Amazon отдельно предупреждает о потере качества при сокращении пространства соседей.

Проверить пять случаев: пустая история; единственный общий бестселлер; новый для окна кандидат; повторная покупка; два пользователя с совпадающими короткими историями. Cold-start получает baseline-популярность и missing, а не искусственных соседей. Binary x/y устойчивы к точным дублям; реальные повторы остаются в исходных данных. Новизна относительно окна не доказывает новизну каталога.

## Две ограниченные гипотезы

**HYP-021 — proposed.** Shrinkage плюс e/c позволяют бустингу отличить согласованную аудиторию от случайного пересечения. Контрмеханизм: любой эффект объясняется популярностью/активностью. Сравнить strong user–item baseline, baseline+q, baseline+q+c+e, baseline с activity-matched случайными соседями при одинаковых anchors/candidates/coverage. Бюджет: эти четыре варианта, один W/K; принять при положительной нижней границе 95% user-block bootstrap разницы основной ranking-метрики и соблюдении бюджета подготовки. Иначе сохранить rejected.

**HYP-022 — diagnostic.** Candidate masking сохраняет полезный сигнал на unseen-to-user товарах, но снимает тривиальный repeat-эффект. Контроль — исходные соседи и item-popularity baseline; бюджет 2 000 пар, без полного расширения P2. Принять продолжение только если измеримый прирост остаётся на unseen-срезе и стоимость допускает основной пилот; иначе rejected. Все решения принимаются на validation, test используется после фиксации. Добавочные абляции заменяют варианты внутри бюджета: binary против event-count весов, IUF против raw cosine; новые ячейки автоматически не добавляются.
