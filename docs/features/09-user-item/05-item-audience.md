# Пользователь ↔ аудитория товара: профиль до действия и неоднородность

Дата: 14 октября 2026. Независимое исследование; ниже предложения экспериментов, не результаты обучения. Purchase ranking остаётся рабочей гипотезой; target, horizon и split не утверждаются. Идентификаторы HYP037/038 не переопределяются.

## Основания и временной контракт

Факты из общего brief: 3 022 290 пользователей, 166 794 товара, 624 заполненных category_id; медиана истории — четыре события. Нет показов и оценок предпочтения. Поэтому аудитория — люди с наблюдаемым действием, а близость к ней — совместимость поведения, не вероятность покупки. Hu, Koren, Volinsky различают предпочтение и уверенность implicit feedback; покупки тоже бывают подарками. [Первичная статья, 2008](https://yifanhu.net/PUB/cf.pdf).

Предложение: отдельные аудитории `k=purchase/view/cart`, без предположения вложенной воронки. Grain итогового признака: `(query user u, candidate item i, anchor t)`. UTC-истории всегда полуоткрытые. Для дешёвого P0 строить дневной snapshot в τ≤t, используя только события `[τ−7d,τ)`; все кандидаты дня используют одну версию. Лаг `t−τ` — секунды, отдельный признак. Это лаговая аппроксимация, а не точное rolling-состояние в t. Для окна аудитории хранить `min(7d,τ−log_start)` в секундах; для вложенных профилей — возраст наблюдения anchor и среднее покрытие сохранённых p. Усечённое окно не считать полной неделей.

Пусть `A_ik(τ)` — уникальные пользователи с действием k по i в окне. Для каждого v выбрать последнее такое событие s<τ, затем записать профиль `p_v(s−)` строго до s. Повторные действия меняют сохранённый профиль, но человек имеет вес один. Это явная семантика «последнее действие», не event-weighting. Все события одинаковой секунды получают профиль до обновления всей секунды.

Базовый профиль: `h_vc(a)=count(view, category_id=c, [a−7d,a))`, `p_vc(a)=h_vc/Σ_c h_vc`. category_id — ключ, числовой порядок не используется. При нулевом знаменателе профиль отсутствует. Никаких IDF, fitted vocabulary или обучения P0 не нужно; словарь категорий расширяется по наблюдаемым событиям. Профиль anchor `q=p_u(t−)` и исторические p строятся одинаково. View frequency — предложенный вес; distinct products проверяются отдельно.

**Другая допустимая конструкция:** `p_v(τ−)` для всех членов исторической аудитории. Это current-cohort rehash: описывает нынешние интересы прошлых посетителей. Использовать можно только прошлое относительно τ; выдавать такой профиль за состояние v в s нельзя. Общая временная шкала принципиальна: [Ji et al., TOIS](https://arxiv.org/abs/2010.11060) показывают искажения offline-оценки при её нарушении. Конкретный snapshot-контракт здесь — наше предложение.

## P0: средний профиль с честным support

В основном варианте удалить u из аудитории: `B={v∈A_ik:v≠u, p_v(s_v−) exists}`, `n=|B|`, `S=Σ_B p_v`, `μ=S/n`.

- `aud_cos_k=(q·μ)/(||q||₂||μ||₂)`, диапазон [0,1], безразмерный.
- `aud_profiled_users_k=n`, единица — уникальные люди; `aud_users_k=|A_ik\{u}|` включает людей без профиля.
- `aud_profile_coverage_k=n/aud_users_k`, доля; при пустой аудитории missing.
- `aud_self_member_k` и `user_profile_views`, соответственно флаг и число view-событий, показывают источник неопределённости.

При n=0 либо отсутствии q similarity=missing и отдельный reason-флаг; нулевой cosine означает наблюдаемые непересекающиеся интересы. При n=1 признак вычислим, но support нельзя скрывать. Self-exclusion делается точным вычитанием сохранённого вклада u и единицы из profiled count, только если этот профиль существует; общий audience count корректируется независимо. Не вычитать текущий q вместо исторического p_u(s−).

Начать purchase-аудиторией; добавить viewer prototype как отдельную абляцию P0. Не смешивать их коэффициентом «purchase важнее view» без проверки. Пустая purchase-аудитория не заменяется view молча. Сходство не гарантирует комплементарности товаров и не заменяет наблюдаемое поведение пары.

## P1: распределение, корзины и остаточная механика

Среднее скрывает различие между двумя узкими группами и одной широкой. Предложение с компактной статистикой: `R_ik=Σ_B sqrt(p_v)` покоординатно; `aud_BC_k= sqrt(q)·R_ik/n`. Это средний коэффициент Бхаттачарьи между пользователем и отдельными профилями, [0,1], безразмерный; применяется та же self-exclusion. Формула предложена здесь, результаты для REES46 отсутствуют. При q=(½,½) аудитория из двух one-hot профилей даёт 1/√2, а два профиля (½,½) дают 1: одинаковый μ больше не скрывает различие.

Cart prototype — P1 с теми же правилами. Дополнительно сравнить full profiles с исключением candidate item из view-историй обоих участников: иначе прежние просмотры i механически сближают пользователя и аудиторию через категорию i. Это проверка добавочной информации сверх прямой истории, не универсальное лечение leakage.

## P2: несколько прототипов

Локальные K≤4 центроида исторических профилей аудитории: `aud_mode=max_l cos(q,μ_il)` плюс число людей выбранного mode. Fit только на допустимом snapshot; новый товар/малый support остаются P0, без выдуманного кластера. MIND мотивирует представление нескольких интересов, но исследует user retrieval, а не наш audience-feature: [Li et al., CIKM 2019](https://arxiv.org/abs/1904.08030). Общие user layers уже исследованы в `docs/features/05-user-layers/`; повторять их как новую гипотезу не следует.

## Стоимость, проверки и критерий

Оценка: dense float32 `item×624×2 audiences` занимает 0,833 GB для одной статистики S; R удваивает это. Это арифметика без индексов, pair-профилей и runtime overhead. Главная стоимость — distinct `(item,user,k)` и сохранение sparse p для self-subtraction, не cosine. Строить snapshot последовательным проходом с дисковыми промежуточными таблицами; хранить лишь нужные версии, не матрицу 3m×166k. При cached norm(S) lookup O(nnz(q)+nnz(p_u)) с self-subtraction; norm обновляется как `||S−p_u||²=||S||²−2S·p_u+||p_u||²`. P2 требует отдельного замера.

Предложенный бюджет пилота: один дневной snapshot, purchase→view последовательно, лимит 8 GiB RAM и два часа построения; при превышении сначала уменьшить частоту обновления/область пилота, не обещать весь месяц. Замеры RSS, disk bytes, wall time и coverage обязательны.

Абляции на одинаковых причинных Q/Y/C: первоначальный manual-18 baseline и расширенный strong user-item baseline показывать отдельно; затем +purchase, +view, +R, +cart. Self-included/excluded, event-time/current-rehash, event/distinct-product profile и frozen-day/точное состояние сравнивать по одному. Edge cases: первый view даёт пустой профиль посетителя; единственный покупатель совпадает с u; purchase/view одной секунды; человек сменил интерес после покупки; ранний октябрь имеет усечённые вложенные окна. Отчитываться по coverage и sparse-history срезам; улучшение similarity само по себе не критерий успеха.
