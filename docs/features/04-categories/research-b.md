# Тема 4B. Категория как условие интереса и масштаба

Дата: 14 октября 2026. Независимый угол: небольшие условные признаки поверх сильного boosting baseline; записка A не использовалась. Ниже — предложения экспериментов, не измеренный прирост.

## Основания и границы

DIN моделирует интерес относительно кандидата и использует категориальную историю; это основание проверять user×category взаимодействия, но не доказательство полезности конкретной ручной формулы на REES46. [Первичная статья DIN](https://arxiv.org/html/1706.06978v4). DHAN отдельно исследует иерархию категорий: её эффект следует отделить от агрегатов по точному ID. [Статья авторов DHAN](https://arxiv.org/abs/2005.12981).

По предоставленной диагностике October: 624 category_id, 252 ID с именами, 126 уникальных category_code; 372 ID никогда не именованы. Числовой ID — самостоятельный категориальный ключ, не порядковая величина. Одинаковый code у нескольких ID не доказывает взаимозаменяемость ID. Основные агрегаты сохраняют все ID; объединение по code и префиксам — отдельный эксперимент темы 6. Неизвестные имена не собирать в одну поведенческую «категорию missing». Поздние предполагаемые имена не использовать.

Anchor задаёт время t UTC и доступные атрибуты кандидата i, категории c, бренда b. История строго [t−7d,t); события одной секунды прогнозируются до любого обновления состояния. Если metadata кандидата недоступны на anchor, нужна последняя запись строго раньше t; будущий каталог запрещён. Для раннего октября хранить observed_window_days, а не объявлять полное недельное наблюдение.

## P0: четыре сигнала

Обозначим V_uc число view пользователя u в категории c за неделю, V_u — все его view, V_i и V_c — соответствующие общие числа view товара и категории.

1. **uc_view_share_7d = V_uc/V_u**, grain (u,c,t). Дополнительно передавать V_u и V_uc из baseline: одинаковая доля при одном и ста просмотрах имеет разную опору. При V_u=0 — missing и user_no_view_history=1; V_uc=0 при V_u>0 означает наблюдаемый ноль. Первоначально без fitted smoothing: иначе требуется только past-fit prior, а не глобальная октябрьская доля.
2. **uc_view_recency_7d = t−max(event_time)** среди view (u,c) в окне, секунды. Нет совпадения — missing плюс uc_unseen_7d. Это отсутствие недельного наблюдения, не «никогда не интересовался». Совместно с долей отделяет текущий интерес от массы повторных view.
3. **item_view_share_in_category_7d = V_i/V_c**, grain (i,c,t), view. Передавать V_c как support. V_c=0 — missing; V_i=0 при V_c>0 — 0. Это доля зарегистрированных просмотров, не CTR, рыночная доля или вероятность покупки. Категория с одним наблюдаемым товаром даёт 1: добавить число наблюдавшихся товаров, а не интерпретировать как сильную популярность.
4. **relative_price_category = log(p_i/m_c)**, grain (i,c,t). Для экономного MVP m_c — медиана последних положительных цен по одному товару из категории, наблюдавшемуся в [d−7d,d), d — начало текущего дня UTC; metadata берутся as-of d. Это закрытый дневной snapshot, а не точная rolling-медиана на t и не каталог доступных товаров. Цена кандидата p_i допустима только если известна на anchor. При нуле, отсутствии цены, m_c или менее пяти товаров — missing с отдельными флагами и support; порог пять — проверяемый инженерный выбор. Не удалять исходные нулевые цены.

## P1 и P2

**P1 user_category_entropy_7d:** grain (u,t), view; q_c=V_uc/V_u, H=−Σq_c log q_c, дополнительно K=число затронутых ID. K=1→H=0, V_u=0→missing. Формула соответствует [официальной документации SciPy](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.entropy.html); влияние на предсказание — гипотеза. При коротких историях проверить добавочный эффект сверх V_u и K, без заявления о стабильном «типе пользователя».

**P1 brand_inside_category_share_7d:** grain (u,c,b,t), view; V_ucb/V_uc_known_brand. Missing brand не совпадает сам с собой как настоящий бренд. Передавать знаменатель и долю view с неизвестным брендом; при нулевом знаменателе missing. Исторический бренд события не переписывать позднейшим брендом товара.

**P1 category_user_activity_7d:** grain (c,t), view; V_c/U_c, U_c — distinct наблюдавшиеся пользователи. Это интенсивность среди наблюдаемых посетителей, не доля всех пользователей. U_c=0→missing, передавать U_c; проверить вариант с исключением самого u.

**P2 metadata_similarity:** x_i — one-hot точного category_id и известного brand, без learned weights; z_u — средний x прошлых view за неделю. cos(x_i,z_u), нулевая норма→missing плюс flag. [Документация cosine](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.pairwise.cosine_similarity.html) задаёт нормированное скалярное произведение. При metadata только category/brand это почти переупаковка долей: сначала ablation, не новый большой pipeline. Префиксы code относятся к теме 6.

## Стоимость, проверки и решение

Разреженные (u,c), (u,c,b), item/category counters и очереди истечения дают линейное число обновлений по событиям после сортировки; стоимость snapshot цен — отдельная агрегация. Exact U_c требует счётчиков активных (u,c), не одной суммы. Не разворачивать users×624×windows. Оценки времени/RAM требуют benchmark, не обещания.

Ablation: baseline→четыре P0 по одному→P0 вместе; затем P1 блоками. Для redundancy использовать одинаковые anchors/candidates и четыре варианта baseline, +точные категориальные агрегаты, +таксономия темы 6, +оба. Отдельно оценить unnamed ID и support 1/2–4/≥5, cold users и товары. При ranking пользовательская entropy постоянна внутри candidate set: полезность возможна через взаимодействия, а не самостоятельное изменение порядка.

Обязательные edge cases: первый view; несколько событий в секунду; два ID с одним code; отсутствующий/изменившийся brand; единственный товар и нулевая цена. Проверить boundary t−7d и неизменность признаков при добавлении событий ≥t. Purchase/cart расширения оставить после выбора target/horizon: прошлые счётчики допустимы, будущие labels и незрелые outcomes — нет.
