# Тема 4A. Категории: интерес пользователя и положение кандидата

Дата: 14 октября 2026. Независимый угол: минимальный набор событийных агрегатов, который разделяет личную склонность, общую популярность категории и популярность товара внутри неё. Это предложение эксперимента; модели, цель и split не выбраны.

## Гранулярность и время

Факты предоставленного EDA: 624 заполненных `category_id`; 252 ID имеют текст, соответствующий 126 уникальным `category_code`; 372 ID весь октябрь без названия. Следовательно, ID и код — разные группировки. P0 использует ID как строковую категорию, не числовую величину; отсутствие кода не обнуляет историю ID. Код хранится отдельно с `code_missing`; будущие восстановленные названия исключены. Иерархические префиксы относятся к теме 6.

Для anchor `(u,i,t)` категория кандидата должна быть известна к моменту прогноза: из допустимых текущих атрибутов anchor либо последнего наблюдения до `t`. Месячная неизменность product→category — диагностика, а не разрешение использовать будущий каталог. Обозначим `N_e(g,W,t)` число событий типа `e` группы `g` в UTC-интервале `[t-W,t)`. Для одинаковой секунды сначала вычисляем весь пакет прогнозов, затем обновляем состояния. Документация Featuretools явно различает включение cutoff и исключение: требуемому интервалу соответствует `include_cutoff_time=False`; это подтверждает семантику, но не требует внедрения библиотеки. [Featuretools: Handling Time](https://docs.featuretools.com/en/stable/getting_started/handling_time.html).

## P0: компактный основной блок

1. **`uc_view_7d`, `uc_cart_7d`, `uc_purchase_7d`**: `N_e((u,c),7d,t)`, grain user×category_ID. Три отдельных счётчика вместо искусственной вложенной воронки. Ноль означает отсутствие наблюдавшихся событий в доступном окне. Добавляем общий `history_coverage_7d` и наблюдаемый возраст пользователя; раннее начало октября не считаем семью полными днями наблюдения.

2. **`uc_last_age_e`**: секунды от последнего события каждого из трёх типов по `(u,c)` за доступную историю до `t`. Если события не было, значение missing и индикатор отсутствия; нулевой возраст невозможен при strict-past секундных данных. Три давности различают завершённую покупку и продолжающийся интерес без ручной гипотезы о знаке эффекта.

3. **`uc_view_affinity_7d`**: `(N_view(u,c)+α·p_c)/(N_view(u)+α)`, где `p_c=N_view(c)/N_view(all)` на том же прошлом окне, `α=5` — заранее фиксированная экспериментальная константа. Это сглаженная доля просмотрных событий, не вероятность покупки. Сохраняем знаменатель `N_view(u)` как support; при отсутствии глобальных просмотров affinity missing. Prior обновляется только прошлым потоком, без итоговых частот месяца. Значение 5 проверяется на validation, не объявляется оптимальным.

4. **`c_view_users_1d`, `c_purchase_users_7d`**: число уникальных пользователей категории среди просмотров за сутки и покупок за неделю. Grain category_ID. Показывают широту интереса и покупательной активности; покупатели не называются транзакциями. Отсутствие истории даёт ноль плюс coverage. Глобальные признаки одинаковы для кандидатов одной категории, но различают категории.

5. **`ic_purchase_share_7d`**: `N_purchase(i,c)/N_purchase(c)`, grain item×category_ID; знаменатель обязательно передаётся модели. При нулевом знаменателе missing, при известном положительном знаменателе и отсутствии покупок товара — 0. Числитель берём из существующего item-блока, не пересчитываем. Это доля событий покупки внутри категории, не CTR и не доля продаж по заказам: orderID отсутствует.

P0 содержит 10 числовых сигналов плюс support/missing/coverage. Сильный baseline уже должен иметь обычные user/item counts: категорийный блок добавляет условный контекст, а не копии существующих столбцов.

## P1 и P2

P1: `uc_distinct_items_view_7d` и `uc_distinct_known_brands_view_7d` для `(u,c)` отличают изучение ассортимента от повторных просмотров; отсутствующий бренд не считается отдельным брендом. Вместе передаём долю просмотров с известным брендом. Точную cardinality окна нельзя получить суммированием дневных distinct.

Отдельная P1-абляция повторяет только affinity и purchase-recency на **полном текстовом коде**, объединяющем несколько ID; missing-коды не объединяем в фиктивную поведенческую категорию. Исторические события сохраняют атрибуты, доступные тогда; позднее появление текста не переписывает прошлое задним числом.

Ещё P1: `relative_price=log(price_i/median_price_c)`. Референс — последние положительные цены **различных товаров**, наблюдавшихся в категории за прошлые 7 суток, максимум одна цена на товар. Это ассортимент наблюдений, не полный каталог. Требуем, например, ≥20 товаров; иначе missing с support. Цена кандидата — допустимая цена anchor/as-of; ноль сохраняем отдельным флагом. Порог — гипотеза. P2: затухающие affinity и label-derived category rates; последние требуют зрелых исходов и задержки.

## Стоимость, проверки и абляции

Материализация: сортированный поток, разреженные `(u,c)` состояния, очереди истечения 7d, последние timestamps. Для distinct нужны счётчики кратности. Prefix-счётчики позволяют получать окно разностью двух strict-past lookup; joins делаем только для anchor/candidate ключей. `ASOF LEFT JOIN` сохраняет кандидатов без истории и даёт максимум одно совпадение; используем явное строгое неравенство и уникальное состояние на timestamp. [DuckDB: ASOF](https://www.duckdb.org/docs/current/guides/sql_features/asof_join). Полный anchor×event range join может создать огромный промежуточный результат; оконные операторы буферизуют вход. [DuckDB: Window Functions](https://duckdb.org/docs/lts/sql/functions/window_functions). Время и память требуют замера.

Проверки: события ровно на обеих границах окна; первый anchor без истории; разные ID с одинаковым кодом; ID без текста и бренд без значения; нулевая цена/малый ценовой support. Ordered categorical statistics CatBoost не заменяют корректную внешнюю хронологию: механизм статьи устраняет другой источник target leakage. [CatBoost paper](https://arxiv.org/abs/1706.09516).

Абляции на одинаковых anchors/candidates: baseline→counts/recency→affinity→category popularity→item share; затем независимые P1-блоки. Проверять прирост по короткой истории, missing-коду и редким категориям, стоимость подготовки и размер состояний. Для ranking отдельно измерять качество внутри категории и между категориями; для conversion сначала определить anchor/horizon. Никакая группа заранее не объявляется полезной.
