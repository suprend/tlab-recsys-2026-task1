# Тема 1B. Счётчики как объём, широта и повторение

Дата: 14 октября 2026. Независимый угол: минимальные счётчики с явной единицей наблюдения, устойчивость к burst и стоимость точного incremental расчёта. Записка A не читалась. Это предложение экспериментов; обучение и замеры не выполнялись.

## Семантика до формул

Факты из переданного EDA: 42 448 764 строки; только `view/cart/purchase`; 30 220 surplus точных дублей; 348 session ID встречаются у нескольких пользователей; 31 517 групп одного пользователя с одинаковой секундой. Purchase-строка не равна заказу или количеству единиц товара. Без impressions отношение покупок к просмотрам не является CTR. Повторы нельзя автоматически считать дублями, ботами или ошибками.

Для anchor `(u,i,t)` история `H_W(t)={e:t−W≤e.time<t}`, UTC. Все anchors одной секунды рассчитываются до добавления **любых** событий этой секунды, включая глобальные item-счётчики других пользователей. Текущий товар/сессия доступны только при соответствующей постановке anchor. Требование глобальной временной шкалы согласуется с исследованием утечек, но выбор конкретного split остаётся отдельным решением. [Ji et al., TOIS](https://arxiv.org/abs/2010.11060).

Счётчик пустой наблюдаемой истории равен 0; это не доказательство отсутствия более ранней активности. Добавить `user_seen_before` и `window_observed_seconds=min(W,t−dataset_start)`; `t−first_observed_user` — возраст наблюдения, не tenure. Общая длительность окна учитывает границу датасета, но не доказывает непрерывность логирования. Не делить counts автоматически на короткую экспозицию: это отдельная гипотеза.

## P0: конкретный компактный MVP

Пусть `N[g,k,W]` — число строк типа `k` в `H_W` на grain `g`. Предложены следующие **выбранные** сочетания, а не декартово произведение всех групп/окон:

| Признак | Grain; окно; типы | Что различает |
|---|---|---|
| `u_view_7d`, `u_cart_7d`, `u_purchase_7d` | user; 7×24 часа; три типа отдельно | Объём прошлой активности |
| `ui_view_7d`, `ui_cart_7d`, `ui_purchase_7d` | user–candidate product; 7 суток; отдельно | Наблюдаемая история именно кандидата |
| `i_view_24h`, `i_purchase_24h` | product; 24 часа; два типа | Свежий объём спроса, не вероятность конверсии |
| `u_view_1h` | user; 1 час; view | Короткий burst совместно с недельным уровнем |
| `u_distinct_view_items_7d` | user; 7 суток; view | `|{product_id}|`: широта просмотра |
| `i_distinct_view_users_7d`, `i_distinct_purchase_users_7d` | product; 7 суток; соответствующий тип | `|{user_id}|`: охват против повторов |

`N` учитывает исходные строки без молчаливой очистки; для exact duplicate sensitivity подготовить альтернативу с удалением только полностью совпадающих строк. Источник не перезаписывать; фильтрация model history и политика target-дублей документируются независимо. Для обоих вариантов сохранять одинаковые anchors/labels, чтобы не смешать эффект признаков с изменением задачи.

Если у entity нет истории, все её counts/uniques — 0. NULL/пустой текст категории не нужен для этих признаков: product ID и category ID не подменяются строковым названием. При реализации `count(*)` считает строки, `count(x)` исключает NULL, `count(DISTINCT x)` считает разные непустые значения: это существенно для дальнейших session/category features. [DuckDB aggregate semantics](https://www.duckdb.org/docs/current/sql/functions/aggregates).

## P1: только после измеренного P0

**Повторы.** `u_repeat_view_excess_7d=N[u,view,7d]−u_distinct_view_items_7d`. Это обращения сверх первого **в окне**, не число вернувшихся пользователей и не повторная покупка. Признак алгебраически избыточен при наличии обоих исходных counts: проверять как замену или отдельное облегчение обучения, а не объявлять новой информацией. Аналогично `N/unique` — интенсивность на наблюдаемую сущность; при `unique=0` вернуть NULL плюс флаг, без искусственного знаменателя 1. Для разнообразия достаточна одна такая трансформация, не все ratios.

**Burst.** Если одного `u_view_1h` мало, проверить `burst_share=N[u,view,1h]/N[u,view,24h]`, NULL при нуле; это доля активности, не скорость. Добавлять вместе с поддержкой `N24h`; первый час датасета отдельно стратифицировать. Порог «аномально много» нельзя выбирать по полному октябрю: только past-fit/freeze либо forward snapshots.

**Сессии.** `u_distinct_sessions_7d=|{(u,user_session)}|` по всем типам, NULL исключить, добавить `session_missing_count`. Это сессии с хотя бы одним событием в окне, не начатые/завершённые сессии. `current_session_events_so_far` — только предыдущие события `(u,s)`; доступен, если anchor раскрывает `s`. Полная длина сессии и «в ней потом купили» запрещены. Gap-сессии с фиксированным 30-минутным порогом — отдельная операционная гипотеза; вычислять по префиксу, без будущего закрытия. Session windows по gap действительно отличаются от rolling windows. [Apache Beam, windowing](https://beam.apache.org/documentation/programming-guide/#823-session-windows).

**Переходы.** Два счётчика user за 7 суток: `view→cart` и `cart→purchase` между соседними timestamp-группами внутри известного `(u,s)`, обе группы в окне. У каждой группы множество event types должно быть одноэлементным; смешанные группы исключать и считать отдельно как ambiguous. Несколько однотипных строк группы дают один переход. Переход не доказывает работу с тем же товаром: same-product версия — отдельный, вероятно более разреженный эксперимент. Не строить все пары событий: их число квадратично и преимущественно измеряет активность. Это наблюдаемые паттерны, не причинная воронка.

P2: approximate distinct и автоматический поиск многих окон — только после обнаруженного ресурсного ограничения/прироста; точные короткие окна служат контролем.

## Материализация и сильные проверки

Предлагаемый алгоритм: сортировка по времени; перед запросом удалить события `<t−W`, затем прочитать counts для всей секунды, затем добавить её строки. Обычные counts поддерживаются сложением/вычитанием. Exact unique требует reference count по `(entity,value)` и уменьшения cardinality только при переходе частоты `1→0`; сумма дневных uniques неверна. Для P0 хранить только выбранные состояния; пары user–item и очереди активных событий могут доминировать в памяти. После сортировки обход линейный по событиям для фиксированного набора окон; это оценка сложности, не обещание скорости на M3. Проверить wall time, peak RSS, spill и число активных ключей. DuckDB windows буферизуют вход и могут быть ресурсоёмкими; наивный self-join anchors×history тоже не принимать без замера. [DuckDB window documentation](https://duckdb.org/docs/lts/sql/functions/window_functions).

Контроли: B0 counts; B1 добавление uniques; B2 короткий burst; B3 sessions/transitions. Одинаковые anchors/candidates, бюджет обучения и временные границы; прирост оценивать над общим сильным baseline, включая recency из других групп. Для ranking user-only признаки постоянны внутри query: отдельно проверить, добавляют ли они полезные взаимодействия с item features. Отчёт по cold/warm history, одному/нескольким дням, повторным/новым кандидатам; raw counts против `log1p` — контроль представления, не обязательная очистка.

Минимальные edge cases: (1) перестановка строк одинаковой секунды не меняет признаки; (2) событие ровно `t−W` входит, ровно `t` исключается; (3) при истечении одной из двух одинаковых entity–value строк unique остаётся 1; (4) одинаковый session ID разных users не объединяет историю, NULL не становится общей сессией; (5) добавление будущих строк не меняет уже рассчитанные признаки. Сверить incremental результат с прямым bounded SQL на synthetic fixture и небольшом префиксе. Эти проверки верифицируют semantics независимо от целевой метрики; target/horizon и mature labels ещё требуется выбрать.
