# Базовые событийные счётчики: независимое исследование A

Дата: 14 октября 2026. Угол исследования: минимальный интерпретируемый state для сильного CatBoost, где интенсивность, охват и повторный интерес представлены раздельно. Это проект эксперимента, без обучения и обещаний прироста. Target, horizon и split остаются открытыми.

## Контекст и временной контракт

Факты из предоставленного контекста: October2019 содержит 42,45 млн событий `view/cart/purchase`; медиана пользователя — четыре события и один активный день. Нет impressions и order ID. Поэтому число покупок означает purchase-строки, а `purchase/view` не является CTR, числом заказов или автоматически вероятностью конверсии. Эти факты здесь независимо не перепроверялись.

Пусть anchor `(u,i,s,t)` известен в момент `t`, время UTC, `s=(user_id,user_session)`. Для группы `g` и типа `a`:

`C[g,a,W](t)=Σ 1[group(e)=g ∧ type(e)=a ∧ t−W≤time(e)<t]`.

`W=obs` означает `[T0,t)`, где `T0` — начало загруженного окна, а не lifetime. Состояние читается для ВСЕХ anchors секунды `t` до добавления любых событий этой секунды: это касается и item-популярности между разными пользователями. Сортировка строк внутри секунды не восстанавливает причинный порядок. В SQL `RANGE … CURRENT ROW` включает peers; `EXCLUDE CURRENT ROW` исключает только одну строку. Нужен `EXCLUDE GROUP` при единственном `ORDER BY event_time`, либо явное `event_time<t`. Документация также поддерживает `FILTER` и оконный `DISTINCT` ([DuckDB Window Functions](https://www.duckdb.org/docs/current/sql/functions/window_functions)).

## P0: выбранный минимум

В таблице `a∈{view,cart,purchase}`; тройки считаются раздельно. Выбор окон — проверяемая гипотеза о кратком интересе и недельной активности, а не результат поиска оптимума.

| Grain | Признаки | Смысл |
|---|---|---|
| User `u` | `u_{a}_7d`, `u_{a}_obs` — 6 | Недавняя активность и накопленная наблюдаемая история |
| User `u` | `u_unique_items_7d`, `u_active_utc_dates_7d` — 2 | Ширина поиска и распределение активности по датам |
| Item `i` | `i_{a}_1d`, `i_{a}_7d` — 6 | Быстрая и более устойчивая популярность |
| Item `i` | `i_unique_viewers_7d`, `i_unique_buyers_7d` — 2 | Охват пользователей вместо повторных строк |
| Pair `(u,i)` | `ui_{a}_obs` — 3 | Повторный интерес к конкретному кандидату |
| Pair `(u,i)` | `ui_recency_{a}_sec` — 3 | Время после последнего события данного типа |
| User `u` | `u_recency_any_sec` — 1 | Давность последней наблюдаемой активности |
| Session `s` | `s_{a}_prefix`, `s_unique_items_prefix`, `s_elapsed_sec` — 5 | Контекст текущего визита, если session доступна anchor |

Distinct определяется буквально: `|{product_id}|`, `|{user_id}|`, `|{UTC_date(event_time)}|` внутри соответствующей истории. Частичная UTC-дата допустима; это не число полных дней. `s_prefix=[T0,t)` с фильтром по ключу сессии; elapsed — `t−min(time(e))` в этом prefix, а не длительность завершённой сессии. Если задача выдаёт рекомендации без известной текущей сессии, весь session-блок исключается из согласованного baseline.

`recency=t−max(time(e))` по соответствующей наблюдаемой истории. При отсутствии события — `NaN` и индикатор `has_past_{a}`; ноль не используется как отсутствие. Session elapsed при пустом prefix тоже `NaN`. Для user и item добавить `history_age_sec=t−first_past_time` и `has_past`; age неизвестен до первого прошлого события. Эти поля означают возраст наблюдения, не возраст пользователя или товара.

Общая доступность: `available_history_sec=t−T0`, `coverage_7d=min(1,(t−T0)/604800)`. Они отличают нулевой недельный счётчик раннего anchor от полного наблюдаемого окна. Возраст сущности не заменяет coverage: впервые увиденный сегодня пользователь мог существовать раньше. Для существующего ключа без прошлых событий counts равны 0; отсутствующий session ID означает неизвестный session-блок, а не сессию с нулевой активностью. `COUNT(*)` считает строки, `COUNT(column)` пропускает NULL, что необходимо учитывать в реализации ([DuckDB Aggregate Functions](https://www.duckdb.org/docs/current/sql/functions/aggregates)).

Для next-purchase ranking user/session counts постоянны внутри одного query: их ожидаемая польза — взаимодействия с candidate-признаками. Item/pair counts непосредственно различают кандидатов. Для conversion user-интенсивность может работать напрямую; это нужно проверять отдельно.

## Материализация и стоимость

Рекомендуемый алгоритм — проход по времени с групповым read-before-update. Prefix-counts и последние timestamps требуют scalar-state по ключам; rolling counts — очередей истечения. Exact rolling distinct требует reference-count каждого объекта и удаления его из distinct только при последнем истёкшем вхождении. Суточные totals нельзя выдавать за точное rolling-окно с произвольным `t`.

Оценка алгоритма: сортировка `O(N log N)`, затем проход линейный при фиксированном числе окон, плюс запись `O(A·F)` для `A` anchors и `F` признаков. Реальная память зависит от активных пар и очередей, не только числа пользователей; Python-словари могут быть дорогими. Материализовать раздельными блоками и по согласованным anchors, без всех user×item комбинаций. 40 float32 колонок на миллион anchors — примерно 160 MB только значений, без ключей, NULL-масок и промежуточных данных; это арифметика, не benchmark. DuckDB допускает OOM на сочетаниях blocking operators и агрегатов; измерить peak RSS, spill и wall time ([DuckDB OOM](https://duckdb.org/docs/lts/guides/troubleshooting/oom_errors)).

Raw counts оставить основным вариантом: CatBoost квантует числовые значения по границам, поэтому логарифмирование всех счётчиков не является обязательным ([CatBoost Quantization](https://catboost.ai/docs/en//concepts/quantization)). Любые выученные границы/приоры для дополнительных преобразований должны соблюсти отдельный past-fit контракт; сами указанные counters не используют labels.

## P1, P2 и проверка

P1: `ui_unique_sessions_obs` с пропуском отсутствующих session ID; отдельный missing-session count. Для товара — уникальные cart-пользователи, если ablation покажет дополнительную пользу. Для user — distinct purchased items, чтобы отличить широту покупок от повторов. P2: экспоненциальное забывание и отношения интенсивностей; не вводить без выигрыша над count+recency.

Абляции на одинаковых anchors, candidates и временных границах: (1) базовые counts → +distinct → +recency/coverage; (2) удалить по одному user/item/pair/session блоку; (3) 1d item против 7d и обоих; (4) raw против отдельного `log1p` варианта; (5) sensitivity к точным дубликатам с сохранённым исходником. Метрика зависит от выбранной задачи; дополнительно срезы unseen pair/item, короткая история и ранний октябрь. Val/test histories обновляются только действительно доступными прошлыми событиями при зафиксированных весах; альтернативный frozen-history режим оценивается отдельно. Label horizon требует зрелых outcomes и purge, который определяется после выбора target.

Обязательные edgecases: пять same-second событий не попадают друг другу в историю; событие ровно `t−W` включено; две разные покупки одного товара не схлопываются; одинаковый session ID у разных users не объединяется; anchor в начале октября имеет нулевые counts и неполное coverage. Ни одна абляция не доказывает причинное влияние признака на покупки.
