# Тема 6A. Каждый узел category_code: строгая семантика агрегации

Дата: 14 октября 2026. Независимый угол: сохранить всю иерархию как дешёвый слой признаков, не подменяя её category_id и не создавая ложные вероятности.

## Данные и представление

По переданной диагностике полного октября 126 полных category_code образуют 159 уникальных узлов-префиксов: 13/60/85/1 на глубинах 1/2/3/4. Это инвентаризация конца месяца, не известный в начале каталог. Эти числа здесь независимо не пересчитывались. Предлагается forest с искусственным корнем `KNOWN_CODE`, отдельным `ALL_EVENTS` и независимыми `ID:<category_id>` для любых числовых категорий. Узел — полный префикс: `code:furniture.living_room.chair` отличается от другого пути, оканчивающегося на `chair`. Разделитель — точка; underscore остаётся внутри токена. Сохранять `node_key,parent_key,depth,first_observed_at`, терминальность именно as-of.

Событие с известным кодом обновляет каждый уникальный узел своего пути ровно один раз, `KNOWN_CODE` и `ALL_EVENTS` — по одному разу. Событие без текста обновляет `ALL_EVENTS` и свой ID; оно не становится общей семантической категорией «unknown». ID-признаки служат fallback и при известном коде. Если код для ID стал известен позже, не переписывать прошлые события молча: P0 использует текст, доступный у события; альтернативное восстановление требует отдельной политики provenance/as-of. Совпадение product→code за весь октябрь этого ограничения не отменяет.

## P0: полезный минимум

Для anchor `(u,candidate,t)` определить `C_u(n,e,W)` — число прошлых событий пользователя в поддереве n, `G(n,e,W)` — соответствующее глобальное число; `e∈{view,cart,purchase}`, `W=7×24 часа`, история `[t-W,t)` в UTC. Кандидатный путь доступен только из допустимых на t атрибутов. На каждом существующем уровне выдавать:

- `un_{e}_cnt_7d=C_u(n,e,7d)`: три счётчика grain `(user,node)`; глобально `node_view_cnt_7d`, `node_purchase_cnt_7d`, grain `node`. Покупка — строка purchase после выбранной общей политики точных дублей, не заказ.
- `un_{view,purchase}_recency_s=t-max(event_time<t)`: два интервала на `(user,node)`, по всей наблюдаемой истории; отсутствие события — NULL плюс `has_history`, не ноль секунд.
- `un_view_share_known_7d=C_u(n,view)/C_u(KNOWN_CODE,view)` и `un_view_share_all_7d=C_u(n,view)/C_u(ALL_EVENTS,view)`. Первая измеряет предпочтение среди распознанной истории, вторая сохраняет масштаб пропусков. При нулевом знаменателе NULL с флагом. Добавить `user_code_coverage_7d=known/all`.
- `node_view_users_7d=|{u:C_u(n,view,7d)>0}|`: точный distinct на `node`; `node_views_per_viewer_7d=G(n,view)/node_view_users_7d`, NULL при нуле. Это интенсивность наблюдаемых просмотров, не CTR.

Счётчик 0 означает отсутствие наблюдённых событий в окне; неизвестный путь означает NA и `candidate_code_missing`, отсутствующий четвёртый уровень — NA и глубину. Добавить `observed_window_seconds=min(W,t-start_of_dataset)`; ранний октябрь не даёт полных семи дней. Frequency/recency категории имеют прямой прецедент в [PCIC, §3.1.3](https://arxiv.org/html/2308.01195v1), но результат на повторных покупках grocery не доказывает прирост на REES46.

## P1: backoff и сглаженная иерархия

Вместо автоматического удвоения всех окон сначала проверить один feature `deepest_supported_depth`: максимальная глубина с `C_u(parent,view,7d)≥k`; k выбирается на временной development-проверке. Сохранять исходные уровни: backoff не должен стирать узкую историю.

Для ребра parent→n предложить условную долю `q̂_u(n|parent)=(C_u(n,view)+α q_global(n|parent))/(C_u(parent,view)+α)`. Здесь `q_global=G(n,view)/G(parent,view)` из допустимого прошлого, а не доля самого parent. При отсутствии глобальной поддержки — NA/backoff к ближайшему поддержанному предку. α задаётся заранее либо на warmup; глобальные priors — warmup-fit/freeze или forward snapshots. Shrinkage редких дочерних оценок к информации предков обоснован [McCallum et al., ICML 1998](https://www.cs.cmu.edu/~roni/papers/hier-icml98.pdf); указанная формула — наше предложение для событий, не воспроизведение их классификатора. P2: decayed counts и path embeddings только после измеренного выигрыша P0/P1.

## Материализация, проверки и эксперимент

Разворачивание известных кодов даёт максимум четыре семантических membership на событие; корни и ID — дополнительные обновления. Верхняя граница `4×42,448,764=169,795,056` memberships — оценка, не объём фактически известной истории и не benchmark. Не хранить dense `users×159×windows`: только наблюдённые `(user,node,event_type)` и требуемые anchors. Сначала прогнозировать всю группу одной секунды, затем обновлять состояние. DuckDB поддерживает `COUNT(DISTINCT ...)` в окнах и `EXCLUDE GROUP` для исключения peers одинакового timestamp ([документация](https://duckdb.org/docs/current/sql/functions/window_functions)); проверить установленную версию и измерить peak RAM. Для rolling distinct нужны множества/счётчики активности либо точный SQL; суммы дневных distinct неверны.

Пять обязательных случаев: одинаковый suffix у разных родителей; пользователь в двух siblings; события точно на t и t−W; неизвестный код при известном ID; короткий код, одновременно являющийся родителем длинного. Для последнего сумма детей может быть меньше parent из-за прямых терминальных событий: учитывать residual `STOP`; distinct parent — объединение пользователей детей и residual. Нельзя складывать уровни пути или distinct детей.

Ablations на одинаковых anchors/candidates: baseline+ID; добавить только полный код; добавить всех предков; добавить distinct/coverage; затем сглаживание. Отчёт отдельно по missing-code, новым user/node и малой поддержке, с временем/RAM. Target, horizon, candidate generation и временной split остаются решениями проекта; purchase/view не объявлять conversion probability.

## Review appendix — 14 октября 2026

У исходного deepest_supported_depth проверяется C_u(parent)≥k. С этой формулой название и смысл — deepest_parent_supported_edge_depth: ребёнок может не иметь истории. Для deepest_node_supported_depth проверять C_u(n)≥k у самого узла. При отсутствии поддержанного semantic edge значение missing с flag, ID fallback хранится отдельно; искусственный KNOWN_CODE не становится содержательным родителем-категорией. Оба варианта требуют отдельной проверки, исходная формула сохранена.
