# Тема 3 — нормировки: сначала единица наблюдения, затем деление

Дата: 14 октября 2026. Независимое исследование B; материалы исследования A не читались. Угол: минимальное семейство признаков с различными знаменателями вместо универсального «conversion rate».

## Факты и границы интерпретации

По предоставленному контексту October2019 содержит view/cart/purchase, но не показы, заказы или регистрацию. Покупки и просмотры — отдельные потоки; `purchase_count/view_count` может превышать единицу. Это отношение интенсивностей действий, не CTR и не вероятность покупки после просмотра. Медиана пользователя — четыре события: редкая история делает знаменатель частью сигнала, а не технической деталью.

Везде ниже история — `[t−7d,t)` в UTC, обрезанная началом доступных логов; `coverage_days` и `history_age` передаются отдельно. Всю группу одинаковой секунды прогнозируем до обновления состояния. Предлагаемые признаки — эксперимент, не подтверждённый прирост.

## P0: полезный минимум

1. **`u_category_view_share_7d`**: для `(user, candidate.category_id)` число прошлых view данной категории, делённое на все прошлые view пользователя. Это вложенная доля событий, `0≤s≤n`, где один просмотр принадлежит одной категории. Дополнения обязательны: `s`, `n`, `denom_zero`, возраст наблюдения. При `n>0,s=0` получаем наблюдаемый ноль; при `n=0` доля неизвестна, а не нулевая заинтересованность. Категория без текстового имени остаётся известным category_id. Биномиальная форма допустима как рабочая модель сглаживания, однако повторные действия одного пользователя зависимы: номинальные биномиальные интервалы нельзя выдавать за доказанную неопределённость.

2. **`i_purchase_view_action_ratio_7d`, `c_purchase_view_action_ratio_7d`**: для item и category_id — `P/V`, отдельно purchase и view. Передаём оба счётчика; `V=0` означает missing ratio, включая случай `P>0`. Ничего не ограничиваем единицей. Для пользователя аналогичное отношение отложить: baseline уже видит его счётчики, а поддержки мало. Не применять Beta–Binomial к этому отношению: успехи не вложены в испытания. Для настоящих биномиальных данных официальный интерфейс statsmodels принимает именно successes и failures ([GLM](https://www.statsmodels.org/stable/generated/statsmodels.genmod.generalized_linear_model.GLM.html)).

Этого достаточно для первой абляции над общими strict-past counts. У пользователя нормируется предпочтение, у item/category — состав действий; симметричное размножение всех формул по всем сущностям не требуется.

## P1: сглаживание и разные источники variation

**Вложенные доли.** Использовать `p̂=(s+κμ)/(n+κ)` с сохранением `s,n` и веса данных `n/(n+κ)`. `μ` — исторический фон, `κ` — сила prior. Различия сущностей могут отражать истинную гетерогенность, случайность малой выборки, сезонность и состав аудитории. Partial pooling сохраняет различия лучше полного объединения, но уменьшает шум независимых оценок ([Stan, repeated binary trials](https://mc-stan.org/learn-stan/case-studies/pool-binary-trials.html)). Для item возможна цепочка category_id→global; пользовательскую долю категории сглаживать к глобальной доле этой категории, а не общей константе. Категории с большим каталогом закономерно имеют иной фон. Нельзя объявлять numeric category_id семантическим деревом.

**Интенсивность во времени.** `g_views_per_observed_day=N_view/E`, для `g=user,item,category_id`; `E` — реально покрытая логами длительность окна, не число активных дней и не доказанное время доступности товара. У user `N/active_days` — отдельная условная характеристика активности. При `E=0` интенсивность неизвестна. Gamma–Poisson даёт рабочее сглаживание `(N+α)/(E+β)`, где β измеряется днями; временная неоднородность и сверхдисперсия требуют проверки. Связь count с exposure через log-offset описана в [statsmodels](https://www.statsmodels.org/stable/generated/statsmodels.genmod.generalized_linear_model.GLM.html), сопряжённость — в [Stan](https://mc-stan.org/docs/2_23/stan-users-guide/posterior-predictive-simulation-in-stan.html).

**Концентрация и всплески.** Для user добавить сначала только `category_view_HHI=Σp_c²`, затем альтернативно энтропию `H=−Σp_c log p_c` ([SciPy](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.entropy.html)). Это распределение внимания, не rate; при отсутствии view — missing, при одном — максимальная наблюдаемая концентрация с поддержкой один. Для item/category проверить `view_burst= N_[t−1d,t)/E_1 − N_[t−7d,t−1d)/E_6`; окна непересекающиеся, поддержки обеих частей обязательны. Разность избегает взрыва при нулевом прошлом фоне.

Все fitted priors, κ, clipping и пороги получают только warmup до первого downstream anchor и замораживаются либо обновляются forward snapshots. Fit на конце train нарушает strict-past ранних train rows. `ε` только меняет знаменатель произвольно; `log1p` сжимает шкалу, но не создаёт испытания, поддержку или зрелые исходы.

## P2, стоимость и проверка

Настоящий conversion-rate строить после выбора anchor и горизонта H: один допустимый anchor — одно испытание, `y=1` при целевой покупке в заданном будущем окне. В историю при t включать только anchor `a` с `a+H+δ<t`, где δ — заданная задержка доступности данных. Незрелый отрицательный исход нельзя считать отказом ([Chapelle, delayed feedback](https://wnzhang.net/share/rtb-papers/delayed-feedback.pdf)). Правила повторных anchors/атрибуции остаются target-dependent.

Материализация: один временной проход; sparse user–category state, item/category счётчики и очереди истечения событий. Distinct-user fractions требуют дополнительных множеств и остаются P2. Дневные buckets подходят закрытым UTC-дням, но не являются точной заменой rolling-окна. Benchmark стоимости нужен отдельно.

Абляции: counts → добавление P0; raw против smoothed долей; intensity отдельно от burst; HHI против H. Проверить cold-start, `P>0,V=0`, пустой category_code при известном ID, неполное раннее окно, одинаковые секунды. Сравнивать одинаковые anchors/candidates и отдельно малую поддержку; улучшение общей метрики не доказывает пользу каждой нормировки.
