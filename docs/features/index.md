# Группы событийных признаков: исследования и план отбора

Исследование 14 октября 2026 года. Пользователь запросил несколько независимых исследований на каждую из восьми тем и сохранение всех результатов. Для каждой темы выполнены две независимые записки; их предложения не являются измеренными результатами моделей. Итоговый target, horizon и split ещё не выбраны.

## Общие договорённости

Одна строка исходных данных — действие с товаром, не рекомендательный показ. Основные события: view, cart, purchase. Показатели на разных единицах (строки, уникальные товары, пользователи, сессии, зрелые прогнозные исходы) не смешиваются без явного определения.

Для прогноза в t история содержит только события со временем меньше t. Окно W — [t-W,t); одинаковые timestamp обрабатываются одной группой до обновления состояния. Временные снимки признаков присоединяются назад по времени. Это общая идея point-in-time retrieval; она не означает, что проекту нужен отдельный feature store. [Документация Feast](https://docs.feast.dev/getting-started/concepts/point-in-time-joins).

Параметры, обучаемые по данным (priors, quantiles, clusters, IDF, encoder), также должны быть получены раньше строк, для которых создают признаки. Само исключение будущих событий из history не предотвращает утечку через fitted state. Начальный простой вариант — warm-up до downstream train, затем заморозка параметров и обновление только наблюдённой истории; более сложный — forward snapshots.

Полный октябрь — 31 день. Полное 30-дневное окно появляется только 31 октября, если начало наблюдения принимается за 1 октября 00:00 UTC. `history_age` означает возраст наблюдаемой истории, не регистрацию или lifetime пользователя. Неполное окно, нулевая активность и неизвестное свойство — разные состояния.

Цена и бренд меняются: candidate metadata и контекст прошлых событий требуют собственной as-of политики. Непроверенные названия категорий из следующих месяцев не включаются автоматически. Подробные исходные факты — [данные](../data.md), [аудит восстановления категорий](../category-recovery.md).

Допущение replay: ingestion/availability timestamp в исходной схеме отсутствует; считаем событие доступным сразу после его секунды event_time. Это необходимое допущение, а не доказательство отсутствия задержек/исправлений логов. Если появится время фактической доступности, потребуется одновременно ограничивать event-time и availability-time; один as-of join по event_time этого не обеспечивает. [Feast: available feature values](https://docs.feast.dev/getting-started/concepts/point-in-time-joins).

Группировка одинаковой секунды глобальная: item/category counters других пользователей также не видят события на t. При конфликтующих brand/price последней доступной секунды нельзя выбирать строку по случайному порядку; сохраняется ambiguity.

Для learned слоя с fit cutoff τ отдельно хранить `layer_coverage_seconds_W=min(W,max(0,t−τ))`, помимо source coverage. Основной event-time-owner вариант не создаёт counters до τ; полная недельная история слоя появляется через неделю после τ. Пересчитанный в τ прошлый cohort snapshot — другой допустимый режим, но не историческое назначение событий моделью до её появления.

## Согласованные рекомендации

Эта сводка выбирает небольшой порядок экспериментов из независимых предложений; отметка P0 в отдельной записке не является общим решением включить признак. Сначала общий строгий baseline, затем добавления по одному семейству. Результатов обучения пока нет.

Обозначения: `C(g,k,W)=count{e:g(e)=g,type(e)=k,t−W≤e.time<t}`, `V=C(…,view,…)`, `P=C(…,purchase,…)`; `S=2019-10-01 00:00 UTC`. При нулевом знаменателе отношение missing с флагом и support; при положительном знаменателе и нулевом числителе — настоящий ноль. Для счётчиков выбран единый encoding: пустая доступная история → 0, даже при coverage=0, вместе с coverage/observed flag; не наблюдавшаяся временная полоса не интерпретируется как доказанная неактивность. Возраст до первого прошлого события — missing с has_history=0, а не измеренный нулевой возраст. Не заменять отсутствие наблюдаемого текста отсутствием активности ID.

| Тема | Полезный минимум для первой проверки | Отложить и как проверить |
|---|---|---|
| 1. Событийные счётчики | User: три counts 7d и distinct viewed items 7d. Pair `(u,i)`: три counts 7d и recency view/purchase по наблюдаемой истории. Item: view/purchase counts 24h и distinct viewers 7d. Типы отдельно, без молчаливой фильтрации. | Session prefix — только если сессия доступна anchor; дополнительные burst/transition признаки после baseline. Повторы и distinct проверять отдельными добавлениями. |
| 2. Временные окна | 1d и 7d на выбранных grains; `E_W=max(0,t−max(S,t−W))/86400`, `has_history`, `history_age=t−first_past_time`. Это покрытие выгрузки и возраст наблюдения, не exposure. | 30d как отдельное добавление с E30. Полосы `C1`, `C7−C1`, `C30−C7` — обратимое представление counts; distinct не вычитать. Тренд `C1/1−(C7−C1)/6` только при полном 7d; calendar snapshots и decay — отдельные варианты. |
| 3. Отношения | `V(u,c,7d)/V(u,7d)` с обоими counts; реализовать один раз совместно с темой 4. Остальные ratios не обязательны для начального ядра. | P1: один item action-ratio `P(i,7d)/V(i,7d)` с обоими counts. Сглаживание `p̂=(s+κμ)/(n+κ)` только для явно определённого grain и past-fit prior. Purchase/view не биномиальная вероятность и может быть >1. Rates по покрытию лога и since-first-observed — разные P1-гипотезы, не коррекция неизвестного exposure. |
| 4. Категории | `C((u,category_id),view,7d)`, view-share из темы 3 и view-recency по точному ID за наблюдаемую историю. Популярность кандидата внутри категории: `V_i/V_c` с item/category view-counts 7d. Все 372 неименованных ID участвуют. | Cart/purchase category counts, purchase-share, entropy `−Σp_c log p_c`, brand-inside-category и relative price `log(p_i/median_c)` — P1 по отдельности. Ценовой reference: одна последняя положительная цена на наблюдавшийся товар, as-of snapshot и support; для первой P1-проверки предлагается дневной snapshot и support≥20; 5 из 4B — отдельная sensitivity, а не эквивалентная реализация. |
| 5. Пользовательские слои | Дополнительный опыт после прямых user-category признаков: одна заранее заданная rule-сегментация и item×layer counters. `owner(e)=assignment_u(e.time−)` сохраняется с событием; сравнить raw counts с `p_il=(C_il+αq_i)/(C_l+α)` и lift `log(p_il/q_i)` при `q_i>0`. | Dominant-category и activity/past-purchase правила — конкурирующие варианты, не один общий набор. Learned layers — P1: fit cutoff τ, freeze, counters с τ, отдельное coverage; проверить self-excluded вариант. Current-membership cohorts допустимы при всех состояниях as-of t, но имеют другую семантику/стоимость. |
| 6. Узлы таксономии | Полный путь code и все его префиксы с namespace; на candidate ancestors — user view counts/share/recency за 7d, coverage известного кода и source support. Знаменатель — исходные события, не сумма memberships предков. | Иерархический affinity `Σq T(q)·2l(c,q)/(d(c)+d(q))/M`, sibling mass и root entropy — отдельные P1-кандидаты относительно ID baseline. При smoothing child|parent учитывать STOP. Сравнить ID-only, full-code-only, ancestors, оба ID+tree на одинаковых anchors. |
| 7. Текст | Category-only one-hot/полные префиксы/TF-IDF controls; один cosine `z_i·S/‖S‖` и support/coverage. Сравнить event-weighted и unique-product profiles отдельно; BM25 против простого IDF-overlap. Missing/OOV не равно известному нулевому сходству. |
| 8. Выбросы и качество | Raw counts без удаления активных пользователей, `price_zero/price_missing`, при необходимости состояние и возраст доступной цены; политика дублей отдельно для histories/anchors/targets. Измерить raw против exact-collapsed history на фиксированных anchors. | Доля past-only surplus дублей `(N−D)/N` с support, log1p и clipping — отдельные добавления. Для clusters — отдельная геометрия log/robust/TF-IDF; все внешние quantiles/scalers past-fit. Anomaly score — P2, не bot-label и не фильтр удаления. |

Начальное ядро тем 1–4 по независимому ревью содержит 18 числовых колонок плюс coverage/availability flags: 4 user, 5 pair, 3 item, 3 user-category и 3 item-within-category (ratio и два support-counts). Признаки тем 5–8 — независимые последующие добавления, а не условие первого baseline.

Поддержка и вычислительная цена являются частью сравнения. Counts/recency обновляются в одном временном проходе после сортировки; точные rolling distinct требуют reference counts, а median — отдельного состояния/агрегации. Разреженные ключи и материализация только согласованных anchors предпочтительнее плотных user×item/category grids. Все численные оценки памяти в записках — арифметика без runtime overhead; скорости, peak RAM, spill и размер выходов ещё не измерены.

Схема проверки: baseline → каждый блок отдельно → полезные блоки вместе → исключение блока из итогового набора. Общие anchors/candidates, labels, split, бюджет обучения и режим обновления histories; поддержка cold/short history, missing metadata и early-month отдельными срезами. Counts+ratio, HHI+entropy, ID+taxonomy и lexical+dense могут быть избыточны: полезность проверяется по дополнительному приросту, а не числу новых столбцов.

## Ревью, разногласия и следующие решения

Независимые проверки: [темы 1–4](review-01-04.md), [темы 5–8](review-05-08.md). Ревью проверяют определения и дизайн эксперимента; это не исполнение model tests и не подтверждение выигрыша. Исходные предложения A/B сохранены; уточнения добавлены отдельными review appendix там, где исходная формулировка может повлиять на реализацию.

Расхождения, которые намеренно не скрыты:

- Временной знаменатель: длительность покрытия файла, время после первого наблюдения и число активных дат измеряют разные вещи. Ни одно из них без roster/availability не доказывает пользовательское или товарное exposure. В сводке time-rates — P1, counts+coverage — старт.
- Ownership слоя: event-time owner проще инкрементально; current-membership cohorts также допустимы при всех состояниях as-of t, но перегруппировывают историю. Learned assignment, обученный в τ, нельзя выдавать за существовавший до τ; основной вариант начинает counters в τ и передаёт отдельное `layer_coverage_W=min(W,max(0,t−τ))`.
- Категории: ID и code не взаимозаменяемы; все узлы дерева не являются непересекающимся населением. `KNOWN_CODE` и сумма 13 root counts описывают известные исходные события один раз; сумма всех 159 node counts многократно учитывает один event. Полные числа 126/159/13 — диагностика октября, не ранний каталог.
- Лексический профиль может взвешивать события или уникальные товары; это отдельная ось опыта. Dense/lexical сравниваются при одинаковых metadata, grain, весах, support/missingness и кандидатах. Одновременное изменение профиля, канала brand или code→ID делает вывод о семантике неоднозначным.
- Backoff-depth в 6A проверяет поддержку родителя: при сохранении формулы правильное имя `deepest_parent_supported_edge_depth`; для node-supported depth нужна проверка самого узла. Исходная формула сохранена с review appendix.
- Relative price, smoothing, rule layers и hierarchy similarity имеют разные приоритеты в A/B. Они сохраняются как проверяемые варианты; общий MVP не является объединением всех P0 каждого исследователя.

До реализации/обучения остаётся выбрать:

1. Target, grain anchor и горизонт H; правило повторных anchors и атрибуции purchase, зрелость outcomes и правая граница данных.
2. Допустимые candidates и доступность category/brand/price/текущей session на anchor; отсутствие purchase не превращает событие в отрицательный показ.
3. Временные train/development/test границы, warmup τ и fit cutoffs всех внешних fitted states; как обновляются наблюдаемые histories при замороженных весах.
4. Общую политику exact duplicates отдельно для feature history, anchors и targets, с сохранённым raw и фиксированной задачей основного сравнения.
5. Ресурсный benchmark на одинаковых anchors: wall time, peak RAM, spill, размер feature outputs; затем бюджет серии абляций.

Ночной запуск, перенос на Windows/GPU, реализация признаков и расширение backlog — следующие фазы после обсуждения этих решений. В рамках этого исследования не создавались автоматизации и не запускалось обучение.

Полные записки сохранены независимо от того, вошла ли рекомендация в MVP. Ошибочные или расходящиеся предложения исправляются с заметкой о ревью; их не следует считать автоматически утверждённой спецификацией реализации.
