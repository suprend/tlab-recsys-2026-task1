# BM25 и TF-IDF для доступных метаданных REES46

Дата проверки: 2026-10-14. Исследование первичных документаций и read-only диагностика. Модели, vectorizers и retrieval-индексы не обучались, пакеты не устанавливались. Это варианты будущего эксперимента; цель предсказания ещё не выбрана.

## Рекомендация

Начать с признаков иерархии категории и истории бренда; затем сравнить TF-IDF affinity и BM25 affinity на одинаковых user–candidate примерах. BM25 стоит включить как дешёвый контроль, но делать его основой исследовательской гипотезы пока рано: собственных поисковых запросов, названий и описаний товаров нет.

В October наблюдаются 126 уникальных `category_code`. Read-only запрос к `data/processed/october.duckdb` и `split('.')` дают 150 различных компонентов; 41 код содержит 2 компонента, 84 — 3, один — 4; среднее по уникальным кодам 2.68254. Это диагностика полного месяца, а не доступная taxonomy на раннюю дату. Проверка воспроизводится: `SELECT DISTINCT category_code FROM events WHERE category_code IS NOT NULL`, затем подсчёт компонентов в Python. Дополнительная read-only проверка полного октября дала 5987 различных пар `(category_code, brand)`, включая пропуски. 166794 товара не означают 166794 разных содержательных текстов.

Источник схемы и ограничений: [авторская карточка датасета](https://www.kaggle.com/datasets/mkechinov/ecommerce-behavior-data-from-multi-category-store), локальный `docs/data.md` и полный October EDA. Поздние 205 предложенных названий отсутствующих категорий не считаем проверенными и не подмешиваем в основной эксперимент.

## Что является документом и запросом

**Практический вариант: документ = доступные метаданные товара-кандидата; запрос = профиль из строго прошлых взаимодействий пользователя.** Например, кандидат с `electronics.smartphone` и `samsung` представляется токенами категории и отдельным атомарным токеном бренда. Профиль содержит категории/бренды просмотренных ранее товаров. Это наша адаптация retrieval к рекомендательной задаче, а не восстановление реального search query.

Не конкатенировать сырую историю событий без правила весов. Отдельно считать profile-view, profile-cart, profile-purchase или сначала использовать только view; окно и затухание выбрать заранее/по validation. Для каждого токена можно взять долю прошлых уникальных user–item взаимодействий, сгладив частоту через `log1p`, и нормировать профиль. Повторяющиеся refresh одного товара иначе будут выглядеть как повышенный интерес.

Для первого опыта полезны два скалярных признака: category-affinity и brand-affinity. Раздельные поля позволяют CatBoost учесть их по-разному. Простую сумму независимых field scores не называть BM25F: это отдельная конструкция, а полноценный BM25F объединяет поля внутри модели term weighting. Первичная теория рассматривает документы, запросы, saturation, length normalization и BM25F: [Robertson & Zaragoza, 2009](https://www.staff.city.ac.uk/~sbrp622/papers/foundations_bm25_review.pdf).

Обратное направление `doc=user history, query=candidate` тоже возможно, но меняет смысл: saturation и length normalization тогда относятся к истории, а IDF по пользователям описывает распространённость интересов. Это другой эксперимент. Для контролируемого сравнения направление не менять между BM25, TF-IDF и dense features.

## Токены: минимальное правило для этого опыта

Сохранить category как структурированную taxonomy, не полагаться на whitespace split. Можно использовать префиксы: `cat:electronics`, `cat:electronics.smartphone`; бренд — `brand:samsung`, без искусственного разбиения неизвестных брендов. Это лишь стартовая спецификация; сравнение компонентов и префиксов относится к отдельной токенизационной абляции. Numeric IDs остаются categorical-признаками, а не словами с выдуманным значением.

В `TfidfVectorizer` callable `analyzer` возвращает готовые токены; он обходит стандартные preprocessing/tokenization/ngram stages, поэтому всё нужное задаётся внутри него. Default token pattern разделяет пунктуацию, требует минимум два символа и не сохраняет namespace/путь. `min_df=1`, без stopword removal и без удаления частого корня — разумный начальный контроль. L2-normalized vectors позволяют считать cosine скалярным произведением. См. [официальный API scikit-learn](https://scikit-learn.org/stable/modules/generated/sklearn.feature_extraction.text.TfidfVectorizer.html). Конкретную версию закрепить при реализации; сейчас зависимость не добавлялась.

Отсутствующая категория не должна превращать все неизвестные товары в семантически похожие через общий `unknown` токен. Missing category даёт пустой category vector; affinity=0 сопровождается `category_missing`. Бренд может работать отдельно. Отсутствие пересечения и отсутствие текста различать признаками. Для полностью пустого профиля добавить `profile_empty` и `history_size`; cosine определить как 0 без NaN.

## Какой корпус нужен для IDF

| Документ корпуса | Что означает DF | Ограничение |
|---|---|---|
| Уникальная строка категории | Сколько разных taxonomy paths содержит токен | Категории получают равный вес независимо от числа товаров; удобно для чистого сравнения category geometry с dense encoder |
| Один `product_id` с доступными метаданными | Сколько товаров ассортимента содержит токен | Повторённые метаданные обоснованно учитываются столько раз, сколько товаров их имеют; это влияние структуры ассортимента, не «новый текст» |
| Уникальная пара `(category_code, brand)` | Сколько разных сочетаний содержит токен | Иная мера редкости: частый бренд с широким набором категорий меняет DF; не эквивалентно per-product corpus |
| Строка события | Сколько событий содержит токен | Не рекомендуем: DF смешивает содержание и поведенческую популярность, многократные просмотры размножают один товар |

Для product-metadata affinity рекомендую явно зафиксировать **один document на уникальный доступный product_id**, сохранить category и brand в отдельных полях и честно назвать IDF ассортиментным весом. Для строго category-only сравнения с MiniLM/E5 — corpus уникальных доступных строк категорий. Если разные IDs имеют одинаковый code, при таком grain это одна строка. Смена grain — самостоятельная абляция, её нельзя скрыть под «поменяли модель».

BM25 использует corpus DF и длины документов. Положительный вариант Lucene IDF: `log(1 + (N - df + 0.5)/(df + 0.5))`; `k1` управляет saturation документной частоты, `b` — нормализацией длины. Документированные defaults Lucene — `k1=1.2, b=0.75`. [Официальный Lucene BM25Similarity](https://lucene.apache.org/core/10_3_1/core/org/apache/lucene/search/similarities/BM25Similarity.html).

## Почему BM25 здесь может почти совпасть с weighted overlap

Это математическое следствие предлагаемой токенизации, не измеренный ML-результат. Если в каждом product doc каждый токен присутствует один раз, `TF=1`. При `b=0` множитель `TF*(k1+1)/(TF+k1)` равен 1: остаётся weighted overlap по IDF и весам query. Подбирать большой grid `k1` в таком режиме бессмысленно. При `b>0` BM25 в основном штрафует более длинную taxonomy; глубина иерархии не обязательно означает лишнюю «многословность» товара. Поэтому сравнить `b=0` и `b=0.75` полезнее, чем обещать преимущества saturation на коротких labels.

Повторы query — отдельная проблема. `rank_bm25.BM25Okapi.get_scores` проходит по каждому query token и суммирует вклад, поэтому 100 повторений `samsung` умножают вклад примерно на 100; saturation документного TF это не исправляет. Пакет принимает token lists и сам не делает preprocessing. `get_batch_scores(query, doc_ids)` вычисляет только выбранные документы, но не решает нормирование query. Кроме того, его Okapi IDF с epsilon floor отличается от положительного Lucene IDF. Источники: [README владельца](https://github.com/dorianbrown/rank_bm25), [исходный код](https://raw.githubusercontent.com/dorianbrown/rank_bm25/master/rank_bm25.py). При реализации либо явно назвать именно этот вариант и версию, либо задать формулу weighted BM25 affinity отдельно; не считать разные реализации численно идентичными.

## Временная доступность

Полный October подходит для диагностики, но не для fit IDF ранних прогнозов. Даже fit на всех train-событиях смотрит в будущее относительно первых train-строк. Простой строгий вариант: выделить начальный warmup, построить catalog/vocabulary/IDF только из событий **до первого training prediction**, затем freeze для train/validation/test. Неизвестные поздние токены дают OOV и отдельный флаг. Альтернатива — snapshots корпуса по временным cutoff, причём любой прогноз получает только snapshot, уже существовавший к этому времени.

История пользователя содержит только события `event_time < prediction_time`. При одинаковом timestamp сначала прогноз, затем обновление истории всей timestamp-группой; произвольный порядок строк не использовать. Метаданные кандидата берутся из последней допустимой прошлой записи либо из текущей наблюдаемой карточки, если выбранная постановка делает её доступной. Будущие бренд/категория, новые товары и восстановленные позднее названия в ранний каталог не добавляются автоматически.

## Baseline и две абляции

1. **Baseline:** сильный CatBoost с user/item/user–item агрегатами, category ID, brand и явными parent/root/leaf историями. Считать category/brand counts, recency и missing flags. Это помогает понять, дают ли NLP scores информацию сверх уже доступной иерархии.
2. **Абляция A:** тот же baseline плюс TF-IDF cosine candidate ↔ weighted past-user-profile, отдельно для category и brand. Корпус, токены, временная политика и веса истории фиксированы.
3. **Абляция B:** тот же baseline плюс weighted BM25 affinity с теми же данными/полями/историей; заранее ограничить comparison `b∈{0,0.75}`, `k1=1.2`. При `b=0,TF=1` не трактовать эффект как победу saturation. Сравнить A и B отдельно; объединение лучших scores допустимо только после validation, с отдельной финальной оценкой.

Dense embeddings позже сравнивать на той же candidate/history единице и с теми же metadata/missing cases; обещать, что нейросеть лучше lexical на 126 labels, оснований нет. IDF не даёт синонимов, token overlap не выучивает комплементарность покупок, dense similarity сама по себе тоже не равна purchase probability.

Сначала сохранить одни и те же evaluation rows/candidates. Для view→purchase классификации оценивать выбранные logloss/AP и соответствующие slices; BM25 здесь только feature, retrieval не обязателен. Для next-purchase ranking отдельно оценить Recall@K кандидатов, затем NDCG/Recall финального ранжирования. Смена candidate generator без измерения покрытия смешает прирост recall с качеством ranker. Метрики, horizon и negative sampling окончательно фиксируются после выбора постановки; «не купил» не автоматически означает увидел и отверг.

Не вычислять полную матрицу 3 млн пользователей × 166 тыс. товаров. Для boosting features нужны только выбранные пары. Одинаковые metadata могут переиспользовать document weights, но DF корпуса сохраняет выбранный grain. Истории аггрегировать инкрементально или по cutoff, без расширения каждой обучающей строки на всю прошлую историю.

Независимое ревью: направление BM25, корпус/IDF, строгая временная доступность и единица сравнения проверены; модели и retrieval не запускались. Согласованные правила токенизации — в [nlp-tokenization.md](nlp-tokenization.md).
