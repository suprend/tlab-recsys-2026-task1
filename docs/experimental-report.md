# Ограниченная автоматизация программ признаков для ранжирования покупок

Экспериментальный отчёт по первой задаче T-Academy / T-Lab RecSys 2026. Редакция для независимого ревью, 15 октября 2026.

Мы реализовали воспроизводимые компоненты purchase-ranking pipeline и проверили ограниченный автоматический конструктор признаков против настроенного ручного CatBoost. На development выбран блок из трёх автоматически сформированных признаков: NDCG@20 вырос с 0,458611 до 0,464703. Разность 0,006092 имеет описательный интервал [−0,003207; 0,021294], включающий ноль. Это измеренный результат выбора на development, который пока не подтверждает улучшение на новом периоде. Отложенное сравнение тех же B/W-моделей ещё не выполнено. [Результат и предел доказательства](backlog-reviews/tlab016-feature-program-model-verification.md#L15)

## Исследовательский вопрос

Условие первой задачи требует pipeline градиентного бустинга с хорошими ручными признаками и экспериментальную проверку автоматизации работы с признаками либо метода, превосходящего настроенный boosting. Конкретные dataset, purchase target, архитектура и обязательный LLM API не предписаны; отдельно требуется предотвращать временные утечки. [Проверенное условие](task1-requirements.md#L5)

Наш вопрос: даёт ли небольшое автоматически порождённое дополнение к сильному ручному контролю прирост ранжирования при одинаковых запросах, кандидатах, истории, обучающей популяции и процедуре обучения? Проверяется практический механизм генерации, расчёта и ограниченного выбора программ признаков. Полностью автономное открытие произвольных признаков и превосходство универсальной стратегии поиска в эту постановку не входят.

## Данные и наблюдаемая задача

Использован REES46 Multi-category за октябрь 2019: около 42,45 млн событий, 3,02 млн пользователей и 166,8 тыс. товаров. Это многокатегорийный магазин. Доступны время UTC, view/cart/purchase, идентификаторы товара, пользователя и сессии, category_id, иногда category_code/brand и наблюдаемая цена. Названия, описания, изображения, показы рекомендаций и идентификаторы заказов отсутствуют. Размеры здесь округлены по опубликованной сводке. [Сводка данных](progress-report.md#L13), [происхождение и девять полей](data.md#L41)

Одна строка означает наблюдаемое действие. Непокупка среди кандидатов — условная отрицательная метка выбранного горизонта, а не отказ после показа или dislike. Эксперимент оценивает предсказание записанных покупок, не онлайн-конверсию и не причинный эффект рекомендации. Начало файла ограничивает доступную историю: первое событие не доказывает регистрацию пользователя. Последняя наблюдаемая цена не гарантирует актуальную цену или наличие товара.

Для запроса q=(u,t) история содержит только события с event_time<t; окно W имеет вид [t−W,t). Все события одной секунды t исключаются из признаков глобально, включая товарные агрегаты других пользователей. Категория кандидата разрешается по всей последней глобальной секунде до t: конфликт и NULL не заменяются более старым удобным значением. Историческая категория события сохраняется при последующих изменениях товара. Сырые повторы остаются в обычных counts; distinct-агрегаты имеют собственную единицу счёта. [Семантика признаков](experiments/manual-features.md#L21)

Время поступления данных отсутствует, поэтому replay предполагает доступность события по event_time. Это допущение не проверяет задержки загрузки. EDA и проверка целостности источника использовали весь месяц; исследование не заявляет, что весь будущий исходный файл оставался физически непрочитанным. Закрытыми для выбора моделей остаются query-level targets и метрики зарезервированных дат. [Раскрытие доступности](progress-report.md#L23)

## Запросы, кандидаты и временное разбиение

Каждый день в 00:00 UTC выбираются пользователи с любым событием за предыдущие 48 часов. Детерминированный bottom-SHA отбор с фиксированным seed ограничен 2000 пользователями в день и выполняется до чтения будущих покупок. Цель Yq — все различные товары, купленные пользователем в [t,t+24h); незрелый горизонт не оценивается как отрицательный. [Anchor protocol](experiments/anchor-pilot.md#L5)

Cq объединяет до 200 товаров с наибольшим числом различных покупателей за предыдущие 7 дней и до 20 последних различных товаров пользователя из view/cart/purchase за тот же период. Дубли удаляются без дополнения списка после пересечений. Будущие positives не вставляются; ранее купленные товары не запрещены. Кандидаты и каталог определены по прошлым действиям и не означают известный складской остаток. Все сравниваемые rankers получают один Cq. [Candidate protocol](experiments/candidate-pilot.md#L9)

## Метрики и ограничение retrieval

Основная метрика — conditional query-macro NDCG@20 по запросам с непустым полным Yq. Recall@20 — доля полного Yq в первых 20 позициях. IDCG вычисляется по min(20,|Yq|), а не по найденным в C positives. Отдельно сохраняются all-query-zero и query/user-macro варианты; пустой Y отличается от незрелого горизонта. При равных raw scores порядок задаёт точный product_id по возрастанию. [Метрическая процедура](experiments/boosting-baselines.md#L25), [независимая проверка full-Y estimands](backlog-reviews/tlab-006-verification.md#L19)

Selection содержит 73 положительных запроса среди 4000 — доля 0,01825. Генератор находит 65 из 96 target-пар: micro coverage 0,677083; верхняя граница conditional query Recall из-за fixed C — 0,684932. Поэтому даже идеальная перестановка C не вернёт отсутствующие targets. Это Recall ceiling, его нельзя выдавать за численную верхнюю границу NDCG. Приведённые ниже query-macro Recall также нельзя напрямую сравнивать с 65/96 как с тем же estimand. [Принятая coverage-сводка](experiments/heuristic-baselines.md#L52), [точные агрегаты](backlog-reviews/tlab007-selection-aggregate.json)

Дополняющие coverage, возраст наблюдаемой истории, missing flags, retrieval-контекст и возраст последнего события пользователя образуют фактический модельный вход из 41 числового поля. ## Что именно автоматизировано

Конструктор принимает объявленные человеком роли/типы полей, action capabilities, окна 24/168 часов, привязки и три семейства шаблонов: ActionVector, Breadth, CartTiming. Он связывает роли, порождает определения, проверяет типы и временную семантику, удаляет известные aliases полного B/retrieval и рассчитывает физические зависимости, включая missing flags. Получается восемь допустимых whole bundles; готовые списки всех feature-JSON не зашиты вместо генерации. Произвольный SQL, неизвестные operators и inference смысла новой схемы не поддерживаются. [Программы и границы генератора](experiments/feature-programs.md#L7)

До 016 метрик закреплены I1=L02 и I2=L06, а две random-ветви выбраны с replacement через Random(2026): R1=L01, R2=L05. Совпадение потребило бы попытку без redraw; фактически блоки различны. Каждый добавляет ровно 3 физических входа, включая необходимые маски. Общий экспорт 12 новых полей обслуживает четыре альтернативные B+3-модели; модель B+12 не обучалась. Это распределение ограниченных возможностей, а не выбор лучших 12 после оценки всего пространства. [Allocation и closure](experiments/feature-programs.md#L11)

Все четыре ветви наследуют один B: те же 26000 train-Q, fixed C/full Y, query-balanced веса, 41 основной вход, параметры, 300 trained / 300 scored. Дополнительного tuning нет. Правило выбора включает B и все четыре ветви: Recall ≥ Recall(B) − 0,002, затем максимальный conditional NDCG; в полосе 1e−12 предпочитаются меньше добавленных полей и фиксированный порядок ID. B выигрывает равенство и может остаться W. [Prospective selector](experiments/feature-program-selection.md#L5)

## Как воспроизвести доступные части

В репозитории сохранены код, versioned конфигурации, locked dependencies, тесты и агрегированные доказательства. Реальные события, Q/C/Y, модели, private score packages и локальные approvals не входят в clone. Следующие команды взяты из опубликованной инструкции; при подготовке этого draft они не запускались. [Reproduction scope](experiments/fresh-clone-reproduction.md#L3)

```sh
uv sync --locked
PYTHONDONTWRITEBYTECODE=1 uv run --locked python -m unittest tests.test_replay_ranking_claim
uv run --locked python -m scripts.replay_ranking_claim --package tests/fixtures/reproduction/manual18-small
```

Публичный пример содержит 12 синтетических строк и проверяет арифметику full-Y ranking, ties, empty C и zero Y. Он не загружает модель, не считает реальные source-признаки и не выполняет native fit. Символическую генерацию bundles можно отдельно проверить через опубликованный `generate_pool → allocate_slots → registry_for_slot` пример без SQL и приватных данных. [Source-free replay](experiments/fresh-clone-reproduction.md#L13), [пример конструктора](experiments/automation-walkthrough.md#L3)

Для восстановления EDA при отдельно полученном исходном архиве существует команда:

```sh
uv run python scripts/eda.py --input data/raw/2019-Oct.csv.gz --output artifacts/eda-october --db data/processed/october.duckdb
```

Она воспроизводит EDA, а не всю принятую модельную цепочку. Replay приватного исторического пакета требует отдельно выданных access/budget contracts и independently issued digests; создание новых hashes не заменяет source/model review. Полный source-to-model rerun из чистого clone с новыми независимыми подтверждениями пока не продемонстрирован. [EDA entry](../README.md#L23), [private replay contract](experiments/fresh-clone-reproduction.md#L71)

## Интерпретация

Эксперимент уже показывает, что узкий конструктор способен породить допустимые программы, корректно рассчитать их значения и провести конечное сравнение с настроенным ручным контролем. Лучший development-вариант даёт небольшой положительный point estimate при широком интервале, пересекающем ноль. Заявление об улучшении обобщения остаётся открытым до reserved B/W-оценки.

Автоматизированы binding, ограниченная генерация, validation/dedup/closure, расчёт и выбор из конечного семейства. Человек определил схему, primitives, шаблоны, окна и guided priorities; learned proposer, произвольная рекурсивная feature discovery и независимое доказательство преимущества стратегии отсутствуют. Также не измерены онлайн-эффект, полное время ручной подготовки или качество на другом реальном dataset. Получившийся отрицательный либо неопределённый heldout-результат должен быть сохранён вместе с положительным development-выбором, а не заменён новым поиском по final.
