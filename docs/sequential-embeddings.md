# История пользователя и товар в совместном пространстве: практический shortlist

Дата проверки источников: 14 октября 2026. Это исследовательское предложение: модели не обучены, целевая переменная и горизонт ещё не выбраны.

## Вывод

Да, можем вычислять `u = f(history_before_t)` и `v = g(item_features_before_t)`, оба размерности 64 или 128, затем использовать `u · v` как признак совместимости. История пользователя здесь заменяет отдельную таблицу user_id. Для нового пользователя с первыми действиями такой encoder применим сразу; для пользователя совсем без истории нужен fallback.

**Одинаковая размерность не означает общее пространство.** Совместимость задаёт обучение пары encoder-ов общим recommendation loss, либо использование одного осмысленного item space для усреднения и кандидата. Два независимо полученных случайных вектора по 128 координат сравнивать бессмысленно.

Изображения и описания товаров не обязательны. Обучаемые векторы `product_id` получают информацию из взаимодействий; category_id, brand и price могут дополнять их. На наших коротких текстовых кодах категории текстовый encoder будет представлять категорию, а не индивидуальный товар. Товары с одинаковыми полями получат одинаковый content vector; различать их помогает поведенческий item embedding. Это вывод из доступных полей, не гарантия прироста качества.

## Модели

| Подход | Представление пользователя | Представление товара | Начальная настройка и смысл |
|---|---|---|---|
| Weighted mean + небольшой MLP | Среднее векторов предыдущих товаров с весами события и давности, затем обучаемая проекция | ID embedding, при желании MLP над ID/category/brand/price | d=64, история до 50 событий; дешёвый проверяемый старт, порядок учитывает только через давность |
| SASRec-small | Causal self-attention по предыдущим действиям | Обучаемая таблица item embeddings; для cold item нужна отдельная content ветка | d=64/128, 1–2 блока, 1–2 головы, L=50, затем при необходимости 100; учитывает порядок |
| GRU4Rec | Рекуррентное состояние GRU после последовательности действий | Выходные item weights/embeddings; выбирать именно выходное пространство | Один слой 64/128; альтернативный способ проверить пользу порядка и короткого контекста |
| ALS/BPR | Factor пользователя, оценённый из истории взаимодействий | Item factor | d=64; простой поведенческий ориентир без порядка, не замена history encoder один-в-один |

В промышленной работе YouTube candidate-generation network учит user/context embedding по истории, оценивает товары скалярным произведением и использует sampled softmax; это прямой первичный пример совместного пространства и отдельного последующего ranking. Наш weighted-mean вариант — компактная адаптация идеи, а не воспроизведение системы YouTube. [Google Research, Covington et al., 2016](https://research.google.com/pubs/pub45530.html).

SASRec использует item embedding, позиционный embedding и causal self-attention; последняя позиция истории сравнивается с embedding товара. Оригинальный loss — бинарный logistic loss с положительным следующим item и sampled negative, а не обязательный full softmax. Официальный код действительно использует общую input/output item table, `causality=True` и dot product. Событие и реальное прошедшее время в исходной архитектуре явно не подаются: это наше расширение. [Статья авторов](https://arxiv.org/abs/1808.09781), [исходный model.py](https://github.com/kang205/SASRec/blob/master/model.py).

Оригинальный GRU4Rec ориентирован на независимые сессии: состояние сбрасывается между ними. Применение GRU ко всей истории пользователя требует явно изменить протокол построения последовательностей/сброса состояния; нельзя назвать исходный session protocol полноценной долгосрочной историей. Официальная современная реализация поддерживает cross-entropy и BPR-max, shared/separate embeddings. Для scoring берём выходную item representation, не произвольно выбранную входную таблицу. [GRU4Rec, статья](https://arxiv.org/abs/1511.06939), [официальная PyTorch реализация](https://github.com/hidasib/GRU4Rec_PyTorch_Official).

BPR оптимизирует pairwise порядок observed item относительно sampled unobserved item. ALS/BPR доступны в `implicit`; библиотека имеет MIT-лицензию. BPR/ALS дают совместные факторы, но не моделируют порядок действий так, как sequence encoder. [Статья BPR](https://arxiv.org/abs/1205.2618), [implicit](https://github.com/benfred/implicit).

## Входы, обучение и холодный старт

Наша предлагаемая item ветка: `g(item) = MLP(concat(ID_embedding, category_embedding, brand_embedding, normalized_price)) → R^d`. Metadata должны быть доступны до времени предсказания: цена меняется, использовать итоговую цену за весь месяц нельзя. Для невиданного ID — отдельный OOV embedding и известные metadata; обучать с item-ID dropout, если действительно хотим опираться на content в cold start. Если category/brand тоже неизвестны, модель не получит индивидуальных сведений о новом товаре.

В history token можно подать `item_vector + event_type_embedding + position_embedding + time_gap_embedding` (или concat с проекцией). Типы `view/cart/purchase` не синонимы. В weighted mean начать с отдельных средних по типам и последующей проекции: это понятнее произвольных фиксированных весов. Веса и decay либо фиксируются на validation, либо обучаются; покупки не надо считать универсально самым сильным сигналом для любой ещё не выбранной цели.

Для совместного обучения подходят contrastive sampled cross-entropy, бинарный logistic loss или BPR-подобный pairwise loss. Выбор должен соответствовать выбранной задаче: next-item pretraining не автоматически оптимизирует purchase probability. Сначала 64–256 sampled negatives на позицию как наш бюджетный старт, затем сравнить увеличение; in-batch negatives — альтернатива, не гарантированно лучший вариант. Повторяющиеся positive item в batch надо маскировать, чтобы не обучать идентичный товар как negative. `Unobserved` означает неизвестную предпочтительность, а не доказанный показ без клика: impression log у нас нет. Не использовать будущие покупки для очистки negatives задним числом.

При истории длины 0 — learned empty-history vector или популярность/category/context fallback, обязательно флаг `history_empty`. Для 1–4 действий pooling может быть достаточен; сложный transformer не имеет гарантированного преимущества. Отдельно измерять группы по длине доступной истории и cold/warm item.

Все события с timestamp `t` должны иметь контекст строго `< t`. Внутри одной секунды порядок действий не известен: безопасно агрегировать timestamp bucket для контекста/исключать неоднозначные next-step пары, не выдумывать порядок через сортировку event_type. `user_session` не глобально уникален: session key — `(user_id, user_session)`. Одинаковые item подряд и повторные покупки не следует удалять автоматически; это часть поведения, политику обработки проверить отдельной абляцией.

## Реалистичный бюджет памяти

Это арифметика для 166 794 товаров и FP32, **не замер VRAM и не прогноз времени обучения**:

| Объект | Память |
|---|---:|
| Item table d=64 | 40.72 MiB |
| Item table d=128 | 81.44 MiB |
| d=128: веса + градиенты + два Adam moment tensors | 325.77 MiB только для этой таблицы |
| Full logits batch256 × все товары | 162.88 MiB |
| Full logits batch1024 × все товары | 651.54 MiB |
| Full logits batch256 × 50 позиций × все товары | 7.95 GiB только logits |
| Векторы всех 3 022 290 пользователей d=128 | 1.441 GiB |
| Все user-item scores | 1.834 TiB |

Поэтому RTX3070 предположительно 8 GB — разумная кандидатура для маленького encoder с sampled loss и batch64–256, но фактическую память нужно измерить первым коротким прогоном. Не создавать full-catalog logits на каждой позиции последовательности. Shared negative set, ограничение числа обучаемых позиций, batching и смешанная точность дают контролируемый бюджет. Хранение всех histories на GPU тоже не нужно: ragged arrays на CPU и minibatches. Mac можно использовать для подготовки и pooling; CPU ALS через implicit на Apple Silicon требует отдельной проверки установки arm64/source build. README подтверждает готовые CPU wheels для x86_64, в том числе нашего Windows-ПК. Работоспособность конкретных GPU kernels на MPS не подтверждена.

## Как связать с T-Lab и CatBoost

Практическая последовательность: (1) сильный baseline CatBoost; (2) pooling в learned item space или ALS/BPR score; (3) jointly trained pooling two-tower; (4) SASRec-small как проверка полезности порядка. GRU — дополнительный encoder для сравнения при наличии времени, а не обязательный второй большой проект. Начинать с контроля времени и memory на небольшой **хронологически корректной** выборке; не подбирать все архитектуры сразу.

В бустинг можно подать dot score, cosine отдельно от норм векторов, нормы, сходство с последним товаром и средними истории view/cart/purchase, а также флаги пустой истории/OOV. Dot и cosine не взаимозаменяемы: нормализация меняет смысл обученного score. При retrieval сохранить dot product space, если именно его оптимизировали; cosine считать дополнительным признаком или явно обучать нормализованную модель.

**Веса encoder тоже должны быть из прошлого**, недостаточно обрезать только history. Для обучающих строк CatBoost нужны более ранний frozen encoder либо expanding-window snapshots: каждый embedding-признак генерируется checkpoint-ом, обученным до соответствующего временного блока. Иначе будущие покупки проникнут в learned item table. Validation/test получают предыдущий checkpoint и только доступную историю. Для сравнения фиксировать candidate set/target/split и показывать `baseline → + learned scores`; retrieval-качество можно оценивать отдельно, если retrieval вообще входит в выбранную постановку.

## Код и лицензии

- SASRec: авторский TensorFlow код — Apache-2.0, но legacy TensorFlow1/Python2. [Авторский репозиторий](https://github.com/kang205/SASRec). Указанный самим авторским README PyTorch-порт `pmixer/SASRec.pytorch` тоже Apache-2.0; это порт другого автора, не оригинальный код исследователей. Ветка обновлялась, поэтому перед экспериментами закрепить commit и проверить training/evaluation protocol, не переносить готовую случайную leave-one-out оценку. [Репозиторий порта](https://github.com/pmixer/SASRec.pytorch).
- GRU4Rec: официальный PyTorch repository автора допускает free research/education, commercial use требует отдельной лицензии; это **не MIT/Apache**. Для курсовой подходит по заявленным условиям. [License note в README](https://github.com/hidasib/GRU4Rec_PyTorch_Official#readme).
- `implicit`: MIT; README перечисляет CPU wheels для x86_64 Windows/macOS/Linux, стандартные wheels с GPU support — для Linux; это не обещание готовой arm64-установки на Mac M3. Поэтому не обещать GPU ALS на обычной Windows установке; CPU baseline доступнее. [Документация владельца кода](https://github.com/benfred/implicit).

Независимое ревью: первичные источники, лицензии и арифметика памяти проверены; уточнена архитектура доступных wheels implicit. Общий временной протокол — [embedding-experiments.md](embedding-experiments.md).
