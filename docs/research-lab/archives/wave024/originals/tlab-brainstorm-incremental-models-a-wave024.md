**Primary fact.** DBSP models insertions/deletions as signed changes. Its incremental DISTINCT emits a change only when accumulated multiplicity crosses between positive and nonpositive; the previous weighted relation is retained. The paper explicitly assumes small deltas, assigns DISTINCT state proportional to the maintained relation, and warns that changing incremental plans generally requires rebuilding state. Its logical transaction clock is distinct from the physical clock supplied to windowing. None of this establishes constant memory or our speedup. [Budiu et al.,PVLDB2023,Proposition4.7,§§4.4/7.5](https://www.vldb.org/pvldb/vol16/p1601-budiu.pdf)

**Mechanism.** For the existing R2/L05 additions only—item distinct users for view24h/cart168h/purchase24h—advance one projected chronological input across fixed anchors. Retain timestamped occurrence multiplicities plus `(action,item,user)` live refcounts for each applicable window and item distinct totals. Insertions/expirations alter totals only at0↔positive transitions. This shares decoding and state across anchors; it is not another feature/learner/search arm. Keep B41 calculation unchanged and charge it in both complete plans. Prebind the same label-blind requested-item domains; no treatment may filter global peers to the sampled query users.

Answer every query at t after incorporating all partitions' events with s<t and expiring only s<t−h. Events exactly at t−h remain; timestamp-t peers remain excluded. NULL projected users contribute no DISTINCT membership, while B's raw duplicate counts remain untouched. Preserve source-start coverage, output keys, missing/support fields and final projection/order. Event-time availability remains the existing assumption, not a new received-at guarantee. Current three item-only additions need no category join; do not silently recategorize historical rows while maintaining other B states.
