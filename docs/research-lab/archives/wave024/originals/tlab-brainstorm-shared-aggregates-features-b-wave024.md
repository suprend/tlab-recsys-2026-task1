# Wave024 FIRST — exact pane reuse, conditional on compression

15 October 2026. Independent blind draft; no peer024 read. **Zero new mechanisms/IDs:** refine HYP046, rounds012/033/044/073. This is one optional physical-plan proposal, not another feature family or current015/018 prerequisite.

**Mechanism.** For the fixed supported count/DISTINCT leaves, partition time at every declared anchor and window boundary, including source start. Within each half-open pane, materialize integer multiplicity by `(action,user,item)`, retaining NULL-key bins. Derive pair/user/item raw counts by exact sums; derive distinct membership only after summing multiplicities across relevant panes and coarsening to the requested projected key. Never sum pane-distinct scalars. Expiring one copy removes membership only when the remaining count becomes zero. All boundaries preserve `[max(S,t−W),t)` and complete same-timestamp buckets; fixed Q/C, raw duplicates and off-C/global contributors remain. This is a lossless sufficient representation **for these leaves**, not a replacement for raw history, metadata or recency: full-prefix recency, latest metadata resolution, denominators and other leaves retain their existing calculation. Unknown projected identities remain excluded from DISTINCT, without dropping their raw-row contribution elsewhere.

**Primary mechanism versus adaptation.** The [F-IVM author project](https://fdbresearch.github.io/ivm.html) describes trees of maintained intermediate views, factorized computation and ring payloads; it does not establish this pane design or REES46 speed. [DuckDB1.5 aggregate documentation](https://duckdb.org/docs/current/sql/functions/aggregates) distinguishes row count, non-NULL count, DISTINCT and empty-group NULL. Our integer membership bookkeeping is an adaptation, not an upstream rolling-DISTINCT guarantee. Empty rollups must restore the existing count-zero, support and missing policies after domain joins; `sum` alone is insufficient.

**Prediction.** With repeated `(action,user,item)` inside panes and several consumers, one paid compressed table may reduce repeated aggregation work. Counterprediction: mostly unique keys, fine boundaries or existing005 scan fusion make preprocessing/state overhead dominate. Current005 already batches by grain/anchor; fewer logical nodes or scans do not prove lower total cost.

**Nearest finite experiment — UNRUN, ungranted.** Predeclare two bags, each ≤16 invented events, three anchors and six C rows: burst-heavy versus unique-key-heavy, with repeated users across panes, duplicate copies expiring separately, NULL projections, lower/upper-bound peers, an off-C contribution and future suffix. Freeze one existing supported workload and its complete physical output closure. An independent direct-list specification checks every keyed value/mask/support; the strong cost control is unchanged batched005 with optimizer enabled, not separate scans per feature. Compare the shared plan with that control in AB/BA order, same source/domain/sink and declared cache policy. One prospective allocation: ≤30 CPU seconds, ≤60 wall seconds, ≤512 MiB, two threads, zero fits/labels; no execution is authorized here.

**Task1 benefit, costs and falsifier.** Potentially cheaper calculation of the same generated pool, with unchanged information/learner/Q/C. Charge boundary planning, source reading, grouping, serialization, all membership/support state, complete export/readback, validation, warmup, failures and cleanup. State can approach raw-event cardinality; no asymptotic memory saving is promised. Any semantic mismatch rejects the plan; no lower total process CPU than005 leaves savings unconfirmed. A finite pass establishes only the tested calculation contract, never ranking benefit or general scalability. Original015 startup failure remains a failure; this proposal grants no retry.
