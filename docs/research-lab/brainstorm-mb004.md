# MB transfer round004 — Amazon Reviews 2023 is a capability test, not a 24h-purchase replication

**Independent first freeze, 2026-10-15.** Main external dataset: **Amazon Reviews 2023**, distributed by the McAuley Lab at UC San Diego. RelBench rel-amazon is a task-design contrast, not a second proposed dataset. This note is blind to retrieval A's session-dataset draft and other round004 drafts. Only primary documentation/author sources and existing project contracts were read. No corpus files, actual Q/C/Y, SQL, model imports, fits, paid APIs, weights or shared repository edits were used. No new HYP or execution budget is issued.

**Result:** the count/distinct/recency algebra can transfer to a declared *review-event* bag. Our unchanged view/cart/purchase programs, B41 base and whole-program 24h purchase-fullY experiment cannot transfer. The blocker is missing business semantics and clocks, not insufficient timestamp precision.

## Provider, size, license and release identity

The [official site](https://amazon-reviews-2023.github.io/main.html) links the McAuley-Lab HuggingFace release and Yupeng Hou's author repository. It describes a 2023 academic collection, not Amazon transaction telemetry. The [author paper v2, revised 20 April 2026](https://arxiv.org/html/2403.03952v2#S3), reports **571,544,897 reviews; 54,514,264 users; 48,185,153 reviewed items; 35,393,189 metadata records**. These are provider-stated statistics, checked on 15 October 2026, not independently counted. Site totals round them to571.54M/54.51M/48.19M. There are33 domains plus an Unknown dump; the [release README](https://huggingface.co/datasets/McAuley-Lab/Amazon-Reviews-2023/blob/main/README.md) says34 category-file names. Do not replace these figures with HuggingFace's generic size tag.

The advertised cutoff is September2023. Site/README give May1996 as the start, whereas current paper Table1 gives June1996. Record the discrepancy rather than inventing an exact coverage interval. In [Appendix B](https://arxiv.org/html/2403.03952v2#A2), authors sample public user identifiers then collect user review pages. They explicitly warn that item review coverage is incomplete for unsampled users and recent reviews can be missing even *before* cutoff. The paper's individual-history completeness motivation does not certify our complete24h purchase observation.

**Data license is unresolved, not MIT.** The [author repository LICENSE](https://github.com/hyp1231/AmazonReviews2023/blob/main/LICENSE) grants MIT terms for software/documentation. The [maintainer's 8 March 2024 dataset-license reply](https://huggingface.co/datasets/McAuley-Lab/Amazon-Reviews-2023/discussions/1) says they cannot assign a dataset license and distribute it primarily for research; a later thesis-specific reply is not a general permissive data grant. The current official dataset card supplies no data-license declaration. Likewise the paper's CC-BY publication license cannot be substituted for corpus rights. This is an unresolved ingestion/redistribution fact, not a restriction on this documentation-only analysis.

## What the schema supports

The [published field definitions](https://amazon-reviews-2023.github.io/main.html#data-fields) define timestamp as **review time**, verified_purchase as purchase verification, rating as1–5, and user_id/asin/parent_asin as identifiers. Parent ASIN joins metadata and groups variants. The paper states millisecond precision; precision does not change what event occurred. No purchase/order time, orderID, complete transaction log, impressions, views/carts, sessions, query schedule or observed no-purchase outcome is documented.

Metadata includes category hierarchy, details/brand, store, price and product rating aggregates. Price is explicitly at crawling time; no per-field availability history is exposed. Some reviewed items lack metadata. These facts permit the following **own adapter classification**, not claims about actual row quality:

| Requested capability | Portable part | Required refusal or narrower meaning |
|---|---|---|
| Count, projected distinct, observed-prefix recency | Same user/item/pair group algebra; lower-inclusive, upper-exclusive windows; exclude global timestamp peers | Apply only to explicitly declared review rows. Review is not view, cart or purchase. |
| Nominal identity and joins | Exact string keys, one declared item grain, collision-free transport | Parent-ASIN aggregation is a grain choice, not an innocuous rename of variant ASIN. No arithmetic on IDs. |
|24/168h windows | Same duration arithmetic after explicit Unix-ms→UTC normalization | Sparse windows are allowed; absent channels are unsupported, not known empty zero. |
| Category-conditioned historical features | Same NULL/conditional-key algebra in principle | Snapshot category cannot backfill historical review categories without availability evidence. All category-dependent requests must refuse or use an explicitly different nonhistorical policy. |
| Price, average_rating, rating_number, helpful votes, bought_together | Schema fields exist | Crawl/post-event aggregates are not historical state. A bundle recommendation is not an order edge. No inferred available_at. |
| Session and exposure operators | None documented | Do not synthesize session IDs as original sessions or treat absent impressions as nonexposure. |
| Purchase24h fullY and no-purchase queries | None identifiable | verified_purchase is insufficient; absence of a review is not absence of purchase. |

“Positive-only” here means observed-interaction support, not that all star ratings are positive sentiment. A one-star review remains an interaction. verified_purchase=false is not a purchase-negative label; five-star filtering would define a different target.

The [author preprocessing README](https://github.com/hyp1231/AmazonReviews2023/blob/main/benchmark_scripts/README.md) says ratings-only files retain the earliest review per(user,item), then optionally apply iterative5-core filtering. Thus even0-core is a deduplicated bag, not the raw review multiplicity. Whole-corpus5-core membership can depend on future reviews. The [official split documentation](https://amazon-reviews-2023.github.io/data_processing/0core.html) offers leave-last-two and absolute timestamp splits; earlier review history is not earlier purchase history. These are not our natural daily query anchors or complete24h negatives. A global chronological split is necessary for an event-time study, but cannot recover unobserved purchases.

## Two concrete adapter falsifiers

**F1 — indistinguishable released rows, contradictory purchase-fullY.** Fix a synthetic external query atT and C={I,J}. The only released record is a verified review ofI atT+10days. WorldA purchasesI atT+1hour andJ atT+2hours without reviewingJ; WorldB purchasedI atT−7days and never purchasedJ. Both worlds produce the same documented release fields. True purchase24h fullY is{I,J} inA and empty inB. No deterministic adapter from these fields can be correct in both worlds. A chronological split, a verified-only filter, extra sampled negatives or finer time resolution does not fix this identifiability failure.

Expected result: requesting purchase24h/fullY must fail *before* feature/model/selector evaluation. It must not return a fabricated emptyY or treat missing reviews as negatives. Conditional NDCG may be undefined inB; it must not be replaced by0. Counting released reviews in the next24h creates a separately named observed-review target, with a different population/denominator and acknowledged missing-review coverage. A score on that task cannot confirm purchase ranking.

**F2 — future snapshot and future vocabulary must not alter an old decision.** AtT−1hour the synthetic history contains u reviewing itemA with unknown category. One future release snapshot assigns categoryK, price10 and a product rating aggregate toA; it also adds itemB first reviewed atT+1day. Those snapshots have no availability-at-T evidence. A whole-file metadata join that makes the old category-conditioned count1 instead of unknown, or expands old C withB, fails portability even if all event rows are filtered belowT.

Expected result: noncategory review count1/distinct1/recency3600s stay identical under the future-suffix mutation; historical category remains unknown/refused; past-only U(T)/C excludeB. The original B41 itself requires unsupported action/category semantics, so the existing whole-program runner must STOP on protocol incompatibility rather than silently chooseB. A new review-only B′ and legal pool would need a separate source-local contract. Alternative permitted metadata policies must be declared upfront, not chosen after the winning score.

Both falsifiers are literal specifications/identifiability arguments, not executed adapter tests or evidence of bugs on real rows. Passing them would only establish a narrow source adapter contract.

## Whole-program selection: reusable decision algebra, new experimental identity

Current [automation-pool.json](../../configs/features/automation-pool.json) declares view/cart/purchase, strict-past raw-event rows, an event-time availability assumption, fixed category roles and a purchase-distinct retrieval alias. [manual-18.json](../../configs/features/manual-18.json) embeds those actions/category semantics in B41. A reviewer cannot approve Amazon by filling unavailable channels with zeros or merely matching41 physical columns.

The [selection rule](../../docs/experiments/feature-program-selection.md) could be reused abstractly: complete bundles, B included, fixed equal arms, Recall feasibility, global NDCG maximum/tolerance, fewer-column then ID ties, paid collisions/resource failures and no refill. Its actual baseline metrics, fullY definition, source acceptance, query population, C, registry, retrieval alias, model checkpoint, slots and target-opening reservation cannot transfer. If the source/task fails before fitting, it is an invalid experiment, not evidence that four completed candidates lost toB.

As a contrast, the [official RelBench rel-amazon card](https://huggingface.co/datasets/stanford-star/relbench-v1/blob/main/rel-amazon/README.md) explicitly starts from timestamped reviews and defines user-item tasks over **two years**, including purchase-labelled, five-star and detailed-review variants. A task name is not independent evidence of purchase timestamps; its review-based schema and declared horizon require their own exact versioned task definition. The review-rating autocomplete task also differs from prospective event ranking. No RelBench data or label table was opened here, and no claim depends on mixing version-dependent row counts or task totals.

**Finite next gate, no execution grant:** one versioned capability manifest; two tiny fixtures above; exact key/clock/bag normalization; independent expected outputs; reject unsupported programs before allocation. This is zero fits/zero corpus downloads. Source reading of the implementation follows this first freeze as at most one append-only addendum. Any later review-event benchmark needs separately accepted rights/provenance, source coverage, calendar/Q/C/Y, resource limits and fresh development reservation. Current W=R2+3 and all current heldouts stay CLOSED. The present evidence supports a refusal-aware portability boundary, not cross-dataset predictive transfer.

## Single post-freeze addendum — source-code portability review, 2026-10-15

The frozen body above is unchanged. This is the one permitted addition. Read-only working-tree source review used HEAD `9f78b352cccfcf8a82c8f6dbed1e2ed9cd518cbe`; the three inspected local implementation files had no working-tree changes. No modules, tests, SQL or native jobs were executed. The generator gate was independently corroborated by the delegated reviewer.

1. **Honest capability declarations fail early.** [feature_programs.py:70](../../scripts/feature_programs.py#L70) demands exact fields/types/context and the ordered view/cart/purchase list. Review-only actions fail at82–83; the code explicitly rejects invented zeros. Its event-time assumption, global-peer policy, frozen windows/templates and purchase-retrieval alias are also exact requirements. Amazon string keys/integer timestamps need a typed transport adapter, but casting cannot manufacture the required business events. This maps directly toF1; it is an intended scope restriction.

2. **Declarations cannot authenticate themselves.** [generate_pool:98](../../scripts/feature_programs.py#L98) receives a declared contract and registry, not an event collection. Its output [at154](../../scripts/feature_programs.py#L154) requires external source/protocol/Q/C/Y lineage and sets execution_approved=false. Copying the expected declaration could pass symbolic validation while falsely relabelling reviews. That observation is not a generator bug: the documented external source gate owns truth of action/clock/coverage. A declaration digest preserves identity, not purchase observability.

3. **The chooser is not a source verifier.** [choose:38](../../scripts/feature_program_experiment.py#L38) expressly delegates source/model/score authority. It accepts five original identities, finite conditional metrics and recognized statuses, then applies the global band. Unsupported/incomplete states cannot become resource_failed merely to retainB. [prepare_plan:226](../../scripts/feature_program_experiment.py#L226) authenticates accepted source/control, exact B41, original slots L02/L06/L01/L05 and F57. [append_program_features:50](../../scripts/program_model_data.py#L50) preserves inherited Q/C/Y and appends a checked three-column delta. It does not infer source formulas or recover missing targets. Thus F1/F2 belong before this accepted input boundary; equal arrays/metrics cannot repair an invalid purchase protocol.

4. **Author adapters are version-specific too.** The Amazon author [ratings loader](https://github.com/hyp1231/AmazonReviews2023/blob/main/benchmark_scripts/kcore_filtering.py) directly indexes `sortTimestamp`, whereas the published field table names `timestamp`. A literal documented-schema record containing only timestamp would raise KeyError on that path; only ValueError is caught. This static observation does not establish which key actual corpus versions contain. A future adapter must pin the exact schema/clock mapping and refuse an unrecognized variant, rather than guessing units or treating similarly named clocks as purchase time.

5. **RelBench is not a drop-in provenance bridge.** The pinned [v1.1.0 Amazon builder](https://raw.githubusercontent.com/stanford-star/relbench/v1.1.0/relbench/datasets/amazon.py) defaults to books/5-core from `amazon_v2`, converts `unixReviewTime` using seconds, drops products with missing parsed price, and restricts reviews to the surviving product intersection. Product/customer tables have time_col=None; only review_time is temporal. These are distinct corpus, population and metadata policies, not Amazon Reviews2023 milliseconds or historical item-state evidence. Its behavior reinforcesF2: filtering by a later product snapshot can alter Q/C/Y support before ranking. No RelBench loader, download or label computation was invoked; unavailable task-source URLs were not treated as verified implementations.

**Final boundary:** identical aggregation operators and decision algebra are reusable components. Honest review-only sources are currently refused, and a new source-local review protocol would require deliberately different accepted inputs. There is no demonstrated end-to-end portability, predictive gain, complete purchase-fullY or new execution authority.
