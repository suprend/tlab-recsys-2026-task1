Sum quantity/money/cancellation-as-of — будущие operators, отсутствующие в compiler005; synthetic invoice oracle не означает, что manual18 уже поддерживает их.

Small UCI≤30MB/600krows/60CPUmin/0fits — отдельный **неодобренный** proposal; не прибавка к016 или глобальному ledger. Приоритет остаётся REES46. Ни публичная лицензия, ни удачный mapping не подтверждают recommendation generalization.

## Round005: арифметика корректна, promotion rule надо разделить

Независимый пересчёт подтвердил таблицу sensitivity: при n73 half-width .01147/.02294/.05735, detectable Δ .01639/.03277/.08193, необходимые n4900/19600/122500. Hoeffding half-width≈.31791. При zero-convention .002×73/4000=.0000365 верно. Эти числа условны на independent positive queries/fixed models; actual variance, positive-user clusters и confirmation support неизвестны. Candidate rows и bootstrap repetitions не увеличивают независимую поддержку.

Первичные основания корректно ограничены: [Cawley–Talbot](https://jmlr.org/papers/volume11/cawley10a/cawley10a.pdf) предупреждает о переобучении selection criterion; [Thresholdout](https://arxiv.org/pdf/1506.02629) — контролируемый механизм доступа, не обычная точная метрика; [Ladder](https://proceedings.mlr.press/v37/blum15.pdf) прямо называет adaptive significance-test вариант heuristic. [Bergmeir et al.](https://robjhyndman.com/papers/cv-wp.pdf) допускает CV при специальных условиях, не оправдывает shuffled purchase-ranking split. Новый DP/leaderboard implementation не требуется.

**Material amendment1:** фраза «CI пересекает0/порог — inconclusive» противоречит сохранённому gate point Δ≥.002 и lower>0. Пример estimate .002, CI[.001,.003]: установленный promotion gate проходит, хотя CI пересекает practical threshold. Однозначно записать: CI crossing0 — inconclusive по знаку; point<.002 — practical gate не пройден; lower>0 и point≥.002 — заявленный gate пройден **без доказательства true Δ≥.002**. Для последнего нужен lower≥.002 и отдельный prospective amendment, сейчас его не добавлять.

User-cluster bootstrap с пересчётом conditional query-macro ratio — подходящий предложенный estimand; не среднее user means и не item resampling. Он не оценивает неопределённость будущих дневных shocks. Selection CI остаётся screening-only. Confirmation25/final26 chronology правильно различает заранее frozen-model evaluation и новое решение по confirmation outcome. Config reservation/availability пока требуют отдельного acceptance; никакой поздний выбор/refit в нулевой gap не разрешён.

## Round006: bucket/DAG корректны, физический speedup неизвестен

Последний global timestamp определяется по `[S,t)`, затем сворачивается **весь** tied bucket. Field-independent NULL/conflict states и отсутствие older-clean backoff согласованы с005/009. Count/nonnull/min/max reducer корректен при объявленном equality и предварительном nonfinite guard. Price0 — NON-NULL clean-but-invalid, не missing. `arg_max` игнорирует NULL argument, `arg_max_null` всё равно выбирает строку; ни один не проверяет consistency peers. [DuckDB aggregates](https://duckdb.org/docs/current/sql/functions/aggregates).

Max+rejoin — оправданный P0 physical proposal. Equivalence active-presence↔last_past_ts≥lower верна только при том же event predicate, не заменяет raw count/distinct users. Strict `ASOF … t>bucket_ts` после bucket reduction допустим; ASOF USING использует>= и включает peers. [Join specification](https://duckdb.org/docs/current/sql/query_syntax/from). Exact anchor/source/policy cache identity обязательна; calendar day не достаточный key.

Reference distinct active products с current clean category и finite positive price включает товары внеC. Historical category numerator005 отдельно. Leave-one-out требует membership-conditioned subtraction, особенно invalid own price/unknown category/empty/singleton R;0×NULL не является guard. As-of historical dictionary не превращается в latest code imputation. Это согласованный будущий009 блок, не новый quality mechanism.

Numeric guard только relevant selected past buckets сохраняет future-suffix invariance. LN(1+p) вместо log10 соответствует логической log1p с tolerance; для очень малых p возможна потеря точности относительно Python log1p, поэтому обязательны заранее заданные tolerances/finite/float32-overflow fixtures. [Numeric API](https://duckdb.org/docs/current/sql/functions/numeric). Reuse/pushdown/spill/индексы ещё не измерены; EXPLAIN ANALYZE исполняет запрос. Proposed100Q gate и один009 ablation не расширяются, engine memory_limit не hard RSS.
