## Primary evidence and its limits

[DBSP, VLDB Journal2025](https://link.springer.com/article/10.1007/s00778-025-00922-y), published8May2025, describes compositional automatic incrementalization. I inspected its publisher abstract/metadata; subscription full text was not available. Its [author compiler documentation/code](https://github.com/feldera/feldera/blob/main/sql-to-dbsp-compiler/using.md) exposes SQL→incremental change-stream compilation. The [author distinct operator](https://raw.githubusercontent.com/feldera/feldera/main/crates/dbsp/src/operator/distinct.rs) distinguishes a batch's positive-weight set from incremental changes to the accumulated relation. These establish mechanisms and an implementation boundary, not our cost or adoption of Feldera.

Two primary2024 engineering records sharpen the caveats. [Feldera's lifetime analysis](https://www.feldera.com/blog/time-series) requires true source properties such as append-only input and bounded disorder before discarding state. [Issue1768](https://github.com/feldera/feldera/issues/1768) records identical temporal input maps creating three separate rolling traces, closed via1805 in May2024. A shared logical stream consequently does not prove shared physical storage. I did not inspect the linked patch successfully and do not claim its current implementation details.

[DuckDB's February2025 author article](https://duckdb.org/2025/02/10/window-catchup) describes optimized window DISTINCT and cases falling back to a naive implementation. In inspected [author code](https://raw.githubusercontent.com/duckdb/duckdb/main/src/function/window/window_distinct_aggregator.cpp), the fast path builds previous-occurrence/merge-sort-tree state and requires no exclusion and no argument ordering. Rewriting strict-past features with `EXCLUDE GROUP` cannot simply assume this path. Current upstream code is mutable and is not proof about the project's pinned installed engine. Both proposals below are our adaptations, not algorithms or performance attributed to these sources.

## A005-01 — compile fixed anchor/window boundaries into shared count intervals

**mechanism.** Given frozen anchors A and finite windows W, construct sorted boundaries B={source_start}∪A∪{a−w:a∈A,w∈W}. Compile each raw-count leaf to counts over disjoint `[b_j,b_{j+1})` intervals, keyed by its exact grain/action/policy signature. Every raw row contributes its multiplicity to one interval for each required grain. Build cumulative counts per key; every requested `[a−w,a)` is then the difference of two boundary prefixes. Shared inputs serve all windows and days. An event exactly at a belongs to the next interval and cannot affect a's output; lower-bound equality remains included. These boundaries are not arbitrary calendar buckets: irregular anchors create additional boundaries.

Observed recency and first-seen state have separate full-prefix min/max reducers and never expire with finite counts. Candidate metadata retains the **whole latest global timestamp bucket**, including known/NULL category mixtures from other users. Category counters use historical event category, not the latest metadata category; complete category denominators are not restricted to C. Ratios, coverage and missingness remain final typed projections. Membership can be restricted only using a predeclared label-free union of requested users/items over the fixed workload; if that union is unavailable before replay, retain all eligible keys or defer. Unknown candidate category still yields NULL conditional features; known empty keys yield0. Frozen retrieval inputs remain passthrough, not regenerated C.

**testable_prediction.** With many anchors over overlapping source prefixes, decoding/examining source rows once and sharing count intervals should reduce repeated scan/aggregation work relative to unchanged005. It may lose when union support, sorting, interval payloads or common export dominates. There is no guaranteed speedup and no expected ranking gain: exact B/W features are the output contract.

**nearest_source_free_experiment.** First use direct-list predicates and a separate interval interpreter on ≤4096 invented rows, ≤32 users/items,15 anchors and windows24/168h; include irregular anchors, lower/upper equality, raw duplicate rows, emptyC, NULL mixtures, category moves and an off-candidate denominator contributor. Compare every core/mask and full output keys, not merely a row count. Count examined rows, interval cells, transitions, metadata buckets and complete sink writes. No SQL, producer imports or model is required for this first gate. A later separately authorized native comparison must use unchanged005, optimizerON, the same fixed B41+exact R2 registry and complete common sink; faster than the direct-list oracle alone proves little.

**benefit_task1.** This makes repeated-anchor reuse an automatically derived physical plan from typed definitions. A successful result can show correct automated calculation and a scoped CPU/state improvement; it cannot show superior feature generation, human-time savings or recommendation quality.

**Finite physical cost.** Let E be raw rows to the last anchor, G the distinct grain/action keys, P boundary points, S nonempty key/interval cells, and F emitted feature values. P≤J(L+1)+1 for J anchors and L window widths. Count dispatch is ≤6E for the six existing grains; S≤6E and dense prefix storage is at most G(P−1) counters, so sparse storage is preferable. Prefix construction is O(S) after grouping/sorting cells, and reads cost two prefix lookups per count. Metadata/first-seen, distinct support, masks, joins and O(F) writing remain paid work. Group/action keys and interval cells need encoded bytes, not just counts, before a memory claim.

Count binning alone permits unordered rows; a combined chronological pipeline with recency snapshots/last-occurrence state requires authenticated nondecreasing timestamps or a paid external sort, potentially O(ElogE) comparisons and O(E) spill. That cost can erase the benefit. No late-row dropping is permitted. Reading once is not bounded memory: union keys, latest metadata buckets and high-cardinality supports can exceed8GiB. Logical scan count does not establish physical bytes/pages read, and existing005 may already prune source partitions. Retain failed/censored attempts.

**newvsrefine / knownoldIDs.** Refinement of HYP-046 and TLAB-005/016; type/identity obligations already in HYP-002 and round009, honest timing already in round012. It adds a finite-anchor interval representation and explicit cost comparison, not a canonical new hypothesis. The future compiler/measurement gate is independent of finishing015.

## A005-02 — specialize exact multiwindow DISTINCT to last occurrence

**mechanism.** For an append-only prefix already processed through all events `<a`, a value v is present in `[a−w,a)` iff its latest qualifying occurrence ℓ(v) is at least a−w. Compile DISTINCT leaves sharing grain, action, projected nominal value and NULL/filter policy into one last-occurrence map. On a new occurrence, move that value's membership from its old boundary interval to the new interval. Maintain interval counts with prefix/rank lookup; windows24/168h share this state. Repeated rows in the same interval do not add DISTINCT memberships. Raw COUNT keeps its independent multiplicity counters.

At each anchor, snapshot before ingesting **any global timestamp peer** at a. Evict a value only when its latest occurrence is strictly below the largest remaining required window's lower frontier; an older occurrence expiring must not delete a value reobserved later. An intrusive per-interval membership list with removal on a move avoids an unbounded queue of stale expiry notices. Full-prefix recency/metadata remain independent. NULL projection follows COUNT(DISTINCT)'s NULL-skipping policy, whereas NULL candidate category remains an unavailable conditional key. Sharing across different actions, projections, source policies or missingness contracts is forbidden.

**testable_prediction.** For repeated interactions, retained memberships approach the number of distinct `(grain-key,action,value)` triples within the maximum active window, rather than the number of raw occurrences or separate per-window multiplicity traces. Benefit disappears on nearly unique data; pointer/hash overhead can make it worse. It applies only to monotone anchor replay and immutable append-only events, not arbitrary deletions, corrections or time travel.

**nearest_source_free_experiment.** Compare direct sets, a generic exact multiplicity/expiry implementation, and the specialized map on the same tiny input; then fixed4096-row repeated-value and all-unique controls. Explicitly test a value duplicated across days, renewed before its old expiry, same-second duplicates, NULL, shuffled global peers and appended future suffix. Both filters must agree at every anchor/window; record live keys, live expiry entries, moves and storage bytes. Test a source retraction as an expected **unsupported-plan rejection**, not a misleading successful result. No native engine is needed. Only after correctness may a future cost pilot assess unchanged005 against A005-01 with generic distinct and with specialization, all with the same complete B/W outputs.

**benefit_task1.** The compiler chooses sufficient state from declared operator/source properties, making exact DISTINCT support explicit rather than assuming all aggregates have reversible sums. This is an operator specialization inside the same physical automation family; it supplies no additional predictive information.

**Finite physical cost.** D active distinct triples require a map entry plus one live interval-membership entry each. Prefix/rank state costs O(P) per nonempty distinct group, or sparse equivalent; do not hide that factor behind O(D). Each relevant raw row is examined once; at most two distinct projections per row are needed for the current user/item vocabulary. Membership moves cost O(logP) with an indexed count structure, unchanged intervals can avoid a move, and each retained value is evicted once before a possible later reinsertion. Window readout is O(logP) per group/window plus O(F) final broadcast/sink. Distinct-state key count may still scale with E; no cardinality-independent memory bound is claimed. Primitive schemas outside this whitelist fall back to a reviewed exact operator, not approximation.

**newvsrefine / knownoldIDs.** Refinement/suboperator of HYP-046 and existing TLAB-005 exact-distinct semantics. Last-occurrence sufficiency is not claimed as an academic invention. Its distinct value here is a typed, multiwindow physical specialization and a head-to-head state/cost falsifier. No extra HYP or native budget follows.

## Executed literal evidence and next decision

A standard-library-only probe used12 invented events,8 anchors, windows1/7 **days**,15 boundary points, and all six count grains. All16 count-dictionary comparisons and16 user/item DISTINCT-dictionary comparisons matched independent direct predicates. The input contains duplicates, expiry, same-second peers and NULL metadata. Before anchor2, item1 has3 raw views but1 distinct viewer; summing daily distinct counts gives2 and is wrong. Its latest category is10 at anchor2, then a known20/NULL global peer bucket makes it unavailable/ambiguous at anchor3. The complete category10 denominator is4 versus3 after an invalid candidate-only filter. The ledger retains the exact input and scope. This validates tiny algebraic/state witnesses, **not** the full B41/R2 compiler or throughput. Peer-permutation/future-suffix and bounded generated-shape tests remain the next gate.

Two further counterexamples delimit admission: after occurrences x@0,x@1, deleting x@1 requires recovering0, which a single last-occurrence value cannot do; and taking last occurrence over the entire future source before snapshot a leaks later state. Source-property checks and chronological snapshots are mandatory.

Prospective source-free gate: ≤4096 generated rows,15 anchors,2 windows,0 fits,≤60 process-CPU seconds and128MiB; every setup/oracle/output/failure counts. These are proposed stop caps, not authorization or feasibility measurements. Pass yields a candidate for engine design; semantic failure rejects the rewrite; equal state/work keeps correctness only; worse physical cost closes the efficiency claim. Any later timing must keep round012's balanced setup/cache/common-sink discipline and include sort, validation, metadata, preparation, serialization and cleanup. Both mechanisms remain **candidate/refinement awaiting independent skeptic**, with no prerequisite added to015 and no new ongoing experiment.
