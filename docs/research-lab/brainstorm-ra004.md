## What the contract can preserve, and what must refuse

Event mapping is proposed explicitly: visitorid→nominal user, itemid→nominal product, `view→view`, `addtocart→cart`, `transaction→purchase`. A visitor key is not a verified person/login. Transaction ID is not an event ID, quantity, session or license to collapse repeated rows. Counts preserve raw event rows; projected distinct counts use non-null named entity keys. Y is distinct product IDs from transaction events, not number of orders or revenue. Unknown actions/keys require a declared validation policy. Purchase absence cannot be replaced by an add-to-cart or click label from a convenient prepared benchmark.

Use exact integer source time plus an explicit epoch-unit adapter to UTC; never infer machine timezone or transport IDs/timestamps through float32. Source units must pass the later gate. At daily 00UTC anchor t, all global native-timestamp peers at t are excluded from every historical feature, eligibility and C; target is `[t,t+24h)`. Window lower bounds are inclusive; recency uses the complete permitted observed prefix rather than only a seven-day slice. A daily clock does not need sessions. Thirty-minute synthetic sessions or a benchmark's next-click examples would create a separate task, not repair a missing field. Whole target windows must mature and observation completeness must be established; observed minimum/maximum timestamps alone do not prove either.

The original C rule transfers as a **rule**, rebuilt solely from this source's history: P200 distinct purchase visitors over 7d plus R20 distinct recent products over all three actions over 7d, union/dedup/no-refill, bought products retained, size ≤ 220. Eligibility remains any observed action in the prior 48h, with ≤ 2,000 bottom-hash queries chosen before Y. IDs, calendar dates, manifests, training populations, model state and heldout claims do not transfer. Prior-event catalog is an observation proxy, not inventory. Do not filter C or fullY using latest `available`, inject future transactions into C, or demand that a target already appear in source metadata.

The [frozen manual registry](../../configs/features/manual-18.json) has 12 noncategory cores and 6 category-conditioned cores. Its implementation chooses candidate category from the last global past **event bucket**, and category counters use historical event category. RetailRocket needs a separately reviewed property-to-EventFact enrichment: for each actual event, resolve each required property from strictly earlier recorded state; properties never become fake views. Missing earlier state stays unknown. Later property rows cannot backfill an earlier event. Conflicting latest equal-time values, including known+NULL, stay unknown without older backoff. A constant value's missing repeated snapshot is not deletion.

Two possible category semantics must not be silently exchanged. Under frozen last-observed-event semantics, a category update after the latest item event does not update candidate context. Under query-current-property semantics it does, changing six cores and B context. The latter requires a new adapter/control identity and review. Recorded weekly snapshots also do not establish exact business change instants or ingestion times. The tree lacks an established historical availability clock; no invented category names, brand or price mappings are allowed. Existing round036 already records this seam; this note adds explicit acceptance/refusal witnesses below.

AST8's count/distinct/cart-recency operands use the three observable action channels, user/item/pair grains and 24/168h windows, so their **individual event-valued definitions** have a plausible transfer. This does not approve their execution pipeline. `scripts/feature_programs.py` validates the exact schema, all three action capabilities,18-core base and 41-column model schema before generating L01–L08; every bundle adds exactly 3 physical columns. Silently replacing unsupported category fields by zeros/NULLs or deleting six cores does not preserve that accepted base. Static L02/L06, two uniform replacement draws with seed 2026, whole-bundle collision consumption/no-refill and fixed opportunities describe an existing procedure, not permission for new fits. A reduced baseline needs a new explicit contract; it cannot be passed through the existing full-base generator by renaming columns.

## Two concrete adapter rejection witnesses

**F1 — clock/action/bag/Y boundary.** Hand-declared anchor T is UTC midnight; express durations in source milliseconds only after unit confirmation. Put a view at `T−86,400,000`, another at `T−1`, two identical cart rows at `T−1,000`, and another user's view at T. The first view is inside the 24h lower boundary; the second has recency 0.001 seconds; the peer at T contributes to no past item/user aggregate. Pair cart count is 2, distinct cart visitors 1. Put transactions on products Z at T and W at `T+86,400,000`: fullY contains Z and excludes W; if Z is outside C it is still a miss. Rejection examples: treating milliseconds as seconds, rounding `T−1` into T, retaining only one duplicate cart, converting cart into purchase, admitting the global peer, or deriving target from session-next-event/covered positives. This is a literal specification, not an executed dataset test.

**F2 — metadata clocks do not make business events.** Property X/category=A at `T−4h`; user U views X at `T−3h`; X/category=B at `T−1h`; X/available=0 at `T−30min`; X/category=C after T. Historical view category stays A. Under frozen manual18 context, candidate X remains A because its latest event was that view; under a separately declared query-current-property protocol it is B. If U has only that view, category-conditioned U view count/share is 1/1 for frozen A and 0/1 for property-current B. Neither protocol may produce C. The availability row must neither erase category B nor alter view counts. A latest category bucket containing B and NULL must yield unknown under the declared conflict policy, with noncategory counts intact. Reject a single final dictionary, an item-wide latest-property lookup, cross-property overwrite, join fanout, or treating property updates as events. A resolver cannot pass by switching expected A to B after seeing output.

## Fair common estimand, with no current quality experiment

First choose the estimand and capability route before labels. Route 1 preserves the full original feature meanings after a reviewed as-of EventFact adapter, including last-observed-event category; full18/B41 acceptance remains conditional. Route 2 explicitly compares a **reduced common event-only study** on both REES46 and RetailRocket:12 manual noncategory cores and compatible source context, with the same event-only AST definitions. Strip category-dependent context on both sources, regenerate/schema-review physical closure and allocation identity, and give the changed baseline its own name. This is not reproduction of the accepted manual18 experiment. If neither route can establish source completeness and feature semantics, refuse the quality test and retain the source-only finding.

Within each dataset d, use identical Q/C/fullY, dates, source availability, learner/training rule and limits for the manual control and chosen augmentation. Estimate the paired per-query difference `Δd = mean_q[NDCG@20(Bd+G,Cd,Yd)−NDCG@20(Bd,Cd,Yd)]`, with the established fullY ideal/zeroY convention; additionally report fullY candidate coverage and off-C loss so a fixed-C ranker gain is not advertised as catalog retrieval gain. Query IDs are source-local, so raw levels across sources are not paired or pooled as if users were interchangeable. Candidate cardinalities and purchase rates may differ naturally across sources; no outcome-dependent size matching or purchaser-only query selection is permitted.

If studying the bounded selection procedure, keep its preregistered opportunities, collision/no-refill law and model budgets across compared strategies; train source-local controls from eligible mature windows and charge their preprocessing/fits. Selection and confirmation dates are new source-local prospective choices; no reuse of the REES46 closed heldout or target-driven source/date/bundle choice. Two datasets and one random allocation seed support a limited transport case study, not general superiority of learned automation or measured human-hour savings.

Today's **documentation/metadata research** confirms claimed capabilities and proposes falsifiers. A future scan of actual property files is already real source processing: it must charge both property parts, state reconstruction, sorting/indexing, raw-preserving event enrichment and physical reads; inspecting a small prefix does not certify strict-past coverage. It can establish adapter mechanics and data quality, not model quality. A real external quality test additionally requires a separately authorized, versioned source/adapter/Q/C/fullY/training/evaluation contract, completion/maturity evidence and all model/cost accounting. The card's 987.5MB is not an RSS or runtime estimate. No new scan, fit budget or external-test approval is granted by this note.
