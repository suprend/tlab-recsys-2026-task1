# Wave004: independent Amazon primary-source check

Checked 2026-10-15. Scope: the Amazon round004 draft and ledger; provider documentation, author paper and source code only. No RetailRocket peer draft, corpus/archive endpoints, actual Q/C/Y, SQL execution, imports, fits, weights, paid APIs or shared edits. RelBench was also independently read by helper `relbench_names`, and the decisive versioned sources were reread by this reviewer.

**Disposition:** the refusal of unchanged purchase/fullY transfer is supported. One material qualification is required: RelBench's advertised two-year horizon conflicts with its pinned v1.1.0 source configuration. The timestamp-key mismatch and exact parent-item deduplication grain should remain explicit adapter gates. These findings establish source semantics, not successful adapter execution or predictive transfer.

1. **Review clock and complete purchase-fullY: supported boundary.** The provider field table defines `timestamp` as review Unix time and `verified_purchase` as a verification flag. It documents neither purchase time nor a complete transaction/exposure log. Parent ASIN groups variants and is the metadata join key; the site also explicitly notes missing item metadata. Price is crawl-time price, and `bought_together` means recommended website bundles. These facts support refusing purchase-time labels or order edges; they do not prove that any particular released row has a bad value. [Provider fields and statistics](https://amazon-reviews-2023.github.io/main.html#data-fields).

   The author's v2 paper states millisecond precision, but Appendix B describes user-centric review collection and acknowledges incomplete item coverage and recent reviews missing before cutoff. The exact four published counts and May-versus-June start-date discrepancy in the draft agree with the paper/site. The identifiability worlds in F1 are the author's own logical argument: the sources support their premises, while no synthetic test was executed. [Paper v2, 20 April 2026, §3/Table 1 and Appendix B](https://arxiv.org/html/2403.03952v2#S3).

2. **Earliest deduplication and iterative core: directly corroborated in code.** `load_ratings` projects `parent_asin`, `user_id`, rating and time. `make_inters_in_order` sorts each user's rows by timestamp, then retains the first occurrence of each parent item. `filter_inters` repeatedly removes users/items below threshold until stable. `preprocess_rating` runs deduplication first; main writes the deduplicated unfiltered output as 0-core and the filtered output separately. Therefore use the precise grain **(user_id, parent_asin)**, not variant ASIN. [Author code, lines 7–101 and 124–128](https://github.com/hyp1231/AmazonReviews2023/blob/main/benchmark_scripts/kcore_filtering.py#L7), [author preprocessing description](https://github.com/hyp1231/AmazonReviews2023/blob/main/benchmark_scripts/README.md#L24).

   Future-sensitive 5-core membership is an inference from whole-file filtering before splits, rather than an observed leak in a checked corpus. A later suffix can move a user or item above the degree threshold. The documented 0-core and absolute-timestamp splits do not undo prior deduplication or create observed purchase negatives. [Official 0-core description](https://amazon-reviews-2023.github.io/data_processing/0core.html#before-data-splitting).

3. **Timestamp spelling: real documentation/code discrepancy, bounded claim.** The public site example uses `sort_timestamp`, its field table and HF README example use `timestamp`, while `load_ratings` indexes `dp['sortTimestamp']` directly and catches only `ValueError`. A literal containing only the documented `timestamp` field would therefore fail that lookup by Python inspection. This is sufficient to require an exact release/schema normalization contract; it does **not** establish that the distributed corpus or published processed files fail. [Site example](https://amazon-reviews-2023.github.io/main.html#load-user-reviews), [HF README example](https://huggingface.co/datasets/McAuley-Lab/Amazon-Reviews-2023/blob/main/README.md), [code lookup, line 13](https://github.com/hyp1231/AmazonReviews2023/blob/main/benchmark_scripts/kcore_filtering.py#L13).

   Version limit: that script's visible history identifies `002ed81`, “Init READMEs,” 6 February 2024. Full-SHA/API retrieval failed; the inspected URL is `main`, not a cryptographically frozen checkout. Do not silently promote that short history identifier to the repository's current HEAD. [File history](https://github.com/hyp1231/AmazonReviews2023/commits/main/benchmark_scripts/kcore_filtering.py).

4. **Metadata availability: source fact versus policy.** The published schema supplies snapshot product fields and no per-field historical availability clock. Requiring refusal/NULL for an as-of category request is the draft's conservative adapter policy, not a provider assertion that categories necessarily changed. A separately declared static-catalog policy could define another task, but cannot be retroactively chosen from scores. F2 is a useful specification for that policy; it is not evidence that an adapter was run or found defective. [Provider metadata fields](https://amazon-reviews-2023.github.io/main.html#for-item-metadata).

5. **Dataset license: unresolved characterization is supported.** The maintainer's 8 March 2024 reply says they cannot assign a dataset license and make it available primarily for research; the later answer concerns one thesis. No license field was found in the current README. The repository MIT text covers software and associated documentation. Neither that code license nor the paper's publication license establishes a general corpus redistribution grant. This records the available provenance, without deciding the corpus's legal status. [Maintainer thread](https://huggingface.co/datasets/McAuley-Lab/Amazon-Reviews-2023/discussions/1), [repository LICENSE](https://github.com/hyp1231/AmazonReviews2023/blob/main/LICENSE).

6. **RelBench: material docs/code qualification required.** The current HF card describes `user-item-purchase`, `user-item-rate`, `user-item-review` as two-year forecasts, and `review-rating` as autocomplete regression. [Current card, tasks](https://huggingface.co/datasets/stanford-star/relbench-v1/blob/main/rel-amazon/README.md).

   Pinned v1.1.0 instead configures all three user-item classes with `pd.Timedelta(days=365 // 4)`, i.e. **91 days**. They select distinct products from `review` using `review_time`; rate adds `rating = 5.0`, review adds text length **>300**. No verified-purchase predicate appears. LEFT JOIN followed by non-null review IDs omits customers without qualifying future rows, instead of emitting explicit empty targets. These are static-source observations, not verification of published cached label tables or successful execution of the SQL. [v1.1.0 task code, lines 222–368](https://github.com/stanford-star/relbench/blob/v1.1.0/relbench/tasks/amazon.py#L222).

   Its dataset builder defaults to Books/5-core from `amazon_v2`, maps `unixReviewTime` to `review_time` in **seconds**, and keeps product/customer tables static. This is a different Amazon release and cannot be called an Amazon Reviews 2023 adapter. [v1.1.0 dataset builder](https://github.com/stanford-star/relbench/blob/v1.1.0/relbench/datasets/amazon.py#L10).

   The v1.1.0 registry has seven Amazon tasks and lacks `review-rating`; the current card must not be presented as that version's task inventory. [Versioned registry, lines 92–98](https://github.com/stanford-star/relbench/blob/v1.1.0/relbench/tasks/__init__.py#L92). Verified version commit: [`9aa346267c2e1c560bd92da07d6f4ad1ca2f0639`](https://github.com/stanford-star/relbench/commit/9aa346267c2e1c560bd92da07d6f4ad1ca2f0639); SHA-specific raw requests failed, while tag source and version commit were readable. No current-version implementation or cached-label horizon is certified here.

Suggested bounded wording for integration: “The current RelBench card describes two-year, purchase-labelled review tasks. Its v1.1.0 code instead configures 91-day review-time targets, and its registry predates `review-rating` autocomplete. Exact task version, target construction and published-label provenance must be pinned separately.”

No job is admitted by this review. The next useful gate remains a source-specific capability contract with tiny independent fixtures; corpus rights, source coverage and a fresh Q/C/Y experiment remain unresolved execution prerequisites.
