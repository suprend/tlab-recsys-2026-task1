## Endpoints и training population: обязательные уточнения

**L02 использует другой target.** Закрытое справа `(t,t+H]` включает purchase ровно в t+H и исключает purchase ровно в t; принятый provisional clock `[t,t+H)` делает обратное. Для текущего 008 использовать endpoints из [config](../../configs/protocols/clock-48h.json), а не из индивидуальной рекомендации L02. History остаётся `[t−W,t)`, все глобальные peers прогнозируются до update. Одна покупка ровно в t даёт positive при clock и отсутствует в history; purchase ровно t+H не относится к этому query. Это допустимая pre-update постановка, не утверждение о внутрисекундном порядке.

Старый target appendix с `(t,t+H]` тоже нельзя читать как универсальное правило maturity. При доступных событиях `<c` right-open target зрел при `t+H+delay≤c`; right-closed требует строгого `<c`. Незрелый хвост исключается, не становится all-negative. [Temporal contract](../../scripts/temporal_contract.py) уже различает эти случаи. Conversion после view из L01 остаётся отдельным protocol ID с собственной единицей наблюдения, endpoints и доступным контекстом; sigmoid не делает conversion и clock-ranking одним estimand.

**Основной BCE и PairLogit имеют разную эффективную training population.** По L01 и принятому target-training контракту BCE использует все зрелые непустые C: Y пуст, Y непуст но весь вне C, mixed C, all-positive C. PairLogit получает сигнал только при `0<p=|Y∩C|<|C|`. Поэтому B_all-BCE против PairLogit — честное сравнение двух training policies, а не изолированный эффект формы loss. Общие Q/C/features/evaluation необходимы, но не устраняют это различие.

L03 предлагает общий informative mask для чистого loss comparison; применять его автоматически к основному BCE нельзя. Same-informative BCE — отдельная ablation, оплаченная дополнительной попыткой либо заменой заранее выбранного варианта. До smoke фиксировать эту развилку и назвать результаты соответственно. Публиковать числа empty C, empty Y, missed-positive и informative groups, не только buyer count. Нельзя подбирать query sample по будущему p или добавлять positive/negative ради обучения. Полностью беспарный train блокирует PairLogit, но не доказывает непригодность BCE.

## Веса и sampling: что именно оптимизируется

L01 задаёт корректный риск `mean_q mean_(i∈Cq) BCE`. Object weight `1/|Cq|` даёт каждой непустой группе массу 1; это macro-query, не macro-user. Для user-balanced риска нужен отдельно заданный вес anchors пользователя. All-zero группа даёт производную `σ(z)` по logit, all-positive — `σ(z)−1`; pairwise не получает relative contrast в обоих случаях. Отсутствие покупки не является зарегистрированным отказом после показа.

Для PairLogit полный `p·n` набор с pair weight `1/(pn)` задаёт единичную массу информативного query. При одинаковом числе k uniform negatives на positive вес `1/(p·k_actual)` корректен; singleton/недостаток negatives обрабатывается до деления. Альтернатива — uniform sample пар с общей массой 1. Эти sampler contracts не эквивалентны по дисперсии, их нельзя менять молча. Default automatic pairs/max_pairs сам по себе не гарантирует заявленный macro-query риск. [CatBoost ranking docs](https://catboost.ai/docs/en/concepts/loss-functions-ranking) подтверждают, что PairLogit использует pair weights, а не object weights. [Pool](https://catboost.ai/docs/en/concepts/python-reference_pool) требует contiguous groups и согласованные indices/weights; одинаковые числовые object weights не заменяют нормировку пар.

HYP-027 математически обоснована как P1: сохранить positives, negative включать без возвращения с `π=m/Nneg`, вес `1/(|C|π)`, denominator полного C. При фиксированном m сумма inverse weights в query детерминирована и совпадает с полным количеством строк. При Nneg=0 ветвь sampling не вычисляется. Self-normalized denominator при неравномерном sampling — другой estimator; sampling с возвращением требует draw probabilities и multiplicity. Large weights повышают variance, clipping меняет цель. Class balancing и `pos_weight` тоже меняют риск; теоретический monotone posterior shift при постоянном множителе не гарантирует сохранённый порядок конечной модели или calibration.

HYP-036 mixed negatives — отдельная ограниченная альтернатива uniform, не автоматическая часть PairLogit. Для восстановления uniform risk нужны известные вероятности смеси и полный support; deterministic hard-only этого не даёт. Hard scorer, sampler statistics и universe доступны до соответствующей строки, иначе ранние train features/sampling используют будущее. Нельзя очищать negatives по покупкам после target horizon. Importance correction внутри C не исправляет неизвестный exposure и не восстанавливает каталог вне C.

## Listwise: суррогат и full-Y criterion различаются

LambdaRank использует pairwise lambdas с rank-dependent ΔNDCG; это не обычный pair loss с фиксированным весом. YetiRank Classic, NDCG-mode и XE_NDCG имеют разные цели/алгоритмы. Название NDCG-oriented не означает оптимизацию именно принятого full-Y NDCG@20. Candidate-only IDCG меняет вес queries с неполным покрытием: из трёх targets единственный найденный первым даёт full-Y NDCG≈0,469, а native candidate metric — 1. Native training surrogate допустим, но выбор checkpoint должен использовать [evaluator006](../../scripts/ranking_metrics.py) с полным Y и фиксированным tie-break.

Сверка [LightGBM v4.6.0 objective](https://raw.githubusercontent.com/lightgbm-org/LightGBM/v4.6.0/src/objective/rank_objective.hpp) подтверждает различие zero-groups: LambdaRank пропускает equal-label пары; XE_NDCG для длины>1 строит случайную φ и может дать ненулевое обновление даже при одинаковых labels. Это не обучение абсолютной вероятности отсутствия покупки. [Native metric](https://raw.githubusercontent.com/lightgbm-org/LightGBM/v4.6.0/src/metric/rank_metric.hpp) при unit query weights возвращает 1 для candidate IDCG=0; такой query может иметь непустой full Y, полностью missed retrieval. Mutable main и проверенный source tag не доказывают поведение установленного будущего runner: pinned версия проходит golden tests перед использованием.

Early stopping по native candidate metric не исправляется последующим внешним отчётом. CatBoost runner должен выбирать итерацию по full-Y selection criterion либо заранее фиксированному iteration budget. Для LightGBM убрать default metric через `metric="None"` и оставить custom full-Y criterion единственным stopping metric; одного `first_metric_only=True` недостаточно, если native metric остаётся первым. Это следует из официальных [train API](https://lightgbm.readthedocs.io/en/stable/pythonapi/lightgbm.train.html) и [early_stopping](https://lightgbm.readthedocs.io/en/stable/pythonapi/lightgbm.early_stopping.html). Empty queries остаются в evaluation manifest, censored отделяются; conditional/all-query/user-macro estimands не смешиваются.

## Компактный MVP и gates

Сохранить CPU CatBoost smoke 008: один all-mature-C query-weighted BCE и один normalized PairLogit, ≤2 fit-конфигурации, 2 threads и текущий time/resource gate. Explicit pair construction сначала проверить tiny oracle: unequal candidate sizes/positive counts, all-zero/all-positive/singleton, duplicate candidate IDs, partial Y coverage, endpoint purchases и same-second suffix invariance. Sample probabilities, суммарная масса query, train mask, maturity/available_at и model/config/input lineage входят в manifest. Raw matrix arithmetic из notes не измеряет Pool/quantization/pairs/fit buffers; preparation, fit, scoring, RSS/spill и failures оплачиваются ledger.

HYP-035 отклонить как дубль существующего PairLogit/BCE 008. HYP-027 оставить needs-pilot после full-C контроля; её дополнительные два fits — предложение, не расширение общего бюджета. HYP-036 — optional P1 после sampler review/cost reservation. HYP-043/044 остаются reserved, L03 не формулирует две новые проверяемые записи. Focal, hinge, YetiRankPairwise и новый BPR-MF — deferred; при разрешённом следующем шаге выбрать один CPU `YetiRank:mode=NDCG;top=20;dcg_type=Base;dcg_denominator=LogPosition`, а не одновременно новую библиотеку и loss. Non-Classic CPU restriction и default Position проверены по CatBoost docs; GPU availability не предполагается.

Smoke устанавливает выполнимость, а не победителя или strong tuned B. До claim нужен bounded tuning на selection 22–23 с равным учётом попыток; confirmation 24–25 закрыта для early stopping и выбора, final holdout не читается. Warmup encoders/priors/calibration доступны до downstream; выбранное решение доступно до freeze. Paired user-bootstrap пересчитывает общий estimand и не устраняет selection bias. По task1 центральный результат — эксперимент автоматизации либо альтернативы сверх хорошо настроенного ручного boosting; новые названия losses его не заменяют. Review группы 01–03 этот результат не устанавливает.
