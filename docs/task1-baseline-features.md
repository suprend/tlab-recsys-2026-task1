# Базовый набор признаков для ранжирования новых товаров (T-Lab 2026, задача 1)

## 1. Принцип и отличия от старого baseline

**Постановка.** В якорь `t` (00:00 UTC) ранжируются кандидаты, которых пользователь до `t` не касался ни одним событием. Прямой истории пары нет, поэтому все пользовательские сигналы действуют косвенно, по двум каналам:
- отношение кандидата к категориям, брендам, ценам и уровню популярности того, что пользователь недавно смотрел;
- item-item и category-category связи от его недавних товаров: совместные просмотры в сессиях, переходы «просмотр → первый cp нового товара».

**Уровни признаков.**
- `s_` — источник кандидата и ранг в нём.
- `u_` — пользователь (запрос). Внутри запроса это константа, поэтому работает только во взаимодействиях. В core оставлены 6 таких признаков, остальные идут в extra.
- `i_` — товар, одинаков для всех пользователей.
- `uc_`, `ub_`, `up_`, `ui_`, `cf_` — пара «пользователь × кандидат»: категория, бренд, цена, популярность относительно вкуса пользователя, item-item CF.

**Правила построения.**
1. **Нормированные формы вместо сырых счётчиков:** доля от глобальной суммы того же окна, lift к глобальной конверсии того же окна, ранг, логарифм, отношение. Сырые объёмы дрейфуют: cart-лог проседает в 2–2.5 раза по неделям, история обрезана началом 1.10.
2. **Единое окно истории L = 14 дней.** Каждый признак читает только события из `[t−14d, t)`. Затухающие суммы с полураспадом 1 д укладываются в это окно. Так распределения признаков одинаковы на всех якорях начиная с 15.10, где история уже полная, а стоимость не растёт вместе с историей. Окна 21–30d из черновика сокращены: на октябрьских train-якорях они были обрезаны, а на ноябрьских val/test — полными, это прямой train/test-перекос. Исключений два, и оба — определения, а не статистики:
   - `pair_first` (новизна пары) смотрит на всю историю, потому что так определён сам таргет;
   - статические атрибуты товара `item_static` (category_id и бренд as-of).
3. **Начало train — 15.10.** Это первый якорь, где окно 14d полное (1.10–14.10). Признак «длина доступной истории» не заводится: это календарь.
4. **cp = cart ИЛИ purchase.** Везде, где cart-лог неровный, cart и purchase объединены. У 56% первых покупок (312k из 558k) cart перед ними нет, так что отдельный cart-сигнал теряет половину конверсий. Отдельные cart-признаки остаются только в extra.
5. **NULL** означает «нет основания для сравнения»: у товара нет бренда или цены, пользователь не касался категории. NULL не подменяется ни 0, ни большим числом. **0** означает «основание есть, совпадения нет». В CatBoost используется `nan_mode=Min` без импутации: документация гарантирует, что split «NaN против остальных» рассматривается. Поэтому флаги пропуска, дублирующие NaN, не заводятся.
6. **Детерминизм.** Во всех `row_number` / `arg_max` / топах источников обязателен tie-break по `product_id` (для сессий — по `user_session`). В октябре есть 1 723 пары (user, ts), где у пользователя несколько товаров с одинаковым временем последнего просмотра.
7. **Дубликаты событий.** В events 30 220 полных дубликатов строк. На входе каждого дневного среза делается `SELECT DISTINCT *`, одинаково для признаков и таргета. На таргет это не влияет, потому что он определяется по первым событиям.

Признаки, которые агент нашёл на старой постановке, вошли в baseline:
- брендовая аффинность стала `ub_share_hl1d` (core) и `ub_weight_hl1d` (extra; внутри запроса порядок тот же, что у share, поэтому нужна leave-one-out проверка);
- сессионный CF стал `cf_cv_*`;
- направленный CF «посмотрел A → купил B» стал `cf_tr_*`, теперь только по переходам к новым для пользователя товарам;
- длинная история пары удалена, потому что пары нет.

Закрыты дефекты старого baseline:
- нет давности cart → `u_hours_since_last_cp`, `uc_last_cp_h`;
- нет конверсий → `i_*_lift`, `i_cat_buy_lift_14d`;
- нет бренда → `ub_*`, `i_brand_*`;
- нет цены → `i_log_price`, `i_price_pct_in_cat`, `up_*`;
- нет иерархии category_code → полезен только l1: `i_cat_l1`, `uc_l1_share_hl1d`;
- нет сессий → `u_ls_*`, `uc_ls_*`, сессионный CF.

Час суток не нужен: якорь всегда в 00:00, окно таргета — целые сутки, свежесть даёт `u_hours_since_last_view`. День недели представлен только привычкой пользователя `u_active_same_weekday_last_week` (extra).

**Итог: 76 признаков, из них 35 core.**

**Состав базы (решение 19.10).** Baseline = все признаки, core и extra. Пометка core/extra означает порядок реализации и ожидание по проверкам, а не исключение из базы. Признак убирается только если он заметно замедляет сборку дня или ухудшает NDCG на валидации за пределами доверительного интервала. Вклад групп показывает абляция «полная база минус группа».

### Общие определения

- `t` — якорь, 00:00 UTC. `d` — календарный день UTC. Все дневные rollup берутся по закрытым дням `d < t::date`; это то же самое, что `event_time < t`. Окно признаков: `d ∈ [t::date − 14, t::date)`.
- **Веса затухания:** w(view)=1, w(cart)=3, w(purchase)=10; множитель `0.5^(age_h/24)`; события из [t−14d, t).
- **`item_static`** — атрибуты товара, не являющиеся статистикой:
  - `category_id` — единственный у товара (проверено);
  - `l1 = split_part(category_code,'.',1)` по карте category_id → code; у каждой category_id не больше одного code, смешанных NULL/не-NULL нет;
  - `brand_asof(p, d)` — последний не-NULL бренд товара по событиям дней ≤ d. Хранится как маленькая SCD-таблица `(product_id, brand, valid_from_d)` и дописывается при закрытии дня. Нужна потому, что бренд на уровне событий несогласован: у 7 606 товаров он в одних событиях NULL, в других заполнен, у 137 товаров два разных бренда. **И R4, и бренд кандидата берут бренд только отсюда**, бренд из строки события не используется.
- **`item_attr_t`** — атрибуты товара на момент t:
  - `category_id`, `l1` из `item_static`;
  - `brand = brand_asof(p, t::date − 1)`;
  - `price` — последняя положительная цена до t по `item_day.price_last` за [t−14d, t) (tie-break по product_id не нужен: ключ — товар); цена ≤0 считается отсутствующей;
  - `pct` — `percent_rank` цены внутри category_id среди товаров с ценой за [t−14d, t); NULL, если в категории меньше 5 товаров с ценой.
- **`rv(u)`** — различные товары, которые u просматривал в [t−14d, t). Поля: `last_ts`, `k` (1 — самый свежий; `ORDER BY last_ts DESC, product_id`), `price_seen` (цена при последнем просмотре; `arg_max(price, (event_time, price))`). Атрибуты берутся из `item_attr_t`. **`rec(u)`** — `rv` с `k ≤ 10`.
- **`ls(u)`** — последняя сессия. Выбирается как `arg_max(user_session, (event_time, user_session))` по событиям u в [t−48h, t). В неё входят **все** события этой сессии с `event_time ∈ [t−14d, t)`, в том числе раньше t−48h: в октябре 10 540 сессий длиннее 48h.
- **Приобретение (acquisition)** — единое определение «прошлого таргета» для признаков. Это пара (u, p), у которой первый cp `first_cp_ts` приходится на тот же UTC-день, что и первое касание `first_ts`. Считается только через `pair_first_at(t)` (§3.5).
- **Lift со сглаживанием:** `((x + m·p0)/(n + m))/p0`, где `p0 = Σx/Σn` по **всем** товарам за то же окно. Без данных значение равно 1: «неизвестно, то есть как в среднем».

## 2. Признаки по группам

Почти все цифры в колонке «зачем» — средний AUC внутри запроса (qAUC) или pooled AUC на прокси-кандидатах (раздел 6). Это проверка одиночного сигнала, а не прирост NDCG. **Большинство чисел замерено на прежних окнах (rv 30d, cov 21d, uc_last 30d) и прежнем определении переходов.** После перехода на 14d их нужно перемерить (§6.4).

### 2.3 Товар (`i_`) — 22 признака (7 core)

### 2.7 Item-item CF от недавних товаров (`cf_`) — 8 признаков (5 core; после §6.3e `cf_cv_cos_max` в core, `cf_cv_cos_same_cat_max` в extra)

Определения (все окна внутри L = 14d):
- `rec(u)` — 10 последних различных просмотренных товаров A (`rv` с k ≤ 10, tie-break по product_id).
- **Совместный просмотр** строится по сессиям из [t−14d, t) с 2..50 различными товарами (сессии, пересекающие t−14d или t, берутся частью внутри окна). `n_ab` — число сессий с A и B; связи с `n_ab ≥ 2`. `n_a` — число сессий (любых) с просмотром A.
- **Переходы** строятся только к приобретениям: пары (user, B) из `pair_first_at(t)` с `first_cp_ts = tc ∈ [t−14d, t)` и `first_ts::date = tc::date`. Повторные покупки и cp ранее тронутых товаров не учитываются, потому что они не похожи на таргет. Для каждого приобретения берутся до 20 последних просмотров других товаров в [max(tc−3d, t−14d), tc) (tie-break по product_id). `n_users(A→B)` — число таких пользователей. `nv(A)` — distinct зрители A за [t−14d, t). `nc(B)` — distinct приобретатели B за [t−14d, t). `N` — distinct зрители любых товаров за [t−14d, t).

## 3. Реализация

### 3.1 Хранение истории

- Таблица `hist` упорядочена по `event_time`. Проверено: в october.duckdb `events` 3 инверсии на 42.45M строк, zone maps отсекают окно, скан 30d с SEMI JOIN на 5k пользователей занимает 0.06 с.
- **Ноябрь дописывается `INSERT … SELECT … ORDER BY event_time`** (или parquet по дням), но не отдельной таблицей через UNION. После загрузки проверить min/max `event_time` по row group в `pragma_storage_info` и время скана окна на якоре 24.11.
- Исходную базу открывать только READ_ONLY. Rollup писать в отдельный файл вне репозитория.
- На входе каждого дневного среза — `SELECT DISTINCT *` (политика дубликатов из §1).

### 3.2 Дневные rollup

Каждый rollup строится один раз на закрытый день d, инкрементален и дописывается в порядке d.

### 3.3 Таблицы, строящиеся на каждый якорь

1. `q`, `cand` — запросы и кандидаты с рангами источников (`s_*`), топы с tie-break по product_id.
2. `item_attr_t` — по R3 за [t−14d, t) и `item_static`; `percent_rank` цены внутри category_id.
3. `glob` — глобальные нормировщики окон: Σ actors_7d, p0 для всех lift, g для `u_brand_explore_rate_14d`, N. Считаются **по всем товарам и пользователям**, а не по кандидатам или запросам.
4. `uev` — один проход по сырым событиям пользователей из `q` за [t−14d, t) через SEMI JOIN. Из него получаются `rv`, `ls`, `u_log_price_med_view_7d`.
5. `cov`, `ns`, `nb` — совместные просмотры за 14d с фильтрами a ∈ rec, b ∈ cand, n_ab ≥ 2. Ранги `nb` считаются по полному списку соседей a, до фильтра по b.
6. `acq` — приобретения за 14d из `pair_first_at(t)`. `tr`, `nv`, `nc` — item-level переходы. `trc` — category-level переходы для `uc_trans_lift_max` (та же выборка пар, агрегированная по category_id).

### 3.5 SQL-наброски (только для неочевидных мест)

**As-of доступ к R2 — единственный разрешённый.** Сырые `pair_touch` / `pair_cp` потребителям не видны.

```sql
CREATE MACRO pair_first_at(t) AS TABLE
  SELECT pt.user_id, pt.product_id, pt.first_ts,
         pc.first_cp_ts                         -- NULL, если cp не было до t
  FROM pair_touch pt
  LEFT JOIN (SELECT * FROM pair_cp WHERE first_cp_ts < t) pc
         USING (user_id, product_id)
  WHERE pt.first_ts < t;
```

**Затухание из дневного rollup (R4) — точная формула.** Множитель раскладывается так: 0.5^((t − ts)/24h) = 0.5^((t − D_end)/24h) · 0.5^((D_end − ts)/24h). Поскольку t — полночь, (t − D_end) кратно целым суткам. `date − date` в DuckDB даёт BIGINT, так что `pow(0.5, t::date − d − 1)` корректен.

```sql
-- закрытие дня d (D_end = d + 1 day); day_events уже DISTINCT
INSERT INTO user_catbrand_day
SELECT e.user_id, s.category_id, b.brand, d,
  sum(CASE e.event_type WHEN 'view' THEN 1 WHEN 'cart' THEN 3 ELSE 10 END
      * pow(0.5, date_diff('second', e.event_time, D_end) / 86400.0)) AS s_dec,
  count(*) FILTER (WHERE e.event_type = 'view') AS n_view,
  max(e.event_time) AS last_ts,
  max(e.event_time) FILTER (WHERE e.event_type IN ('cart','purchase')) AS last_cp_ts
FROM day_events e
JOIN item_static s USING (product_id)
LEFT JOIN brand_asof(d) b USING (product_id)   -- последний не-NULL бренд по дням <= d
GROUP BY ALL;
-- user_cat_day строится так же без brand и с last_purchase_ts

-- якорь t: читать только пользователей q
SELECT user_id, category_id,
  sum(s_dec * pow(0.5, t::date - d - 1)) AS w
FROM user_cat_day
WHERE d >= t::date - 14 AND d < t::date
  AND user_id IN (SELECT user_id FROM q)
GROUP BY ALL;
-- uc_share_hl1d = w / sum(w) OVER (PARTITION BY user_id)
-- ub_*: sum по brand из user_catbrand_day; знаменатель — тот же sum(w) по user_cat_day
```

**`u_new_item_cp_rate_14d`.**

```sql
SELECT q.user_id,
  COALESCE(x.rate, 0) AS u_new_item_cp_rate_14d
FROM q LEFT JOIN (
  SELECT user_id,
    count(*) FILTER (WHERE first_cp_ts >= t - INTERVAL 14 DAY
                       AND first_ts::date = first_cp_ts::date)
    / (count(*) + 5.0) AS rate
  FROM pair_first_at(t)
  WHERE first_ts >= t - INTERVAL 14 DAY
    AND user_id IN (SELECT user_id FROM q)
  GROUP BY 1) x USING (user_id);
```

**`item_day`, новые и приобретённые пользователи.**

```sql
WITH ud AS (
  SELECT user_id, product_id,
         bool_or(event_type = 'view') v,
         bool_or(event_type = 'cart') c,
         bool_or(event_type = 'purchase') p
  FROM day_events GROUP BY 1, 2)
SELECT product_id, d,
  count(*) FILTER (WHERE v) viewers,
  count(*) FILTER (WHERE c) carters,
  count(*) FILTER (WHERE p) buyers,
  count(*) FILTER (WHERE c OR p) actors,
  count(*) FILTER (WHERE pt.first_ts::date = d) new_users,
  count(*) FILTER (WHERE pt.first_ts::date = d AND (c OR p)) acq_users
FROM ud JOIN pair_touch pt USING (user_id, product_id)
GROUP BY 1;
```

**Последние просмотры `rv`.**

```sql
SELECT user_id, product_id,
  max(event_time) last_ts,
  arg_max(price, (event_time, price)) price_seen,
  row_number() OVER (PARTITION BY user_id
                     ORDER BY max(event_time) DESC, product_id) k
FROM uev                       -- пользователи из q, [t-14d, t)
WHERE event_type = 'view'
GROUP BY 1, 2;
```

**Совместные просмотры и ранги источника 4.**

```sql
sv  := SELECT DISTINCT user_session, product_id
       FROM hist WHERE event_type = 'view' AND event_time >= t - 14d AND event_time < t;

full:= SELECT a.product_id a, b.product_id b, count(*) n_ab

```

**Переходы (item и category).**

```sql
acq := SELECT user_id, product_id b, first_cp_ts tc
       FROM pair_first_at(t)
       WHERE first_cp_ts >= t - 14d AND first_ts::date = first_cp_ts::date;
vw  := первые view (user, product) за [t-14d, t);
```

Единственная растущая таблица — R2. Она читается только через `pair_first_at(t)` с фильтром по `first_ts` (окно 14d) и через join на кандидатов при исключении тронутых товаров. Начальную сборку делать с `ORDER BY first_ts` / `ORDER BY first_cp_ts`, иначе фильтр не отсекается zone maps.

Pair-признаки строятся только для запросов с ≥1 таргетом (~3–6k пользователей в день), а не для всех ~400k активных. Это законно: метрика условная, фильтр только выбирает запросы и не участвует в значениях признаков. Боевой режим на всех активных — отдельная задача (R5).

## 4. Утечки: точные границы

| Таблица / признак | Граница | Комментарий |
|---|---|---|
