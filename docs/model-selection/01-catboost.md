# M01 — сильный CatBoost для purchase ranking

Дата: 15 октября 2026. Независимое исследование; обучение, установка и benchmark не выполнялись. Контекст: [данные](../data.md), [план](../experiment-plan.md), [канонический backlog](../backlog.md). Чужие новые model/loss/candidate/user-item записки не использованы.

## Решение и точная единица

**P0: сравнить CatBoostRanker/PairLogit и CatBoostClassifier/Logloss**, сохранив ручные признаки, queries, кандидатов и временные отсечения. Это уточнение TLAB-008, не новая гипотеза. «Сильный» означает проверенный протокол и содержательные user/item/pair признаки, а не обязательную победу ranking objective.

Строка — `(query_id=(user,t), candidate_item)`, группа — один anchor, не пользователь за весь месяц и не session. Для исследуемого distinct purchase-set `y_qi=1[i∈Y_q]`; `Y_q` строится независимо от candidates. Пока horizon/anchor окончательно не утверждены, используем конфиг, а не зашиваем 24 часа в модель. Все features доступны до `t`; параметры модели обучены до начала её периода применения. Повторная покупка может быть positive, отсутствие impression не позволяет объявлять остальные товары неприязнью.

Обе модели — ансамбль симметричных деревьев, `s(q,i)=Σ_m η·h_m(x_qi)`. Ranker сортирует raw score; classifier сортирует тот же logit, sigmoid монотонен. Для BCE: `L=Σ_q |C_q|⁻¹Σ_i [log(1+exp(s_qi))−y_qi·s_qi]`; веса строк нормируют query mass. Это предложенная постановка [официального Logloss](https://catboost.ai/docs/en/concepts/loss-functions-classification), а не обещание калиброванной вероятности покупки.

Для PairLogit задаём явные пары `(positive,zero-label)` внутри query и `w_pair=1/(|P_q|·|N_q|)`, если оба множества непусты: `L∝Σ_qΣ_(p,n) w_pair log(1+exp(s_qn−s_qp))`. Так большой shortlist или несколько positives не увеличивают массу запроса автоматически. При лимите пар нормировать фактически выбранные пары и описать sampling. [Документация ranking](https://catboost.ai/docs/en/concepts/loss-functions-ranking) подтверждает: PairLogit использует веса пар, не object weights; автогенерация без ограничения берёт все возможные пары. Поэтому `weight=1/|C_q|` для classifier нельзя механически переносить в ranker.

## Категории, IDs и временная безопасность

Исходная [статья Prokhorenkova et al., NeurIPS 2018](https://papers.neurips.cc/paper_files/paper/2018/file/14491b756b3a51daac41c24863285549-Paper.pdf), §§3–5, вводит ordered target statistics и ordered boosting как разные средства против prediction shift. Её перестановочная «история» не равна реальному времени зрелости purchase labels. Случайные permutations не доказывают strict-past; `has_time=True` отключает перестановки, но не вводит embargo по horizon и не гарантирует исключение соседних строк одного query из target statistics. Это инженерный вывод из статьи и [описания параметра](https://catboost.ai/docs/en/references/training-parameters/common), а не заявленная гарантия библиотеки.

Практический P0: ручные числовые counts/recency/shares/support плюс доступные as-of category_id, category_code, brand как categorical, missing отдельным стабильным токеном. IDs не передавать числом с порядковой семантикой. Для этих трёх колонок предложить **явный** `one_hot_max_size=4096`: имеющиеся 624 category IDs, 126 codes и 3445 brands укладываются; проверять cardinality фактического train. Это нативная обработка, без внешней one-hot матрицы и без target CTR для этих колонок. Raw user_id/product_id в P0 исключены. [Официальная документация](https://catboost.ai/docs/en/features/categorical-features) подтверждает отсутствие CTR для one-hot features и различие PairLogit против CPU PairLogitPairwise, где one-hot недоступен. Выбор 4096 — наша проверяемая настройка, не default и не доказательство оптимальности.

**P1:** высококардинальные IDs исследовать отдельно; 3,02 млн users и 166,8 тыс. items не означают достаточный support. Native CTR может запоминать частые items, редко встречающийся user ID — почти prior. `max_ctr_complexity=1` — предложенное ограничение комбинаций; CPU `ctr_leaf_count_limit` сокращает память ценой отбрасывания редких значений, поэтому это ablation, а не безвредная оптимизация. Факты параметров: [CTR settings](https://catboost.ai/docs/en/references/training-parameters/ctr).

## Objectives, edge cases и ресурсы

**P1:** после P0 один `YetiRank:mode=NDCG;top=20;dcg_type=Base;dcg_denominator=LogPosition` на CPU. Это отдельный surrogate, не синоним PairLogit; non-Classic modes CPU-only. **P2:** YetiRankPairwise/GPU — только при измеренном ограничении CPU; [текущая ranking-таблица](https://catboost.ai/docs/en/concepts/loss-functions-ranking) допускает GPU для PairLogit и Classic YetiRank, но не для non-Classic YetiRank.

Пять обязательных случаев: группы contiguous согласно [Pool](https://catboost.ai/docs/en/concepts/python-reference_pool); полностью отрицательная/положительная группа не создаёт пар; positive вне C остаётся miss; незрелый horizon не становится negative; same-second peers получают features до обновления. Нулевые queries сохраняются в evaluation и BCE, а для ranker отдельно учитывается доля queries без сигнала. Встроенный NDCG видит только переданные candidates: выбирать модель внешним evaluator с полным Y/IDCG, conditional и all-query метриками.

Предложение P0: CPU, 2 threads, depth 6, до 500 iterations, learning_rate 0,05, фиксированный seed, Plain; максимум два fit суммарно в лимите TLAB-008 ≤60 минут. Это стартовые settings, не defaults. Сначала ≤100 queries для shape/cost gate; затем прежний label-independent pilot. При 6000×220 строк и 32 float32 колонках только numeric buffer ≈169 MB; Pools, категории, пары и копии добавляются. При 110 positives из 220 возможно 12100 пар/query, поэтому binary targets сами не устраняют квадратичную стоимость. RSS ceiling 8 GB — внешний stop condition: [used_ram_limit](https://catboost.ai/docs/en/references/training-parameters/performance) ограничивает лишь CTR и не является жёстким лимитом процесса. Время не оценено benchmark; полный 42,45 млн event log — источник features, не число training rows.

[Текущая installation page](https://catboost.ai/docs/en/concepts/python-installation) уже описывает 1.2.10, CUDA binaries Windows/Linux и compute capability ≥3.5. Mac M3 — CPU-путь; RTX3070 не считать доступной до отдельной проверки VRAM/driver/package. GPU недетерминирован по [FAQ](https://catboost.ai/docs/en/concepts/faq); hardware и эффективные параметры сохранять в manifest.

## Одна дополнительная гипотеза

**HYP-025, needs-pilot, P1:** замороженный item-only CatBoostClassifier prior с native product_id/category/brand, обученный на labels тех же past-only warmup queries/candidates, зрелых до первого downstream anchor, даёт scalar logit поверх manual features. Механизм — shrinkage/взаимодействия identity и metadata; counter — повторение популярности. Контроль: manual baseline плюс простой сглаженный item-rate, обученный на тех же warmup labels; Здесь rate — доля positive candidate labels, не purchase/view CTR; priors/clipping тоже past-fit. Один upstream и один downstream fit, ≤60 минут/8 GB отдельно после P0; исключить обновление upstream на validation. Accept: backlog gate ΔNDCG20/Recall/cost и сохранение выигрыша вне frequent-item slice; reject при нарушенной maturity, отсутствии достаточных labels или воспроизведении эффекта простым rate. **HYP-026 не создавать:** PairLogit versus BCE уже входит в TLAB-008. Главная развилка — оправдывают ли ID-based priors добавочную сложность сверх строгого ручного baseline.
