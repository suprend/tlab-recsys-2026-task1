# NLP в REES46: минимальный честный эксперимент

Проверено 14 октября 2026 года. Решение: **исследовать перенос интереса между категориями через текст, но начать с иерархии и TF–IDF; BM25 — недорогой дополнительный контроль, а не заранее выбранная основная модель**. Цель предсказания и временные границы пока не утверждены; этот документ не выбирает их за пользователя. Модели не запускались.

## Что реально является текстом

В октябре есть 126 уникальных заполненных `category_code` на 252 `category_id`, 372 ID без кода. Названий/описаний товаров, поисковых запросов и картинок нет. Бренд — короткое имя; сначала полезнее трактовать его как отдельный категориальный атрибут, без предположения, что близость букв означает близость интереса.

Дополнительная read-only проверка полного октября: 41 код имеет два уровня пути, 84 — три, один — четыре; 22 кода содержат `_`; всего 150 уникальных строк уровней. Примеры: `appliances.kitchen.coffee_machine`, `electronics.audio.music_tools.piano`, `country_yard.furniture.hammok`.

Иерархия уже несёт существенную часть доступной семантики. Текстовый подход не различит два товара с одинаковыми категорией и брендом. Наличие 166 тысяч товаров не означает наличие такого числа разных текстовых документов.

## Общий baseline и единица сравнения

Сначала сильный CatBoost с ID пользователя/товара/категории, брендом, доступной ценой и прошлой активностью; отдельные категории верхних уровней и прошлые user–category/user–brand/user–hierarchy агрегаты. Состав ручных признаков фиксируется после выбора target. Если иерархию добавить только новой ветке, прирост нельзя приписать эмбеддингам.

Далее сравнивать **одинаковые user–candidate строки, события истории, окна и маску доступного текста**:

| Ветка | Что добавляем к общему baseline | Проверяемый вопрос |
|---|---|---|
| L | TF–IDF сходство категории кандидата с прошлым профилем пользователя | Достаточны ли общие слова и редкость слов? |
| D | Те же similarity-признаки с MiniLM | Даёт ли предобученная семантика больше совпадения слов? |
| B, дополнительная | BM25 между категорией кандидата и прошлым текстовым профилем | Полезно ли BM25-взвешивание; в варианте history-document — насыщение повторов и нормировка активности? |
| L+D, только после сравнения | Компактные признаки обеих веток | Дополняют ли lexical и dense друг друга? |

E5 — второй encoder при наличии времени, а не обязательная новая ветка до первого результата. Для D отдельные one-hot и случайные векторы назначать **по той же строке кода категории**, а не по category_id или product_id; сравнивать те же агрегаторы и размерность случайных векторов. Это отделяет смысл текста от другого кодирования истории.

На 126 категориях можно один раз рассчитать небольшую таблицу попарных сходств; затем извлекать из прошлой истории mean/max similarity, similarity с последней категорией, а при необходимости взвешенное среднее. Views/carts/purchases разделить одинаково во всех ветках. Пустая история и отсутствие текста — отдельные индикаторы; неизвестный ID не превращается в текст `unknown 2053...`. Для разных ID без текста остаются исходные категориальные признаки baseline.

## Где BM25 содержателен, а где почти совпадение слов

[BM25](https://nlp.stanford.edu/IR-book/html/htmledition/okapi-bm25-a-non-binary-model-1.html) учитывает частоты слов, насыщение повторов и длину документа. В наших путях всего 2–4 уровня и почти нет повторов; поэтому BM25 по отдельным категориям в основном проверит пересечение слов, IDF и небольшую поправку на длину. Это вывод из формы данных, а не доказательство бесполезности метода.

Если BM25 включаем, надо явно выбрать одно направление:

- **Простой вариант:** документ — категория кандидата, запрос — каждая прошлая категория; агрегировать оценки с заранее заданными весами событий/давности. Это обычный category–category lexical контроль, ограниченно использующий свойства BM25.
- **Более содержательный вариант:** документ — профиль пользователя из прошлых категорий, запрос — категория кандидата. Повторные просмотры дают term frequency, `k1` ограничивает их влияние; `b` регулирует влияние длины истории. Corpus, IDF и среднюю длину профиля фиксировать на допустимых прошлых snapshots, не на профилях конца месяца. Правило query term frequency и формулу IDF записать: реализации различаются. Повторный просмотр и точный дубль события не считать одним явлением.

Второй вариант сравнить с обычными частотами и простым насыщением счётчиков. Иначе выигрыш BM25 может означать лишь дополнительную нормировку истории, а не преимущество NLP. Минимальный бюджет — одна заранее заданная пара параметров; если подбирать, небольшая сетка исключительно на validation. Направления не смешивать под одним названием без указания.

BM25 по товарным документам `category + brand` тоже возможен, но IDF тогда зависит от числа товаров в категории/бренде. Это другая гипотеза, не эквивалент 126-документному category corpus. Не использовать 42 миллиона событий как независимые документы: это неявно подмешивает популярность. Без названий товаров не делать BM25 основным retrieval по всему каталогу: одинаковые тексты дают массовые ничьи.

## Токенизация

1. Сохранить исходный код, разобрать точку как границу **уровня иерархии**. Для структурной ветки хранить полный путь и префиксы (`appliances`, `appliances.kitchen`, полный код), а не только мешок слов.
2. Для lexical ветки lowercase, `_` разбить на слова, уровни разделить пробелами. Пример: `appliances.kitchen.coffee_machine` → `appliances kitchen coffee machine`. Полный исходный путь оставить самостоятельным категориальным признаком, не потерять его при очистке.
3. Не удалять произвольные stop words, не исправлять автоматически `hammok`, не добавлять синонимы LLM и не стеммить все бренды. На таком маленьком словаре все 126 строк можно проверить вручную; исправления/словари должны быть версионированы и одинаковы для сравниваемых методов.
4. Для dense encoder использовать его штатный tokenizer после выбранного преобразования пути; lexical tokenizer и subword tokenizer — разные этапы. Проверить отсутствие truncation. Нельзя подать готовые word ID lexical vectorizer вместо текста в pretrained encoder.

[TfidfVectorizer](https://scikit-learn.org/stable/modules/generated/sklearn.feature_extraction.text.TfidfVectorizer.html) по умолчанию отбрасывает односимвольные токены, а `\w` сохраняет underscore. Поэтому явный разбор пути нужен даже при готовой библиотеке. Character n-grams пока низкий приоритет: здесь нет пользовательских опечаток/поисковых запросов, а совпадение частей бренда не доказывает смысловую близость.

## Время, пропуски и контроль

- Все события профиля строго раньше момента прогноза; равные timestamp не упорядочивать случайно. Текущий просмотр, если он доступен по постановке, — отдельный context, не скрытый элемент истории.
- Vocabulary/IDF, средняя длина BM25-профилей, редукция размерности и learned weights строятся на допустимом past corpus. **Fit до конца train не обеспечивает strict-past для ранних строк самого train.** Простой строгий вариант: warmup до первого train-прогноза, vocabulary/IDF/avgdl заморозить; новые слова имеют заранее заданное OOV-правило. Альтернатива — expanding/cutoff snapshots, каждый рассчитан раньше строк, к которым применяется. На validation/test transform; не fit на всём месяце. Для каждого fit записать cutoff и единицу документа. Полные 126 кодов октября — EDA-диагностика, а не автоматически доступный каталог раннего cutoff. Наличие полного внешнего каталога до cutoff можно допустить только явно.
- Названия из следующих месяцев пока кандидаты с подозрительной семантикой: основной опыт использует исходные подтверждённые коды. Поздний словарь — отдельный enrichment-опыт с теми же ID-ветками и заявленной доступностью; не подмена пропусков молча.
- Сообщить качество по всему набору и покрытому текстом подмножеству; сравнивать одинаковые строки. Выигрыш только на заполненных категориях не переносить автоматически на весь трафик. Сегменты интереса: редкая категория, нет точного совпадения категории в истории, новый товар при известной категории.
- Выбор кандидатов и негативов общий; после выбора постановки одна главная метрика. Для ranking дополнительно coverage retrieval, если retrieval вообще менялся; для conversion не добавлять такой этап искусственно. Финальный test не используется для выбора encoder/tokenizer/окна/параметров.

## Связь с заданием T-Lab

TF–IDF/BM25/готовые эмбеддинги сами по себе не являются доказательством автоматизации feature engineering. Они могут стать источниками признаков. Если центральная гипотеза — автоматический выбор/конструирование, потребуется отдельно описать пространство операций (окна, веса событий, агрегаторы), одинаковый search budget и контроль с сильными ручными признаками. Если центральная гипотеза — улучшение ручного бустинга альтернативным методом, решающим будет честный измеренный прирост, а не слово NLP в названии.

Практический первый шаг после target/split — реализовать общий causal history interface и hierarchy+TF–IDF, затем MiniLM с тем же интерфейсом. Это даст интерпретируемую проверку гипотезы до скачивания больших моделей. Behavioral embeddings по product IDs могут быть отдельной полезной веткой, но это представление взаимодействий, не NLP.

Независимое ревью: направление BM25, корпус/IDF, строгая временная доступность и единица сравнения проверены; модели и retrieval не запускались. Согласованные правила токенизации — в [nlp-tokenization.md](nlp-tokenization.md).
