# 04. Категории, бренды и условная цена как источники кандидатов

Дата: 2026-10-15. Независимое исследование, без реализации, обучения и новых измерений. Факты взяты из существующих `docs/data.md`, `docs/features/04-categories/` и `docs/experiments/candidate-pilot.md`; правила ниже — предложения экспериментов.

## Контракт и границы

Текущий baseline сохраняется: top200 по distinct purchase-users за `[t−7d,t)` плюс последние20 distinct товаров пользователя из view/cart/purchase того же окна; union/dedup **без refill**, `|C₀|≤220`. Новый источник требует отдельной версии protocol/manifest. Candidate generation и ranking разделены также в [Covington et al.](https://research.google/pubs/deep-neural-networks-for-youtube-recommendations/); это архитектурное основание, не доказательство полезности данного источника.

Query — уже зафиксированный `(u,t)` из Q; полный target Y и eligibility не меняются. Все peers секунды t исключены. `U(t)` содержит ранее наблюдавшиеся товары; это proxy известного ассортимента, без сведений о stock. Покупки вне U/C остаются misses. Гранулярность результата — уникальная `(query,product_id)` с source flags, rank, snapshot и supports. Будущие labels генератор не читает.

624 category_id, 126 текстовых code и 372 никогда не именованных ID — разные сущности. ID остаются самостоятельными ключами; numeric order используется только для ties. Один readable path может соответствовать нескольким ID. Missing code не запрещает ID-retrieval; missing brand не создаёт общий «бренд». Названий, описаний, изображений и восстановленных поздних метаданных не придумываем.

Историческая категория/бренд принадлежат событию. Кандидату назначается последнее непротиворечивое состояние `<t`; нельзя переклеивать всю историю текущими атрибутами. Конфликт последних metadata в одной секунде делает соответствующее поле ambiguous. Категорийная неизменность октября не разрешает будущий lookup. Официальный [DuckDB ASOF](https://duckdb.org/docs/current/sql/query_syntax/from#as-of-joins) допускает строгое `>` и LEFT-соединение с отсутствующим состоянием; выбор политики конфликтов остаётся нашим.

## P0: популярность внутри персональных ID

Для каждого distinct товара, просмотренного u в `[t−7d,t)`, берём последний view с event-time категорией. `h_uc` — число таких товаров категории c; `a_uc=h_uc/Σc h_uc`. Support — числитель, знаменатель, наблюдаемая длина окна. При знаменателе0 affinity missing; наблюдаемый0 не означает dislike. Выбираем top3 ID по `h_uc DESC`, последнему view DESC, ID ASC.

`P_i(t)=|{v:purchase(v,i,s),t−7d≤s<t}|`: distinct покупатель голосует за товар однажды. Для каждой выбранной c ранжируем товары U с **as-of** категорией c по `P_i DESC, product_id ASC`; P=0 означает отсутствие наблюдавшихся покупателей. Начальное предложение: `popular140 + recent20 + category(3×20)`, максимум220 до dedup, без добора. Пустая/короткая категория оставляет меньше кандидатов. Отсутствие user-view истории оставляет140+recent20; никакой скрытой замены на будущую категорию. Отдельный явно версионированный fallback-контроль может возвращать global-квоту, но не смешивается с основным опытом.

Покупательскую популярность материализуем один раз на уникальный anchor t; для daily Q это дневные snapshots с точным окном, не произвольная календарная сумма. Membership товара в c берём на том же cutoff. Такой источник ищет новые user–item пары внутри знакомой категории и может проиграть глобальному head; repeats не исключаем.

## P1: бренд, иерархия, цена

Бренды проверять отдельной заменой20 category-слотов: top2 пары `(c,b)` среди выбранных ID, по distinct past-view товарам; до10 товаров на пару по P, ties по последнему view и ключам. Support<2 — ветвь не активируется. Это инженерный порог, не найденный optimum. Missing brand оставляет ID-ветвь. Глобальный бренд через все категории — отдельная sensitivity: производитель электроники не задаёт взаимозаменяемость товаров.

Иерархия: отдельная замена20 слотов популярностью по полному code либо root-prefix, без объединения unnamed ID. Префиксы сохраняют namespace и точки; underscore не превращается в новый уровень. [DHAN](https://arxiv.org/abs/2005.12981) исследует иерархию интереса, но его CTR-результаты не подтверждают purchase-retrieval здесь. Квоты, например ≤10 на ID и ≤20 на root внутри этой ветви, ограничивают концентрацию; это предложение. Разнообразие измеряем рядом с Recall, не считаем его автоматическим улучшением. [Goldstein–Carbonell](https://aclanthology.org/X98-1025/) рассматривают баланс релевантности и избыточности; MMR или learned diversity остаются P2.

Цена: в c референс `m_c` — медиана последних положительных цен distinct товаров, наблюдавшихся за7d, с as-of membership; минимум20 товаров. `r_i=ln(p_i/m_c)`. Для u берём минимум3 distinct past-view товара c с положительной event-price и `r_uc=median ln(p_event/m_c)`. Среди top100 P внутри c выбираем20 по `|r_i−r_uc| ASC`, затем P DESC и ID ASC; кандидаты без положительной as-of цены идут последними по P. Общий m здесь сокращается в расстоянии: нормализация не создаёт дополнительной персонализации. Нет m/user-support — обычный P-порядок той же квоты с fallback flag. Нулевые цены сохраняются как anomaly, не как бесплатный сегмент. Это наблюдаемый диапазон, не willingness-to-pay; ограничение top100 нужно считать частью источника.

## Стоимость, проверки и контролируемые гипотезы

Sparse `(u,c)`/`(u,c,b)` профили и topL postings не требуют user×catalog. Скан событий, distinct-buyer state, as-of metadata, сортировки и ценовые snapshots оплачиваются отдельно. Pilot ceiling: прежние Q, ≤30мин/6GB RSS, без fits; время не измерено. Проверки: два ID с одним code; unnamed ID; конфликт/смена brand и нулевая цена; первый пользователь/тонкое окно; событие ровно t−7d/t и добавление future suffix. Хранить source overlap, фактический размер C и долю fallback.

**HYP-053, needs-pilot:** category-квота улучшает all-target retrieval Recall относительно C₀ при том же максимальном бюджете. Контргипотеза — потеря global head и эффект размера. В контроле C₀ заменяемые60 слотов — именно global ranks141–200, не повторный top60. Сравнить C₀ с category-версией при одинаковой no-refill политике; дополнительно Recall-кривые по одинаковому фактическому M с заранее заданным round-robin источников. При user-bootstrap95% CI ΔRecall>0 и соблюдении ceiling — accepted-for-next-stage; CI<0 — rejected, иначе needs-pilot. Отдельно new-pair, unnamed, low-support и zero-purchase queries.

**HYP-054, needs-pilot:** ценовой порядок при неизменных категориях/квотах повышает retrieval Recall сверх P-порядка. Один парный опыт, те же gates; HYP-029 уже покрывает conditional-price **ranker features на fixed C**, поэтому его не повторяем. Downstream NDCG/Recall оцениваются затем одним замороженным ranker с pool-independent features; для feature-ablation C фиксируется отдельно. Рост retrieval не приписывается качеству новых признаков.
