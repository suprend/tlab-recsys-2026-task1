# RECENT/REPEAT: прямые кандидаты из истории пользователя

Дата: 14 октября 2026. Независимое исследование; реализации, обучения и измерений на данных не проводилось. HYP039/HYP040 не переиспользуются; новые номера гипотез не назначаются.

## Факты и границы переноса исследований

Текущий реализованный контроль — top-200 товаров по числу distinct покупателей за 7 дней плюс последние 20 distinct товаров пользователя по всем событиям за 7 дней; после пересечений нет refill, купленные товары сохраняются. Fixed-clock anchors пока предварительны. Это исходная точка, не предложение автоматически изменить pipeline.

RepeatNet различает рекомендацию товара из истории и нового товара, однако использует клики как основной пример. Его результаты обосновывают проверку прямого повторного интереса, но не доказывают полезность повторных покупок для October REES46. [Первичная статья RepeatNet](https://irlab.science.uva.nl/wp-content/papercite-data/pdf/ren-repeatnet-2019.pdf). Сравнение session-based алгоритмов показывает конкурентоспособность простых эвристик и оценивает постепенно раскрываемый префикс сессии; это иной протокол, чем покупки после fixed-clock query. [Ludewig et al.](https://arxiv.org/html/1910.12781v1).

TARS моделирует повторяемость покупок по корзинам; постановка предполагает историю транзакций и заданное время следующей транзакции. Здесь нет orderID, а время будущей покупки неизвестно. Поэтому переносить TARS буквально или называть интервалы между purchase-строками replenishment cycles нельзя. [Guidotti et al., определения задачи и TARS](https://iris.cnr.it/retrieve/f06d0e7a-0b7b-4e8e-a148-c85f4d17ce9f/prod_397162-doc_137471.pdf).

## Контракт истории и прямые правила

Query имеет grain `(user_id, t)`, время UTC. Для типа события `a`:

`E_a(u,t,W) = {e: e.user=u, e.type=a, max(Oct1,t-W) <= e.time < t}`;

`L_a(u,i,t,W) = max{e.time: e in E_a, e.product=i}`;

`R_a(u,t,W,b) = первые b distinct product_id по убыванию L_a`.

Пустой максимум — missing; отсутствующий товар не получает фиктивное время. Окно rolling, не календарные дни. При одинаковом последнем timestamp использовать воспроизводимый технический tie-break по ID, не интерпретировать ID как порядок действий. Вся группа событий с временем `t` исключена до прогноза. Product grain обеспечивает, что двадцать просмотров одного SKU занимают один слот. Источник включает лишь наблюдавшиеся до query товары: это known-catalog proxy, не доказательство наличия на складе.

**P0 — минимальная диагностика без смены контроля.** На одинаковых queries отдельно вывести direct-history baselines `R_view(...,7d,20)`, `R_cart(...,7d,20)`, `R_purchase(...,7d,20)` и текущий `R_all(...,7d,20)`. Покупка из `R_view` — возврат к просмотренному, из `R_purchase` — наблюдаемый повтор купленного SKU; эти группы пересекаются. Direct-purchase baseline не надо именовать replenishment model. Отдельно считать долю целевых distinct товаров, встречавшихся ранее в каждом типе истории, с разбивкой по давности. Это измеряет потенциальный потолок каждого источника, а не рекомендационный эффект.

**P1 — конкурирующие замены ровно исторического источника.** Один вариант оставляет окно 7d, но распределяет 20 исходных слотов как cart-8, view-8, purchase-4, затем union/dedup без refill. Квоты — проверяемый пример, не оптимум. Другой вариант меняет только окно purchase-истории на всю доступную October-историю; отсутствие ранних событий не означает отсутствия покупок до October. Не менять одновременно типовые квоты, окно, refill и cooldown: иначе причину прироста установить нельзя. Глобальный popular-200 сохраняется.

**P1 — повторный интерес как альтернативное упорядочивание.** Для view-истории определить единицу поддержки `(u,i,user_session)` с последним view-временем `s`; session key обязательно включает пользователя. Предложенный безразмерный score:

`S_view(u,i,t) = sum_sessions exp(-(t-s)/tau)`, `tau=86400 секунд`, `s in [t-7d,t)`.

Это сессионная поддержка с decay, не число покупок и не вероятность. Сравнить top-20 по `S_view` с top-20 по последнему view при том же входном множестве. Missing session учитывается отдельной пометкой и одним contribution на `(u,i,UTC-date)`; это инженерная условность, требующая отдельной проверки.

**P2 — cooldown.** Только после измерения purchase-repeat support проверить category-dependent понижение, например умножение repeat-score на `min(1, age_purchase/c_category)`, где age и `c_category` измеряются в днях. Порог выбирается до теста; неизвестная категория получает множитель 1. Жёсткое удаление купленного SKU исключает реальные повторные targets и не является default. У 31-дневного окна недостаточно основания для годовой сезонности.

## Контекст, стоимость и пограничные случаи

Fixed-clock query не знает «текущую» сессию. Можно использовать только последнюю наблюдавшуюся сессию с возрастом, не склеивать её с будущей; missing current context означает отсутствие session-source. Для явно наблюдаемого session-prefix нужен отдельный anchor-контракт, без подмешивания первого товара из будущей сессии.

Материализация: последовательный проход событий с TTL-очередями, таблицей последнего времени `(u,i,type)` и ограниченными списками distinct SKU. При готовой сортировке проход порядка `O(E)`; выдача bounded списков порядка `O(b)` при поддерживаемом индексе. Полная TTL-структура зависит от числа активных user-item пар, а не только от `users×20`; память и задержку необходимо измерить. Session-score требует дополнительных пар и expiration state, поэтому ниже простого recent по приоритету.

Проверить пять случаев: точные дубли не создают дополнительную поддержку; cart без purchase не означает актуальную корзину, поскольку remove-событий нет; same-second события не получают выдуманный порядок; sparse/OOV пользователь возвращает пустой personal-source и сохраняет популярность; пересечения источников сокращают фактический размер pool, который обязательно публикуется.

## Контролируемая оценка

Сначала измерять retrieval Recall относительно всех mature targets, marginal coverage сверх popular-200, repeat/new slices, фактический размер pool и стоимость. Queries с нулём покупок не удаляются из операционной аудитории; Recall для них отдельно undefined. Cold targets остаются misses. При сравнении источников одинаковы queries, horizon, ground truth, лимиты и ranker-рецепт; показывать также сравнение на сопоставимых фактических размерах pool. Для абляции ranker-признаков candidate pool фиксируется буквально: добавление recency/count features не получает заслугу за новое retrieval coverage. Полезность источника подтверждают downstream top-K и независимый временной test, а не только высокая доля повторных кликов.
