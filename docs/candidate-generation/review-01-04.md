## Существенные исправления перед execution

**1. Latest bucket нельзя заменить older-clean backoff.** В04 «последнее непротиворечивое состояние» допускает поиск более старой удобной строки, хотя следующее предложение требует ambiguity. Зафиксировать единый вариант: выбрать последний глобальный timestamp `<t`, затем разобрать **все** значения соответствующего поля этой секунды. `{c,c}` известно; `{NULL}` missing; `{c,NULL}`/`{c,d}` ambiguous. Не откатываться к предыдущему clean state. То же правило нужно brand/price и одинаково всем branches. Старая positive price при новой zero/conflicting price не становится текущей молча. [DuckDB ASOF](https://duckdb.org/docs/current/sql/query_syntax/from#as-of-joins) обеспечивает temporal nearest match, но не является нашим conflict resolver.

В04 user-category profile «последний view каждого distinct товара» тоже требует bucket resolution. При двух разных event-category IDs на последней view-секунде row-order choice недопустим. Предлагаю исключить такой товар из known-category profile, сохранить support/coverage и missing flag; это proposal. Исторический category ID события не переклассифицируется latest-global metadata кандидата. Membership источника и event-grain счётчик необходимо называть раздельно.

**2. Category/cohort нормировка требует точной области вывода.** В02 HYP-032 отвергнут верно **для независимых per-category rankings при неизменных квотах**: общий положительный denominator категории не меняет порядок её товаров. Это не доказательство, что `D_i/N_category(i)` никогда не меняет global ranking: при слиянии категорий denominators разные. Тогда меняется cross-category allocation, и это другой опыт. При нулевом denominator нормировку вообще не вычислять.

Если условные shares вернутся в исследование, numerator/denominator должны использовать одну membership policy. Нельзя делить all-history popularity товара с нынешней категорией B на аудиторию только historical event-category B и назвать это вложенной долей. Допустимы historical-event counts либо current-membership snapshot по доступному прошлому, но это разные estimands; второй сам по себе не temporal leak. Для первого category move не переносит A-events в B. В текущий MVP сглаживание этих shares не требуется.

**3. Price-гипотеза не получает пользу нормировки, которая сокращается.** В04 при общем `m_c>0`:

`|ln(p_i/m_c)−median_j ln(p_j/m_c)| = |ln p_i−median_j ln p_j|`.

Следовательно, HYP-054 проверяет близость к историческому price-profile внутри top100 popularity, а не эффект category reference. Support≥20 для `m_c` меняет activation/fallback coverage, но не порядок активной ветви; его нельзя считать независимой семантической информацией. Нужен один reference price на distinct historical product, например последняя допустимая positive event-price в его view bucket. Иначе «минимум3 distinct товара» сочетается с event-weighted median и активный SKU скрыто получает несколько голосов. Missing/zero/conflicting candidate price — отдельные flags; fallback сохраняет ту же source quota. Выбор positive-history policy объявить заранее.

**4. Equal maximum quota не равна equal actual budget.** Все четыре notes правильно требуют overlap/dedup и full Y, но execution contract должен фиксировать source order, rank ties, ownership duplicate и no-refill. У HYP-031 `170global+30trend+20recent` может оказаться намного меньше C₀; у HYP-053 слабая category history оставляет только140 global. Это допустимая продуктовая политика, но эффект включает underfill. Показать native-policy результат и дополнительно paired Recall-кривые на одинаковых заранее выбранных фактических M. Нельзя подбирать M или refill по попаданиям вY. Control replacement — global ranks171–200 либо141–200, а не повторный top30/top60.

## Разрешение гипотез и дубликатов

**HYP-023 — needs-pilot, diagnostic family; не дубликат HYP-004.** Он проверяет чувствительность frozen scorer comparison к C/U, а не добавление recent coverage. Formula/FP32 memory arithmetic01 согласованы; exhaustive dot, arbitrary CatBoost pair-scoring и ANN-quality разделены правильно. [Faiss](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances) подтверждает различие inner product/cosine: query norm не меняет IP-порядок, item norms могут менять. Exact dot требует vectors support и fit/available_at; это не бесплатная замена ручному boosting.

До опыта задать estimand `Δ_U−Δ_C`, paired user draws на одних Q и equivalence margin. Sign reversal с обоими CI вне0 — достаточное сильное свидетельство, но отсутствие reversal не означает эквивалентность. У100 label-blind queries может не хватить positive users; при undefined/широком CI — needs-pilot, без выбора будущих покупателей. Для fixed popularity, если global top20 входят в top200 источника, full-U и C top20 **тождественны**: использовать это как sanity control, не расходовать fit. Full CatBoost audit deferred до замороженного сильного scorer и cost gate.

**HYP-031 — одна needs-pilot запись.** Сглаженный log-ratio корректен как изменение доли buyers товара между непересекающимися окнами; multi-item buyers не делают сумму долей распределением. Distinct B считается непосредственно, не `distinct7d−distinct1d`. [PARE](https://arxiv.org/html/2308.08799v1) действительно сравнивает recent TopPop, но с месячными окнами; предложенные сутки/час,50,3 и50 — собственные константы notes. Три declared variants делят общий30-minute budget; hourly branch остаётся deferred diagnostic, не дополнительный скрытый search.

**HYP-032 — rejected только normalization-only case.** Его содержательный P2-вариант category quota объединить с **HYP-053**, сохранив источники и различия параметров:02 предлагает40 slots/top4 categories из последних20 all-event items,04 —60 slots/top3 из distinct views7d. Это конкурирующие configurations одной family, не два независимых достижения и не бесплатная сетка. Для первого screening выбрать один profile/quota до labels; возможные последующие варианты оплачиваются общим ledger.

**HYP-053 — needs-pilot после metadata/profile уточнения; HYP-054 — отдельная условная needs-pilot после неё.** Последняя сравнивает только price-order против P-order на тех же categories/quotas/top100. Это не повтор [HYP-029](../features/09-user-item/04-interest-profile.md) ranker-price features на fixed C: там двухканальные view/purchase distribution gaps, здесь меняется retrieval set. Recent/repeat 03 — refinements существующего direct-history источника: cart8/view8/purchase4, full-prefix purchase и session-decay проверяются по одному. Новые HYP IDs этим review не назначаются. Cooldown/replenishment и learned session policy — deferred: отсутствие orderID не позволяет назвать purchase-row интервалы циклами пополнения. [RepeatNet](https://irlab.science.uva.nl/wp-content/papercite-data/pdf/ren-repeatnet-2019.pdf) подтверждает repeat/explore session setting, не fixed-clock purchase lift.

## Принятый MVP и обязательные gates

Текущий accepted004 остаётся неизменным: purchase-distinct-user top200 + all-event recent20, union/no-refill, U по любому строгому прошлому событию. Новый источник — отдельный manifest/config. Primary retrieval metric заранее назвать micro либо positive-query macro; публиковать оба, full-Y/cold misses, source marginal coverage, actual C size, zero-purchase population, repeat/new/support/day slices. [Target review](../target-research/review-05-08.md) сохраняет полный Y для IDCG; [Krichene–Rendle](https://research.google/pubs/on-sampled-metrics-for-item-recommendation/) поддерживают осторожность к item-sampled ranking, но не доказывают любую пользу exact retrieval здесь.

Перед pilot: hand fixtures для boundaries/NULL mixtures/category moves/distinct expiry/source overlap; independent bounded oracle; suffix/peer invariance C при отдельно меняющемся Y; accepted input/output fingerprints, fitted-state availability; measured scan/state/RSS/spill/deadline с partial failure. Existing development data дают screening, не подтверждение победы после поиска. Разные пороги принятия02/04 заранее привести к одному prospective estimand/минимальному полезному Δ, сохранив родные предложения в appendix. Candidate branch не вытесняет основной task1: хорошо настроенный ручной boosting и проверяемая автоматизация features остаются обязательным сравнением, retrieval experiments получают ограниченный бюджет.
