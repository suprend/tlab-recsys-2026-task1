# Exact reference: полный prior-observed каталог

Дата: 15 октября 2026. Независимое исследование; purchase ranking — предпочтительная, но ещё не утверждённая постановка. Предполагаемое место публикации: `docs/candidate-generation/01-exact-reference.md`.

## Что считать эталоном

**Факты.** В октябрьском EDA 166 794 товара; это итог месяца, не доступный ранним запросам каталог. Нет stock, даты размещения, показов рекомендаций или регистраций. [Описание данных](../data.md) и [авторская карточка REES46](https://www.kaggle.com/datasets/mkechinov/ecommerce-behavior-data-from-multi-category-store) не позволяют восстановить настоящий продаваемый ассортимент. Поэтому exact reference устраняет усечение поиска, но не создаёт oracle качества рекомендаций.

**Предложение.** Для запроса `q=(u,t)` определить `U(t)={i: first_observed_event(i)<t}` по всем view/cart/purchase. Это proxy известного каталога; grain — уникальный product_id. Полный baseline получает `C(q)=U(t)` без удаления прошлых покупок. Пользовательская eligibility определяется только прошлым, например наличием события в `[t−7d,t)` на фиксированной UTC сетке; 7d и сетка требуют утверждения. Нельзя выбирать только будущих покупателей. Target `Y(q)` строится независимо от U/C, например distinct purchases `[t,t+H)` при зрелом горизонте; H и правило границ provisional.

Snapshot содержит first-observed, последние доступные свойства и статистики с временем `<t`; все события секунды t обрабатываются после запроса. Дневной snapshot недостаточен для внутридневных anchors без delta replay. Fitted vectors/weights/priors доступны до соответствующего prediction; fit на конце train неприемлем для его ранних строк. На validation/test отдельно фиксируются freeze параметров и refresh истории. Позднее известный товар не включается задним числом.

## Exact dot против полного CatBoost

Если совместимые user/item-векторы уже получены допустимым past-only способом, правило retrieval: `C_M(q)=TopM_{i∈U(t)∩V(t)} p_u(t)ᵀv_i`, где V — support векторного представления. Пример исследовательских бюджетов M=200/1000, затем downstream top20; это предложения, не оптимум. Tie-break — фиксированный product_id, без числовой семантики ID. Inner product и cosine — разные scorer: нормировка item-векторов меняет ранжирование; cosine требует нормировки обеих сторон. [Faiss MetricType](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances) описывает это различие; [IndexFlatIP](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes) выполняет exhaustive поиск и хранит 4d байт на float32-вектор.

**Инженерные оценки, не benchmarks.** При N=166 794 item-матрица занимает около 40,7/81,4/162,9 MiB для d=64/128/256. При B=128 полная float32 score-матрица — ещё 81,4 MiB, плюс workspace, IDs, копии и история. Для 2000 запросов, d=128: около 42,7 млрд multiply-add; это не обещание latency на Mac/Windows. Хранить весь Q×N не нужно: батчи запросов, блоки товаров и merge текущего topM дают exhaustive результат с ограниченной памятью. Такой blockwise merge прямо описан в [официальном brute-force руководстве Faiss](https://github.com/facebookresearch/faiss/wiki/Brute-force-search-without-an-index). Сам Faiss для MVP необязателен; доступность конкретных ускорителей здесь не проверялась.

CatBoost-allitems требует `f(u,i,t)` для каждой пары и применения деревьев; arbitrary pair-features не превращаются автоматически в один dot-product. [CatBoost predict](https://catboost.ai/docs/en/concepts/python-reference_catboost_predict) требует все использованные моделью признаки. При 2000×166 794 получаем 333,6 млн строк: только 18 float32 колонок — около 22,4 GiB без служебных объектов. Поэтому полный materialization противоречит разумному запасу RAM на 32 GB. Потоковое построение, broadcast user/item частей и sparse lookup pair-history уменьшают peak, но не число скорингов. Полный CatBoost допустим как небольшой audit, а не объявляется невозможным или быстрым без замера.

## Метрики и опорные сравнения

Для непустого Y публиковать `coverage_U=|Y∩U|/|Y|`, `coverage_V=|Y∩U∩V|/|Y|`, candidate Recall@M и финальные Recall/NDCG@20. All-target denominator сохраняет cold-target misses; in-support результаты идут отдельно. IDCG вычисляется по полному Y, без удаления недоступных целей. ANNRecall относительно exact topM измеряет поиск соседей; он не равен Recall будущих покупок. Для Y=∅ отдельно показывать долю запросов и заранее объявленную zero-policy; условная метрика покупателей не меняет операционную eligibility.

При ограничении вычислений выбирать hash-sample запросов до чтения labels, сохранять весь U внутри запроса, общий sample и веса для сравниваемых моделей. Это даёт sampling uncertainty, а не подмену catalog ranking. Сэмплирование items изменяет ранги: Krichene–Rendle показывают возможную перестановку сравниваемых методов даже в ожидании. [Первичная статья KDD 2020](https://research.google/pubs/on-sampled-metrics-for-item-recommendation/). Полный каталог остаётся наблюдательным эталоном, не причинной оценкой recommendation lift.

P0: полный popularity/last-view/recent-distinct scorer и coverage U на одинаковых Q/Y; shortlisted baseline из [backlog](../backlog.md) сохраняется. P1: exact dot при наличии валидных vectors; ablation dot→cosine меняет scorer, exact→ANN при том же scorer проверяет индекс. P1 audit полного CatBoost отделяет эффект C от feature ablation, где C обязательно фиксирован.

## Граничные случаи и гипотеза

Пять обязательных случаев: U пуст; история пользователя/вектор нулевые; известный после fit item без embedding; цель впервые появляется в секунду t; ties/конфликтующие свойства последней секунды. Конфликтующие свойства помечать ambiguity/missing, не выбирать произвольную строку; нулевой вектор не нормировать. Missing brand/code не исключает item; для OOV/низкого support нужны явные flags и past-popular fallback с отдельным provenance. Если fallback исчерпан, вернуть меньше M, измерить недобор. Нулевую цену сохранить с флагом; повторные покупки допустимы.

**HYP-023, needs-pilot: exact audit выявляет существенную чувствительность выводов к shortlist.** Механизм: C одновременно исключает distractors и позитивы. Counter: shortlist достаточно покрывает цели и сохраняет сравнение. Novelty относительно backlog — проверка полного scorer-пространства, не повтор HYP-004 про recent coverage. Inputs: два уже замороженных scorer, одинаковые Q/U/Y, pool-independent features. Baseline: их сравнение на фиксированном C≤220; эксперимент — те же scorer на полном U для 100 label-blind sampled validation queries. Предлагаемый cap: 30 минут, RSS≤6 GB, без fits; превышение означает deferred, не частичную метрику. Accept: противоположные знаки парной ΔNDCG20 на C/U, обе user-clustered 95% CI вне нуля; reject при CI разности этих Δ внутри ±0,002, иначе needs-pilot. Дополнительно Recall20, coverage и cost. HYP-024 не создаётся: отдельная идея не нужна. Переносимость — аудит любого двухэтапного pipeline, не доказательство улучшения модели.
