# ARGUS и общее пространство пользователя и товара

Проверено 14 октября 2026 года. Исследование первичных источников; обучение и установка моделей не выполнялись.

## Вывод для проекта

Да: можно обучить `u_t = UserEncoder(history before t)` и `v_i = ItemEncoder(item)` с выходами в `R^d`, затем использовать `score(u_t, i) = dot(u_t, v_i)`. Одинаковой размерности недостаточно: совместный recommendation-loss должен сделать этот score полезным для выбранной цели. Независимые векторы длины 128 не становятся согласованными автоматически. Score также не является калиброванной вероятностью покупки.

## Что подтверждено про исходный ARGUS

- История — упорядоченные `(context, item, feedback)`. Полная версия даёт три токена на событие; simplified сворачивает тройку в один вектор и использует causal Transformer.
- Предобучение: next-any-item, включая взаимодействия с неположительным исходом, плюс feedback prediction. У simplified головы получают соответственно `(h_previous, context)` и `(h_previous, context, item)`, исключая текущий feedback из его собственного предсказания.
- Next-item использует sampled softmax с коррекцией распределения негативов; feedback — отдельные задачи по компонентам реакции.
- Затем impression-aware fine-tuning: отдельный item encoder и состояния истории сопоставляются по времени, с имитацией задержки доставки. Векторы пользователя и товара имеют размер 512, ранжирование использует скалярное произведение; авторы применяли pairwise loss и ежедневный пересчёт.
- ItemID в эксперименте кодировался unified embeddings с тремя lookup; это хешированное представление категориальных признаков, а не NLP-токенизация и не определение общего user/item пространства. Item encoder может принимать метаданные без ID.

Источник: [статья авторов, актуальная arXiv v2 от 18.02.2026, §§3–5](https://arxiv.org/html/2507.15994v2).

В первой интеграции score ARGUS добавляли как признак в финальный градиентный бустинг. Causal обработка позволяет получать состояния пользователя для многих моментов истории за один проход, вместо повторного кодирования каждой пары показов. Это мотивирует отдельную проверку `strong boosting` против `strong boosting + neural score`, однако не обещает улучшения на REES46. [Авторская статья Яндекса, разделы «Дообучение» и «Результаты»](https://habr.com/ru/companies/yandex/articles/919058/).

## Важное обновление 2026 года

В продолжении авторы описывают context-event токенизацию: отдельный токен контекста и компактные item/action токены; текущий контекст участвует в последовательности раньше. Такой вариант требует выполнения Transformer в runtime. Также в обновлённом рецепте **исключён feedback-loss**, оставлен next-any-item: дополнительная голова не дала выгоды в их последующих экспериментах. Поэтому «ARGUS обязательно имеет два loss» — неверное универсальное утверждение. Дата страницы подтверждена HTML `datePublished`: 2026-05-21. [Продолжение авторов от 21.05.2026](https://habr.com/ru/companies/yandex/articles/1037766/).

SASRec — более ранний self-attention подход к предсказанию следующего item по истории; в исходной постановке обычно моделируются положительные взаимодействия. Пользовательский вектор из последовательности не уникален для ARGUS. [SASRec, оригинальная работа](https://arxiv.org/abs/1808.09781). Sona — другая архитектура: общая история питает autoregressive decoder и ranking module, обучение включает distillation. Называть нашу простую двухбашенную модель Sona нельзя. [Sona Technical Report](https://arxiv.org/abs/2608.11015).

## Что переносимо на REES46: наши предложения, не результаты статьи

- Item encoder: trainable `product_id` + `category_id` + brand; опционально проверенный текст категории и преобразованная цена. Недостоверные восстановленные названия не использовать как ground truth.
- Event encoder: item embedding + известный тип `view/cart/purchase` + относительное время/позиция. User encoder: сначала взвешенный pooling, затем небольшой GRU или causal Transformer. Начальная исследовательская конфигурация — 64/128 выходных компонент и ограниченная история; её пригодность надо измерить.
- Сначала определить задачу и cutoff. Next-event предобучение доступно по всем трём типам событий; purchase-oriented loss требует отдельной корректной разметки. Предсказание следующего просмотра и будущей покупки — разные цели.
- `view` не является логом рекомендательного показа, `view without purchase` не означает dislike. В REES46 нет достаточных данных для буквального impression-aware fine-tuning ARGUS или off-policy коррекции рекомендаций. Sampled negatives — альтернативы в обучении, не наблюдавшийся отрицательный feedback.
- Для каждой обучающей/валидационной строки история строго раньше времени прогноза. Веса нейросети, словарь, статистики и признаки также не должны обучаться на будущем; score нейросети для бустинга должен быть получен через временную схему, исключающую обучение нейросети на целевых исходах этих строк.
- У большинства пользователей короткая октябрьская история; длинный музыкальный контекст 8192 и результаты на 300B событий нельзя переносить как ожидаемый эффект. Проверять по сегментам длины истории, cold/warm; fallback для пустой истории обязателен.
