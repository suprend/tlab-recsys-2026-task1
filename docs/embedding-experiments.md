# User/item embeddings: эксперимент для REES46

Исследовано 14 октября 2026 года. Ни обучение, ни скачивание моделей не выполнялись. Target, горизонт и даты разбиения ещё не утверждены. Ниже — предлагаемый протокол, а не принятое решение. Сверены текущие `docs/experiment-plan.md`, `docs/nlp-experiments.md`, `docs/text-embeddings.md`.

## Что хотим проверить

Да: `e_i = f_item(item attributes) ∈ R^d`, `z_u(t) = f_history(events strictly before t) ∈ R^d`, `s(u,i,t)=dot(z_u(t),e_i)`. Одинакового числа координат недостаточно: пространство нужно согласовать общей функцией потерь или строить профиль как агрегацию тех же item-векторов. История даёт embedding даже для пользователя, которого не было при обучении, если у него есть наблюдаемые события. У пользователя без истории нужен отдельный fallback. Это поведенческое representation learning; полноценные тексты и картинки для него не обязательны.

User encoder из истории и отдельный item encoder соответствуют общей двухбашенной идее; первичный пример такого обучения — [Yi et al., RecSys 2019](https://research.google/pubs/sampling-bias-corrected-neural-modeling-for-large-corpus-item-recommendations/). [SASRec, Kang & McAuley 2018](https://arxiv.org/abs/1808.09781) использует self-attention над предшествующими действиями для предсказания следующего товара. Эти источники подтверждают подход, но не гарантируют прирост на REES46 и не делают реализацию воспроизведением ARGUS.

## Начать с контролируемой лестницы

1. Сильный ручной CatBoost: прошлые user/item/user-item/user-category/user-brand агрегаты, давность, частоты, популярность, повторы, доступные атрибуты/цена, уровни иерархии. Набор уточняется под target.
2. Те же строки + сходства профиля из фиксированных category text embeddings с кандидатом: уже описанный NLP-контроль; он не различает товары с одинаковой категорией.
3. Те же строки + профиль как weighted mean обученных item-векторов. Это обязательный дешёвый behavioral baseline до Transformer.
4. Те же строки + компактный causal sequence encoder с item ID, типом события и временными признаками. Начальная идея: SASRec-подобный encoder; архитектуру и objective следует описывать как адаптацию, особенно при нескольких типах событий.
5. Только при полезном эффекте — ID + metadata, раздельные профили views/carts/purchases или многозадачное обучение. Не запускать одновременно все усложнения.

Главное сравнение — baseline CatBoost против baseline + нейросетевые признаки. Самостоятельный neural ranker может быть диагностикой, но не заменяет сильный ручной бустинг из условия. Если используется автоматический поиск агрегатора, весов или окон, фиксировать пространство поиска и одинаковый validation budget.

Практический стартовый размер — `d=64`, история до последних 50 событий, 1–2 слоя; это бюджетная гипотеза, не измеренная рекомендация по качеству/скорости. Таблица 166 794 × 64 float32 занимает около 40.7 MiB, но обучение расходует дополнительно память на градиенты, optimizer, активации и батчи. Отдельная обучаемая таблица на 3 млн пользователей не нужна, если требуем user embedding именно из истории. Сначала небольшой сохранённый по времени пилот, затем масштабирование без изменения протокола; фиксировать coverage пилота.

## Objective зависит от того, что предсказываем

| Вариант | Положительный пример и история | Что измеряет / ограничение |
|---|---|---|
| Следующий наблюдаемый event/item | Товар следующего события; история до него | Поведение магазина и логирования, включая повторные просмотры; 96% событий — view. Результат нельзя называть вероятностью покупки |
| Следующая покупка | Товар следующей покупки; views/carts/purchases до выбранного момента | Ближе к покупкам; нельзя считать все непокупавшие истории подтверждёнными отрицаниями. Нужно определить момент запроса и считать ожидание следующей покупки с цензурированием |
| Конверсия после view в течение H | Наблюдаемый view — anchor, label будущей покупки после него | Реальные просмотренные пары дают положительные и зрелые отрицательные labels; view доступен в момент решения, target — будущая покупка. Это conditional conversion, не ранжирование предпочтений всего каталога |

Для next-item/next-purchase предлагается один sampled-softmax/contrastive objective как первый протокол; BPR допустим как альтернативный pairwise контроль, [оригинальная постановка](https://proceedings.mlr.press/r7/rendle09a.html). Не смешивать потерю для observed conversions с искусственными catalog negatives без описания новой постановки. Тип supervision определяется происхождением target, а не названием loss. Next-item, автоматически полученный из самой последовательности, обычно относится к self-supervised предобучению; разметка конверсии задаёт отдельную supervised задачу. Одна contrastive функция потерь не определяет этот режим.

Event weights `view=1, cart=3, purchase=5` могут быть только тестируемой конфигурацией. Лучшая последовательность решений: сначала сохранить event_type и раздельные простые агрегаты; затем на validation проверить один weighting/decay. Удаление всех повторов разрушит сигнал повторных покупок/сравнения товара; точные дубли, повторы разных секунд и несколько событий одного timestamp — три разных случая. При одинаковом timestamp использовать строгую границу `event_time < t`: сортировка по номеру строки создаёт несуществующий порядок.

## Negatives и что можно заявлять

Нет impressions и propensity: «нет взаимодействия» не означает «показали и не понравилось». Можно учиться предсказывать следующую зарегистрированную активность/покупку при исторической экспозиции; нельзя по этим метрикам заявить причинный эффект новой рекомендательной политики. Основание о selection bias — [Schnabel et al., ICML 2016](https://proceedings.mlr.press/v48/schnabel16.html).

Для первого encoder фиксировать sampler, seed, число negatives, support и распределение. Catalog at t — товары, уже наблюдавшиеся до t, как явно ограниченный proxy доступности; реального stock/catalog нет. Сначала uniform из этого support; популярность, если используется, рассчитывается только до соответствующего cutoff. Не тянуть будущие items из каталога конца октября. Внутри батча исключать совпадающий target ID: другой пользователь с тем же товаром не делает его negative. Для horizon/set target исключать все положительные товары именно выбранного train-target, без чтения val/test. Не фильтровать negatives по будущей истории пользователя: это утечка. Уже посещённый/купленный товар не исключать автоматически — повторная покупка допустима.

False negatives среди неизвестных предпочтений неизбежны; не выдавать искусственные negatives за наблюдаемые отказы. In-batch sampling переиспользует распределение популярности; [Yi et al.](https://research.google/pubs/sampling-bias-corrected-neural-modeling-for-large-corpus-item-recommendations/) исследуют его коррекцию. Выбранная sampled loss не даёт автоматически калиброванную probability; [gSASRec](https://arxiv.org/abs/2308.07192) отдельно рассматривает overconfidence при negative sampling. Это причины записывать loss/sampler, а не повод добавлять много коррекций до первого baseline.

## Временная строгость: encoder тоже обучаемый признак

Отсутствие будущего в history не спасает, если веса encoder уже обучены на будущем этой строки. Например, encoder обучен 1–20 октября, а его score используется как supposedly strictly-past признак для строки 10 октября. Для условия задачи это нужно устранить. Общая проблема нарушения глобальной временной оси показана [Ji et al., TOIS](https://arxiv.org/abs/2010.11060).

Самый простой проверяемый вариант:

- `W` — warm-up для encoder и накопления истории. Все его train examples/labels должны быть полностью наблюдаемы к cutoff W; preprocessing, vocabulary, normalization и negatives также без будущего.
- После W encoder заморожен. Период `B` — обучение CatBoost на признаках этого encoder и истории строго до каждого anchor. Все сравниваемые ветки используют одинаковые строки B; ручной baseline может использовать историю W.
- Validation и test позже B. Веса encoder и выбранного CatBoost фиксированы; текущую историю пользователя можно обновлять ранее поступившими событиями, как в online serving. Это не обновление параметров. События одинаковой секунды обрабатываются одной группой до обновления истории.
- При конверсии с горизонтом H последний train anchor должен иметь зрелый label до момента обучения/начала следующего блока. Удалить незрелые хвосты или поставить явный embargo H; не использовать события validation для дозаполнения train-labels после заявленного fit cutoff.
- Test не участвует в выборе encoder, весов событий, H, epoch и количества попыток. Все branches получают одинаковую политику обновления истории и доступности свойств товара.

Статический user profile на начало validation отвечает другой задаче, чем профиль с обновляемой историей; можно сравнить отдельно, но нельзя одной ветке обновлять события, а другой нет. Подмешивать из будущего готовый label раннего anchor нельзя; прошедшую покупку можно добавить в историю лишь после её фактического timestamp.

Более сложный второй вариант — forward/chained folds: encoder каждого блока обучен только до его начала. Случайный K-fold не подходит. Склеивать сырые координаты нескольких независимо обученных latent spaces в единые столбцы CatBoost рискованно: оси могут произвольно вращаться/переставляться. Скалярные scores/cosines, нормы и агрегаты похожести устойчивее к общему ортогональному повороту, но их шкала всё равно может изменяться; нужна диагностика дрейфа/калибровки, а не обещание полной сопоставимости. Для первого результата warm-up freeze проще. Стандартное обучение neural model на всём train и проверка на future test валидно как отдельный offline recommender-протокол, но не доказывает строго-прошлую доступность neural features для ранних строк train бустинга.

## Какие признаки отдать CatBoost

Первый набор: `dot(user,item)`, cosine, нормы, cosine с последним товаром, mean/max similarity кандидата к истории, отдельные similarity views/carts/purchases, длина истории, OOV/empty-history flags. Раздельные операции не все обязаны войти сразу: сравнивать с теми же агрегаторами на weighted mean. Сырые координаты/произведения координат — дополнительная абляция только при одном замороженном пространстве и достаточном бюджете. Не хранить 64-мерный embedding для каждой из 42 млн строк без необходимости: рассчитывать в выбранных anchor точках и кешировать item vectors; измерять materialization cost.

Metadata embedding: ID + category + brand; цена как динамический атрибут требует as-of политики, иначе фиксированная таблица товара подмешает будущие изменения. OOV item ID — общий unknown ID + доступные на t метаданные; нет текста категории — missing indicator и исходный category ID, без придуманного названия. Cross-month recovered names требуют отдельной политики доступности, не включать автоматически в October causal experiment.

Обычной треугольной causal mask SASRec недостаточно для событий одной секунды: более ранняя позиция в массиве может иметь тот же timestamp. При обучении по многим позициям нужна mask по времени относительно каждого target, объединение timestamp buckets или исключение внутрибакетных next-step пар. Это правило относится и к обучению encoder, и к генерации его признаков.

В ranking-протоколе впервые появившийся target может отсутствовать в catalog-at-t. Такие запросы нельзя скрыто выбрасывать: показывать общую метрику с miss вне support, coverage и отдельную условную метрику внутри support. У замороженного на W ID-vocabulary товары, впервые наблюдаемые позже W, становятся OOV; ID-only ветка не различает их индивидуально. Metadata fallback и warm/cold срезы проверять отдельно; не считать warm-item метрику качеством всего трафика.

## Одинаковая оценка и стресс-проверки

Пока не выбран target, основную метрику нельзя назначить. Для conversion возможны PR-AUC/logloss, а group ranking только если есть обоснованные группы кандидатов; для next-item — Recall/NDCG на фиксированном candidate universe. Sampled ranking среди 100 negatives — другой эксперимент, не catalog Recall: первичный результат о несовпадении sampled и полных метрик — [Krichene & Rendle, KDD 2020](https://research.google/pubs/on-sampled-metrics-for-item-recommendation/). Если full-catalog дорого, уменьшать число query points, а не скрыто упрощать каждый каталог. Для reranking фиксировать одни и те же candidates, отдельно учитывать retrieval coverage и не приписывать выигрыш новому candidate generator.

Обязательные проверки перед выводом:

- Нулевые истории, незнакомый item, очень длинная история и повторный target item; coverage OOV не скрывать от общей метрики.
- События строго в момент anchor и после него: искусственное добавление/изменение будущих событий не меняет ранее рассчитанные features, vocabulary и fitted encoder checkpoint.
- Вся цепочка признака содержит `encoder_fit_cutoff`, `history_cutoff`, version/preprocessing/sampler; label cutoff отдельно.
- Группы длины истории 0/1–4/5–20/>20, новые/известные items, head/tail, повторные/новые user-item покупки, дни и sessions; сегменты не подменяют общий результат.
- Сравнить neural score с popularity-only/last-item-repeat: модель могла выучить популярность и короткий повтор, а не сложный интерес.
- Одинаковые train/eval rows, candidate set, missing-policy, history windows, metadata availability и CatBoost budget. Улучшение encoder loss без улучшения конечной метрики недостаточно.
- Если найдён прирост: несколько seeds в фиксированном бюджете и доверительный интервал разницы с resampling по пользователю/сессии, не по зависимым event-строкам; временную устойчивость показать отдельно по дням. Один месяц ограничивает обобщение на будущие месяцы.

Решения, которые нужны до реализации: target/anchor/H; strict timestamp semantics; W/B/val/test и зрелость labels; events/duplicates/repeats; support negatives; обновление истории; список branches/метрика/search budget. Размер 64, длина 50, веса событий и loss — конфигурации для проверки после этих решений.

Независимое ревью: уточнены timestamp-aware training mask, in-support coverage, OOV и происхождение supervision. Модели не обучались; предлагаемая схема не утверждена как итоговая постановка.
