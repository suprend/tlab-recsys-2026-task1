# Accepted historical019 control consumer

`strong_control.verify_control(path, *, check=lambda:None)` is a read-only consumer for the independently accepted historical019 development control. It returns `manifest`, `report`, `winner`, `selected_spec`, raw `actual_model_parameters`, ordered B41 `feature_names`, train/selection/ablation `acceptance_refs`, and exact `pins`, plus acceptance/lifetime/proof-limit metadata. `selected_spec` keeps training population, trained iterations and scoring prefix distinct: the selected prefix of a fully trained300-tree procedure is not assumed equivalent to a new shorter fit.

This bounded consumer authenticates exact historical acceptance SHA256 `a7cb383d9a75ac20ebd910fee384cb23eb8e255138df693a100942795e0ef692`, scope `reviewed_strong_baseline_control`, strict version/approval types and the externally reviewed304-pin closure. It reconstructs that closure from206 producer input fingerprints,69 outputs, recovery owner's final pins, original run/report/plan/winner and fit approval/claim, successful recovery verification/log and external lifetime/log, and the three immutable proof documents. A freshly resealed replacement is not trusted. Known failed producer/recovery markers reject; the original failed controller remains preserved, including its separately sealed marker and documented three-field final persistence tail.

Winner and selected-spec bindings, the independently replayed winner evidence, eligible original child checkpoint, native parameter dict, B41 order, original input acceptances, successful zero-fit recovery receipt and external lifetime caps are checked. Raw native parameters come from the chosen original child's saved report, or the accepted incumbent receipt when applicable; there is no coercion or reconstructed default parameter set. Model files, feature/target tables, ranking metrics and source formulas are never parsed or recomputed here. Verification streams pinned bytes, which can include large accepted inputs/models; no model load, prediction, training or database query occurs.

The caller owns and charges that I/O/CPU within its existing phase budget. `check` runs before receipt I/O and at most4MiB apart during pin hashing; it must be coupled to the reviewed worker/controller deadline and actual RSS/CPU accounting. The function has no skip-pin mode, new acceptance writer or caller-supplied trust anchor. It does not invoke `strong.prepare_plan`, environment snapshot or platform helper processes, avoiding the diagnosed019 no-subprocess conflict. Runtime CPU/package/environment equivalence remains the fit runner's separately reviewed stage.

Eight tiny synthetic tests cover exact304 reconstruction and raw selected params, trained300/scoring150 distinction, historical-anchor rejection of fresh replacements, strict approval/schema types, same-sized missing-proof substitution, known failure before large streaming, selected population mismatch, immutable original failure and monotone tail, guarded read and path confinement. Test-only trust-anchor/root substitutions authenticate synthetic fixtures rather than claiming actual historical acceptance. No real source/model/Pool/predict/fit or full304 actual hash pass is executed by these tests.

This is not a generic fresh-run/dataset API or complete fresh-clone bootstrap. It consumes a private historical approval and the reviewed proof limits, including that actual training weights cannot be recovered from a saved CBM and manual18 source proof is reused. Existing018 regeneration/reproduction work remains separate; a future reviewer must be able to rerun that workflow without presenting generated hashes as independently accepted evidence. This consumer grants no additional fit, source recovery, held-out access or quality claim.
