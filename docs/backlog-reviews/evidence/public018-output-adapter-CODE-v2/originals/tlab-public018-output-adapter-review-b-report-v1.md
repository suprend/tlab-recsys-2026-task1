## B-ADAPTER-001 [P2] Validate NPY headers before allocation and consume the same authenticated NPZ bytes

Location: `/tmp/tlab-public018-actual-output-adapter-v1.py:358–367`, especially lines 360–364.

The current preflight caps each ZIP member's uncompressed `file_size`, then `np.load` reads the three NPY arrays before validating their dtype and shape. NPY allocation is controlled by the header's declared dtype/shape rather than the member's actual payload size. Therefore a very small member can pass the ZIP cap and request an array larger than the proposed 8GiB verification limit before the shape check runs. The ZIP inspection also closes its file before `np.load(path)` reopens that path; later inventory repins cannot retroactively protect allocation against a replacement between those reads.

The exact `need` and `saved_scores` AST bodies were exercised with an invented 690-byte RAM ZIP containing three 128-byte NPY headers. Its `group.npy` declared `<i4`, shape `(3_000_000_000,)`, with no numeric payload. The adapter accepted its ZIP caps and entered the load/indexing stage. A Fake NumPy allocation trap calculated the requested 12,000,000,000 bytes and stopped before allocating anything. This establishes the missing preallocation rejection; it does not claim a real 12GB allocation or an actual corrupt producer artifact.
