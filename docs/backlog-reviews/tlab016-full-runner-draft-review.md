Режим: read-only review; ни данные, ни модели, ни SQL, ни тесты, ни fault injection не запускались. Это аудит изменяемого черновика, не code acceptance и не разрешение четырёх fits. Основной сохранённый снимок runner: SHA256 `94838d0e2994079247ac5cfe2e05e6561191da1dbb69113e955d38fff55ef749`; lifecycle helper `scripts/strong_baseline.py`: `10dffd789dded9a578b397b95a7b209285857459c0c92c8c925d1dfca6df3147`. Более ранний наблюдавшийся runner `a0c5623f033829f1c836e66c08d0d38cd54dcca0fc08b923a8f2eda9627f81e8` сохраняется в аудите как версия первоначальных замечаний. Код продолжает меняться; ниже явно разделены findings, их наблюдавшиеся исправления и будущие проверки.

## Material findings

**F1. Parent должен связывать разобранный snapshot с выдаваемым SHA.** В `_invoke_worker` строка 517 сохранённого снимка читает `consumed_body,_=_read(consumed)`, а identity ниже получает другой вызов `_sha(consumed)`. В `_observer` строка 599 читается `evidence,_=_read(evidence.json)`, но returned evidence ref получает отдельный `_sha`. Во втором случае конкретная последовательность: parent проверил старое тело со `status=verified`; перед последующим hash файл заменили новым телом; return содержит hash нового, непроверенного тела. Это нарушение binding независимо от того, создаст ли другой downstream verifier дополнительную защиту. Для consumption первое тело и hash также могут принадлежать разным snapshots; это ещё не утверждение о полном bypass независимого observer.

Минимальное исправление: сохранить digest из того же bounded `_read`, использовать именно его в identity/reference и повторно проверить неизменность перед успешным завершением. Проспективные tiny tests: заменить bytes только между parse и следующим hash; old-body/new-hash ref никогда не может быть успешным результатом. Ранее исправленные `_read_ref` и issued-context seams сами по себе эту новую пару мест не закрывают.

**F2. Успешный receipt первоначально не проверял выделенную CPU/wall allowance.** В версии `a0c5623f…` parent ограничивал entry CPU фактически reaped CHILDREN, но не original slot CPU; finish сравнивался с текущим временем, а не slot deadline. Например, `allocation.cpu_seconds=100`, actual/reaped=101, общий shared cost=3000: parent predicate пропускал превышение индивидуальной выдачи. Другой буквальный случай: finish=slot deadline+1 при ещё не исчерпанном общем producer deadline. Helper проверяет wall в polling loop; завершение между последним poll и следующим условием не заменяет post-exit receipt check. Observer evidence аналогично не ограничивал reaped CPU собственной allowance.

**Наблюдавшееся закрытие F2:** в `94838d0…` success branch требует entry и reaped CPU≤slot allowance, launch≤start≤finish≤original slot deadline; observer требует used≤allocation CPU. Это статическое закрытие, не результат исполненного regression. Тест должен различать exact boundary, one-unit excess и original deadline, без sleeps и без настоящего превышения бюджета.

**F3. Известный RSS resource failure первоначально становился общим STOP.** В `a0c5623f…` общий receipt predicate требовал RSS≤7GiB ещё до определения failed/resource_failure. Честно пойманное превышение worker cap, например 7GiB+1, не могло стать paid/ineligible arm по объявленной политике. В `94838d0…` общий receipt допускает до8GiB, success отдельно требует≤7GiB; финальная conservative child+owner сумма по-прежнему ограничена8GiB. Это разумное статическое закрытие: worker overshoot не разрешает whole-job превышение, неизвестный exit/API/integrity failure остаётся STOP. Нужны отдельные tiny receipts для known failure ниже whole-job cap и превышения общей границы.

**F4. Exclusive create ещё не доказывает crash-durable consumption.** В сохранённом снимке owner-attempt/global four-fit/slot-consumed/observer-once claims пишутся через `open('x')`, без явного `flush`+`fsync`. Это исключает одновременное создание существующего pathname, но обещание сохранности после crash требует дополнительного persistence gate. Python документирует принудительный file sync отдельно. Минимальная граница: claim должен быть успешно сброшен до запуска зависимого worker/observer; sync failure — STOP, без fit, очистки claim или автоматической повторной попытки. File fsync не следует описывать как универсальную гарантию сохранности directory entry при любом сбое файловой системы. [Python os.fsync](https://docs.python.org/3.12/library/os.html#os.fsync).

## Что выглядит согласованным в данном scope

Selector реализует B+все четыре исходных slots, inclusive Recall floor B−.002, один global NDCG band1e−12, затем число физических колонок и lexical ID. Никакого последовательного попарного tolerance comparator не обнаружено. B с0 колонок выигрывает общий band; random winner не доказывает guided superiority. Missing/API/integrity states не подменяются resource_failed. Проверка точного selector JSON остаётся обязательной.

`prepare_plan` требует independently accepted recovered source, unchanged B41 schema/base collections, точный selected allocation L02/L06/L01/L05, typed physical delta, accepted control/environment/native procedure и внешний approval с fingerprints. Это механический перенос существующей strict-past acceptance, не новый source oracle и не доказательство всей B41 по каждому исходному событию. Heldout-opening permission этот runner не выдаёт. До отдельного review независимого observer нельзя утверждать, что один его вызов уже доказал все numeric/model assertions.

Cost identity использует paid source prefix плюс абсолютные SELF и reaped CHILDREN ровно один раз. Worker self receipts не добавляются второй раз. Согласно Python, SELF включает CPU всех threads, CHILDREN — завершившиеся процессы, которых дождались; это не live-meter активного потомка. [Python resource](https://docs.python.org/3.12/library/resource.html#resource.RUSAGE_CHILDREN). Callback CatBoost вызывается после итерации, поэтому stage/callback guards не являются OS hard cap внутри Pool/predict/одной итерации. [CatBoost fit callbacks](https://catboost.ai/docs/en/concepts/python-reference_catboostclassifier_fit#callbacks). Parent supervision, reaping и post-exit измерения нужны независимо; timeout ожидания сам по себе не обещает kill+reap. [Python subprocess](https://docs.python.org/3.12/library/subprocess.html#subprocess.Popen.wait).

600 CPU/wall reserve и cleanup allowance выводятся из исходного owner clock; новые workers не получают новый общий час. В новом снимке owner-attempt claim создаётся перед paid preparation: это полезно закрывает бесплатный повтор подготовки после failed owner. Его fsync и fail-closed reuse ещё требуют проверки.

Terminal report честно называется `model_outputs_verified_pending_external_acceptance`, а receipt boundary требует external full-lifetime seal. Поэтому последний in-process counter не следует выдавать за измерение всей жизни процесса: сериализация и выход оплачиваются внешним наблюдением. Это необходимый оставшийся gate, не основание автоматически повторять observer. Ошибка resource reader в finally, ошибка report write, поздний failed marker, cleanup failure и попытка второго owner/observer должны сохранять доступную failure evidence и не давать acceptance.

Итог: original resource findings имеют наблюдавшееся статическое исправление; snapshot/persistence findings в указанном снимке открыты. Финальный frozen SHA, synthetic lifecycle regressions, отдельный observer review и external lifetime receipt остаются обязательными. Из этого audit не следует новый fit, look, retry или изменение selector.
