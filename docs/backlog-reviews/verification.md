## Критическое ядро: восемь сценариев

Предлагаю один читаемый golden fixture: несколько пользователей и товаров, 30–50 синтетических строк, фиксированные anchors и вручную записанные ожидаемые candidates/results. Генератор кандидатов действительно запускается, а не получает готовый правильный список. Идентификаторы вымышленные. Сценарии переиспользуют fixture, но assertions проверяют смысл, а не внутренние очереди и методы.

1. **Глобальная секунда.** На t разные пользователи делают view/cart/purchase одного товара и меняют metadata. Все прогнозы на t видят состояние до всей секунды, включая global counters. Перестановки peers и добавление suffix `≥t` сохраняют past features, eligibility и candidates при неизменных anchor/context; labels проверяются отдельно, поскольку будущие покупки намеренно их меняют. После единственного batch-update следующий anchor видит всю группу. Это ловит межпользовательскую утечку, которую user-only fixture пропустит.

2. **Границы, календарь, цензурирование.** Событие `t−W` включено, `t` исключено; проверить соседние секунды и пустую историю. Rolling сутки на полуденном anchor включают сегодняшнее утро; закрытый UTC-день — нет. Source coverage равно `min(W,max(0,t−S))`, а не возрасту пользователя; первый strict-past age missing с mask, count=0. Правоцензурированный query не становится negative. Смена timezone машины не меняет UTC-результаты. Early-month и первый query после warmup обязательны.

3. **Exact distinct и expiry.** Для W=10 секунд просмотры товара: A в 0 и 4, B в 3. На t=10 ожидаются count=3/distinct=2; t=11 — 2/2; t=14 — 1/1; t=15 — 0/0. Истечение первой строки A не удаляет A, пока живёт вторая. Distinct parent считается объединением, не суммой детей; разность cumulative distinct не подменяет distinct полосы.

4. **Category ID, namespace и STOP.** Два ID одного code сохраняют разные ID-counts; известный ID без code работает, но semantic features missing. `a.b` и `x.b` различны, underscore не delimiter. Два события на terminal `a.b` плюс одно на `a.b.c` дают parent=3, child=1, STOP=2. Прямые terminal events и пользователь в нескольких siblings запрещают простое суммирование children. Поздно появившийся descendant не переименовывает старые события. [Taxonomy A](../features/06-taxonomy-nodes/research-a.md).

5. **Ratios и support.** `P=2,V=1` даёт P/V=2 без clipping; это не биномиальная вероятность. При V=0 результат missing с denominator/support, при numerator=0 и denominator>0 — настоящий 0. Category view-share проверять по одному event type, окну и grain. Неизвестная категория кандидата отличается от известной категории без истории. Нельзя навязать всем ratios ограничение `[0,1]`. [Rates](../features/03-rates/research-b.md).

6. **Fitted state и learned coverage.** Подставной encoder/prior имеет fit cutoff τ; ранние anchors не получают будущую версию. Изменение данных после τ не меняет frozen параметры. Истории обновляются, weights — нет. Learned event-owner counters стартуют с τ; их coverage `min(W,max(0,t−τ))` отличается от source coverage. Смена assignment не переносит старое событие; перестановка cluster IDs требует version mapping либо разрыва совместимости. Reclassified snapshot допускается только отдельным mode. [Layers](../features/05-user-layers/research-a.md).

7. **Metadata, OOV и цена.** Последняя доступная секунда с конфликтующими brand/price даёт ambiguity независимо от порядка строк. Поздний бренд/code не переписывает историю; unseen token не расширяет frozen vocabulary/IDF. Missing text, OOV и известное нулевое сходство различимы. Price snapshot использует одну последнюю допустимую положительную цену на товар; ноль и неоднозначная цена не превращаются в нормальную цену. Проверить support ровно под/на выбранном пороге; дневной reference не подменять rolling. [Text](../features/07-text/research-b.md), [price](../features/04-categories/research-b.md).

8. **Candidates, зрелость, метрики.** Новая после t покупка остаётся target вне universe/candidates: её запрещено вставлять в shortlist. Candidate dedup, повторно покупаемый товар, пустой C, пустой зрелый Y и незрелый query — разные случаи. Negative sampler исключает только target выбранного H, а не покупки позднего holdout. Для `|Y|=3`, одного retrieved relevant на первом месте и K≥3 ожидаются Recall=1/3 и NDCG≈0,469, а не 1. Короткий список не дополняется missing targets; ties детерминированы. При single target AP=RR; zero-конвенция даёт all-query=`p×conditional` только при одинаковом query weighting. User-macro проверить отдельно. [Evaluation](../target-research/05-evaluation.md), [review](../target-research/review-05-08.md).

## Независимое доказательство поверх golden fixture

**Direct bounded DuckDB oracle:** отдельные SQL-агрегации по исходным synthetic events и anchor table с явными `e.time≥t−W AND e.time<t`, `COUNT(event_id)`, `COUNT(DISTINCT…)` и max timestamp. Не вызывать production feature helpers, expiry queues или общий boundary predicate: иначе обе стороны повторят ошибку. Hand-calculated golden values остаются третьей опорой. Counts/masks/set membership — точное совпадение; дробные результаты — объявленный абсолютный tolerance, например 1e−9 для этих маленьких расчётов.

После synthetic gates предложен read-only реальный replay: 20–50 anchors, два окна, ограниченные keys, исходные события всего необходимого history interval. Не sample-ить строки, разрушающие global/category totals; не объявлять усечённый slice полным source coverage. SQL через существующее окружение, read-only DB, threads=2/memory=2GB; manifest фиксирует bounds, checksum и размер. Это план, не выполненный benchmark.

**Tiny temporal E2E:** warmup → past-only anchors → candidates/features → отдельное присоединение зрелых labels → deterministic popularity/last-item scorer → metrics. Проверить сохранение числа queries на каждом переходе, причины исключений, joins без размножения строк, отсутствие label columns в feature inputs. Достаточно миниатюрного replay, без CatBoost. Критическое ядро должно ловить намеренные дефекты: `≤t`, преждевременный peer-update, future fit, distinct-delete при первом expiry, positive insertion и IDCG только по candidates. Это проверки чувствительности тестов, не требование большой mutation-framework.

Перед добавлением sampled BCE достаточно одного арифметического контроля: перебрать все равновероятные subset draw на трёх negatives и сверить среднюю взвешенную loss с полным candidate-risk. Для PairLogit проверить массу пар=1 у информативной группы и отсутствие деления при p=0/n=0; такие queries остаются в evaluation manifest. Это сильнее теста, повторяющего формулу весов, и не требует обучения.

## Приёмка baseline и эксперимента

Baseline готов, когда manifest воспроизводим, golden/oracle/E2E проходят, нет необъяснённых расхождений, candidate coverage и доли no-signal/empty/censored опубликованы, стоимость подготовки/fit/scoring и peak RAM **измерены**, а не оценены по размеру float-массива. Минимальные контролы — past popularity, recent/last-view и ручной boosting; установка/обучение идут отдельной задачей.

Абляции меняют один feature block при одинаковых anchors, C, Y, split, metadata policy и бюджете; retrieval меняется отдельным экспериментом. До запуска записать main metric, минимально полезный Δ, число validation-попыток и ресурсный cap. Принятие гипотезы требует воспроизводимого эффекта на validation, парной разности с user-cluster uncertainty и отсутствия заранее недопустимого провала критичных coverage/history срезов. Нулевой либо неопределённый прирост — честный результат; passing tests не доказывает полезность. Test используется после фиксации конфигураций; интервалы не компенсируют многократный подбор. Первые ready checks: global-second invariance, endpoints/coverage, distinct expiry, затем маленький E2E и независимый SQL-oracle; learned/text/price gates активируются перед соответствующими P1-опытами.
