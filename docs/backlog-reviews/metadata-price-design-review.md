## Material finding 1: clean metadata и допустимость числовой цены — разные проверки

Фраза «все значения bucket **ненулевые** и совпадают» двусмысленна: число 0 является наблюдаемой ценой, хотя непригодно для объявленного valid-price признака. Исправить на **все значения NON-NULL и совпадают**, затем отдельно `finite(p) AND p>0`. При единственном clean p=0: zero flag включён, log_price=NULL, цена не попадает в R; это не all-NULL missing и не ambiguous. Аналогично clean negative отличается от пропуска. Bucket `{0,NULL}` — ambiguous; его нельзя преобразовать в clean0 удалением NULL перед проверкой.

Нужно также зафиксировать nonfinite policy: source NaN/+Inf/−Inf отклоняются с fail-closed report до логарифма/агрегации; нельзя пропускать +Inf через одно условие p>0 или незаметно приравнивать malformed NaN к SQL NULL. DECIMAL источника ограничивает реальные значения, но generic validator/synthetic input всё равно должен иметь однозначный контракт. Предложение не добавляет шестнадцатую колонку: malformed input — ошибка, а не новая обучаемая категория.

При этом **разрешённый output NaN** — представление ожидаемого NULL у числового признака. «Finite validation» не должно отвергать все такие значения и не должно заменять их нулём. Проверять finite для известных значений, отсутствие ±Inf после float32 cast и соответствие declared missing masks. CatBoost поддерживает numerical None/NaN и отдельно описывает `nan_mode`; для categorical специальной missing обработки нет. [Официальная документация](https://catboost.ai/docs/en/concepts/algorithm-missing-values-processing). Это устраняет реальную возможность несовместимых price/loader интерпретаций.

## Material finding 2: зафиксировать nullable LOO и точную схему до compiler

Алгебра `A−1[i∈R]·z_i` корректна для определённого z_i, но при i∉R и неизвестной цене `0·NULL` может дать NULL. Задать subtraction **кусочно**: `removed=z_i if i∈R else 0`; membership должен вычисляться по фактическому R, не по наличию кандидата в C. Не вычислять z_i в отсутствующей ветви. Тогда при известной категории, invalid own price и непустом R peer_mean остаётся известным, support=N; difference=NULL. Если дизайн намерен делать peer_mean NULL и здесь, это другое определение и его нужно объявить, а не получить случайно.

Обязательная truth table: unknown/ambiguous category → reference/support=NULL; известная категория и пустой R → support0, mean/difference=NULL; self-only R → peer support0; i∉R → supportN без вычитания; known category/unknown own price → mean возможен, difference отсутствует. Mean/difference missing flags имеют разные причины. Поддержка не подменяется нулём для неизвестного conditional key.

Арифметика размера сходится: **2 brand flags +3 code flags +(log_price+4 price flags)+(mean/support/difference+2 missing flags)=15 numeric**, плюс3 nominal. Но «точная схема после synthetic compiler» слишком поздно: compiler нельзя использовать как источник определения. До реализации перечислить имена, порядок, dtype/nullability и truth table flags. Для code особенно различить latest-raw unavailable/ambiguous, dictionary unavailable/ambiguous и recovered; три model flags не обязаны кодировать всё, дополнительные provenance states могут быть служебными, явно исключёнными из model inputs. Existing005 category flags не дублировать. При base41 действительно получается56 numeric+3 nominal=59 inputs; проверять фактические names, а не только count.

## Что в дизайне принято

Последний **глобальный** timestamp `<t` и весь bucket всех пользователей — правильная совместимость с005. Category ID, code, brand, price проверять независимо, без older-clean backoff. При чистой категории и ambiguous price нельзя терять category key. Code dictionary `[S,t)` с одним известным named code допустим как **отдельный recovery provenance**, включая first-known time и conflict state; это не исправление raw/latest code. Поздние месяцы и full-month dictionary не используются. Ambiguous latest code может сосуществовать с однозначным dictionary result; original ambiguity сохраняется, recovery не объявляется достоверной таксономией для всех ID.

`R_c(t)` — distinct активные products по всем event types в `[t−7d,t)`, распределённые по чистой **текущей as-of категории** и valid latest price. Это отдельный stock-proxy/reference estimand, без доказанного наличия. При move A→B текущий reference переносит товар в B; historical005 view numerator остаётся на event-attached A/B и не переписывается. Population R не ограничивается C или выбранными пользователями; иначе цена категории зависит от retrieval. Наличие события задаёт active eligibility; повторы не увеличивают вес product строки.

`mean(log1p(p))` — средняя преобразованной цены, difference — разность в этой шкале. Это не arithmetic mean price, не обычный price ratio и не probability. Зафиксировать source price unit: log1p зависит от денежного масштаба. Sum/mean считать в достаточной precision, проверять float64 oracle до float32 output, с объявленным допуском; не вводить learned clipping. C, U(t), Q и полный Y остаются прежними, future positives не вставляются.

## API evidence и исполнимые gates

Прочитанный toy показывает FeaturesData/Pool ingestion трёх categorical полей, два objective, finite unseen predictions и OneHotFeature/noOnlineCtr в двух деревьях. Это **совместимость интерфейса**, не quality, реальная cardinality, полная CTR-proof или memory benchmark. [FeaturesData docs](https://catboost.ai/docs/en/concepts/python-features-data__desc) требуют float32 numerical, object/UTF8 bytes categorical и предупреждают об отсутствии внутренних checks; порядок numeric→categorical должен совпадать на inference.

Порог4096 проверять по **фактически переданным train encoded values каждого поля, включая sentinels**; при превышении остановка, не CTR fallback. Namespace `value:`/`state:` корректен, если применяется до bytes encoding ко всем значениям. [CatBoost docs](https://catboost.ai/docs/en/features/categorical-features) говорят, что CTR для one-hot features не вычисляются; CPU PairLogit отличен от запрещённых one-hot pairwise-scoring objectives PairLogitPairwise/YetiRankPairwise/QueryCrossEntropy. После единственного разрешённого real fit проверить effective params/cardinalities/JSON CTR evidence; новый fit ради доказательства не добавлять.

100Q gate сохранить: label-independent selection с несколькими днями, ≤22 000 pairs, 2 threads/10min/RSS8GiB/temp2GiB. Independent oracle должен проверить metadata **всех selected pairs** и полный reference membership для их категорий, включая товары вне C; direct list mean после удаления i не переиспользует sum/count production helpers. Fixtures покрывают NON-NULL0, mixedNULL, nonfinite rejection, peers/future, category move, dictionary conflict и отсутствие self. Exact keyed coverage, unchanged base pins, schema/order и cost ledger обязательны.

После этих двух spec fixes дизайн можно принять для bounded реализации. Source/cost acceptance предшествует full exports; максимум **один** whole-block ablation fit против сохранённого base при тех же sampled train Q/loss/settings/checkpoint50 и full-Y evaluator006, до strong tuning. Block gain нельзя приписать brand или price отдельно. Screening остаётся screening; confirmation/final не открываются, бюджет009 не расширяется.
