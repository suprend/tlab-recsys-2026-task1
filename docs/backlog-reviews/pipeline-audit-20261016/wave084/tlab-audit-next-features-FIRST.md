Новых поддержанных кодом дефектов — **0**; новых научных ID — **0**; предложены **2 уточнения** существующего HYP-046 и TLAB-005/016/018. Это SOURCE-проверка frozen combined-v1, не приёмка runtime. **REFINE-1 — независимость значений от упаковки Q/C; HYP-046 / TLAB-005/016/018.**

Механизм: compiler ограничивает домены через `manual_day_users/items`, но категория должна агрегироваться по всем исходным событиям соответствующей категории, а не по выбранному C. Это видно в `scripts/manual_features.py:134–153,180–215`. При правильном контракте одна и та же пара `(query_id,product_id)` должна получить те же признаки при расчёте всех Q одним пакетом и расчёте непересекающихся подмножеств Q с последующей keyed-конкатенацией. Это свойство отдельно от перестановки событий и future-suffix invariance.

Проверяемое предсказание: B45 и дополнительные столбцы всех восьми программ совпадут по имени, типу, NULL и значению; добавление другого пользователя, его кандидатов или пустого C не изменит уже существующие строки. Конкретный различающий пример: пользователь U смотрел I категории A один раз, а другой пользователь V — J той же A трижды; I входит в C(U), J отсутствует в C(U). Доля I в A равна 1/4 и при отдельном расчёте U, и при совместном U/V. Неправильный category-denominator через текущие candidate items даст 1 при отдельном U. Добавить второй anchor после смены metadata, чтобы выявить перенос кеша между anchor.

Контргипотеза: текущие SEMI JOIN уже корректны, дополнительная проверка пройдёт без исправлений и без выигрыша качества. Наличие отдельных category/metadata тестов (`tests/test_manual_features.py:229–270`) поддерживает эту контргипотезу; само отсутствие общей проверки не доказывает баг.

Ближайший опыт: ≤24 придуманных event rows, 3 Q, 5 C, 2 anchor; literal reference задаётся до компилятора. Сравнить один пакет, два переставленных пакета и singleton-пакеты; включить zero-C query. Не пересчитывать retrieval и не менять состав C. Нужны отрицательные контроли для ошибочного candidate-conditioned denominator и повторного использования прежнего anchor. Существующий rich all-eight тест (`tests/test_feature_programs_all_bundles_rich.py:256–373`) меняет события, но не упаковку Q. Считать проверку содержательной, если оба ошибочных варианта отвергнуты; иначе расширение теста отклонить. Время/RSS **UNKNOWN**, нужен отдельный ограниченный engineering-план; fits 0.

Польза Task1: проверяемый контракт безопасного batching для автоматизированного materializer; это не новое качество, новый оператор или доказанный speedup. Объединить с HYP-046/уже известными key/cardinality obligations, не заводить новый HYP.

**REFINE-2 — сквозное равенство training и inference для реально выбранного union; HYP-046 / TLAB-016/018.**

Механизм: выбранный producer создаёт F57 с 12 дополнениями, тогда как каждое обучение получает B41+3. `feature_program_collection.py:48–72,119–178` задаёт union и физический порядок; `program_model_data.py:50–152` связывает полный F57 с выбранной дельтой, преобразует float32/NULL и сохраняет B/Y. Label-free loader отдельно проектирует B41+3 (`inference_data.py:49–125`). Сбой на стыке может пройти изолированные проверки каждого компонента.

Проверяемое предсказание: на одном исходном toy для I1/L02, I2/L06, R1/L01, R2/L05 будут одинаковы feature names/order, X float32 с одинаковыми NaN, точные int64 item keys и group membership после сопоставления query IDs; training Y не изменит X. Query order в двух API нельзя предполагать одинаковым: сравнивать по `(query_id,item_id)`, сохраняя отдельно их объявленный порядок.

Конкретный контрпример для будущего теста: recency=NULL и companion count=0 у одной пары, положительная recency и count у второй; перестановка физического recency/mask или проекция неверного arm может сохранить форму X, но изменить смысл. В новом rich тесте проверяется compiler→B45→inference каждого из восьми блоков (`:302–337`), но F57→`append_program_features` этим тестом не вызывается. Старый `test_program_model_data.py` проверяет ключи, маски и chunk boundary отдельно; это полезное покрытие, не повод объявлять pipeline неправильным.

Контргипотеза: существующая source/model acceptance и отдельные loader tests уже поймали все такие ошибки; новая композиция даст только дополнительный regression guard. Опыт: тот же ограниченный raw toy → настоящий selected union/compiler F57 → настоящий base training preparation и append четырёх arms → label-free inference; независимый literal gold, один большой nominal ID, NULL, неодинаковые actions и empty-C Q. Перемена synthetic Y должна менять только targets/Y. Подмена arm должна провалить frozen-declaration/gold comparison; переставленный schema — loader guard. Runtime/стоимость **UNKNOWN**, ML fits 0; не открывать production collections ради этого. Польза Task1 — evidence для source→model автоматизации; не повышает unselected четыре arms до поддержанного execution scope.

**Граница выводов.** В рассмотренных temporal SQL верхняя граница `<anchor`; historical category остаётся event-attached. Не найден новый контрпример прямой утечки. `feature_programs.py:15–19` явно объявляет event-time availability assumption: отсутствие arrival clocks не устраняется ни одним из предложенных тестов. Нельзя переносить SOURCE-вывод на фактические данные, скрытые late arrivals, native обучение или новое превосходство модели.
