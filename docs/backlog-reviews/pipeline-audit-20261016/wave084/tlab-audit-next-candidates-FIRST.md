## REFINE A: измерять потолок именно выбранной top-K метрики

Связь: **TLAB-004/006/007**, диагностика HYP-004/053/061–062; новый ID не нужен. Сейчас `heuristic_baselines.py:170–180` вычисляет candidate-Recall, а основной критерий задания — query-macro NDCG@20 (`docs/experimental-report.md:40–42`). Документ уже корректно запрещает выдавать Recall ceiling за NDCG: это не найденная ошибка.

**Механизм:** при полном Y, `y=|Y|>0`, `h=|Y∩C|`, `D(m)=Σ[r=1…m]1/log₂(r+1)`, лучший порядок C имеет `Recall@K=min(K,h)/y` и `NDCG@K=D(min(K,h))/D(min(K,y))`. Разность «oracle ceiling − фактическая метрика» отделяет потери перестановки от отсутствующих кандидатов при том же estimand. Такой oracle применяется только после retrieval для анализа, никогда не вставляет positives в C.

**Предсказание:** каждый реальный ranker на том же C не превысит эти bounds. Если существеннее потеря до C, дальнейший fixed-C feature search ограничен; если существеннее gap до oracle, один coverage-процент не обосновывает приоритет новой retrieval-модели. Это описательная локализация, не причинный прогноз улучшения.

**Статический контрпример:** y=h=25,K=20 даёт candidate-Recall=1, но максимально достижимый Recall@20=0,8. Текущий `ranking_metrics.py:114–133` считает фактическую метрику корректно. При y=2,h=1 потолок NDCG отличается от Recall=1/2.

**Контргипотеза:** при h≤20 для всех Q Recall ceiling численно не изменится; новый диагностический столбец сам не улучшит качество. **Ближайший эксперимент:** четыре literal Q: >K positives; off-C/cold miss; empty C; mature empty Y, плюс отдельно censored Q. Независимые формулы и исчерпывающие малые перестановки должны совпасть; затем лишь отдельно разрешённая агрегатная проверка на закреплённых outputs. Бюджет: предложенные ≤5 Q/≤30 items, 0 fits; фактическая стоимость **UNKNOWN**, запуск **UNRUN**. Польза Task1: честно оценить доступное пространство для автоматизации признаков.

## REFINE B: проверить freshness только внутри popularity cutoff ties

Связь: **HYP-031**, более узкий контроль существующего short-term/trend направления (`docs/candidate-generation/02-popularity.md:25,39`); не новый алгоритмический ID. `candidate_pilot.py:61–70` при равном distinct-buyer count выбирает меньший product_id. Это явно объявленный корректный tie-break, а не утечка/дефект.

**Механизм:** альтернативный versioned источник сохраняет основной buyer-count, квоту200 и recent20, но разрешает равенство по последнему strict-past purchase DESC, затем ID. Он может заменить устаревшие товары на границе P200, не перераспределяя целую trend-квоту.

**Предсказание:** вне границы равных count множество P200 неизменно; различия возможны лишь при cutoff ties. Если спрос сохраняет краткую свежесть, новые marginal hits вырастут; это пока гипотеза. **Контргипотезы:** на границе нет ties; замены уже входят в recent20; freshness шумна; ID-порядок уже коррелирует с полезным спросом. При отсутствии изменения итогового C опыт на этом срезе прекращается.

**Ближайший эксперимент:** tiny три одинаковых buyer-count с разными прошлыми purchase-times при квоте2, отдельный нетождественный count и recent-overlap контроль. Проверить ожидаемые ID, неизменность counts, `<t`, peer/suffix invariance и ≤220; искусственный Y не доказывает качество. Следующий no-fit screen сначала измеряет cutoff-tie/overlap mass без labels, затем gained/lost/net full-Y hits при заранее закреплённой метрике. Native-policy и label-independent matched-size результаты раздельны (`11-fusion.md:35–41`). Бюджет tiny ≤6 событий/≤3 Q, 0 fits; реальные scans/cost **UNKNOWN**, всё **UNRUN**. Польза Task1: дешёвый опровергающий контроль до усложнения retrieval и повторной материализации features.

Ни quotas, ни current fixed-C feature ablation, ни science/native allowances этим FIRST не меняются. Сначала обязательные проверки исправленной цепочки; дальнейшие retrieval pilots требуют конкретного плана и доступного бюджета.
