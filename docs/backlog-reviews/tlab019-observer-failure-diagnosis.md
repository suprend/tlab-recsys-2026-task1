# 019 observer failure: независимая ограниченная диагностика

**Воспроизводимая причина совместима с actual ValueError и найдена до source/model verification:** mechanical `Observer.binding()` повторно вызывает `strong.prepare_plan()`, а тот вызывает environment snapshot, создающий запрещённые observer subprocesses. Это дефект контракта observer/planner, не дефект модели и не основание для дополнительных fits.

Цепочка frozen кода: `tests/oracles/strong_output_audit.py:180` → `scripts/strong_baseline.py:132` (`a.environment_snapshot`) → `scripts/metadata_ablation.py:148` → `scripts/train_baselines.py:407` (`platform.platform()`). В свежем процессе на установленном CPython 3.12.14 Darwin последний вызов выполняет `uname -p` и `file -b <python executable>`; гипотетический sw_vers здесь не наблюдался. Python audit hook записывает точные argv без данных запросов.

Два дешёвых независимых свежих процесса подтверждают механизм. Первый `tlab019-environment-child-repro.py` фиксирует CHILDREN CPU до imports=0, после imports=0, после environment_snapshot=0.003732 s. Второй `tlab019-environment-native-guard-repro.py` импортирует frozen observer, создаёт объект без __init__/binding/run и вызывает **его настоящий guard**: до environment PASS, после CHILDREN=0.003923 s — `ValueError('Forbidden observer subprocess')`. Никакой DB/source/model/Pool/predict/fit не открывался. SELF двух процессов 0.316243 и 0.310883 s; первый wall 0.273304 s. Результаты сохранены отдельными `...-results.json`.

Почему это объясняет receipt: guard на строке 135 требует абсолютный RUSAGE_CHILDREN==0, а environment вызывается после большого повторного mechanical hash/lineage планирования. Поэтому ~76.8 CPU до ошибки не противоречат позднему environment вызову. `run()` повторяет guard при terminal cleanup, добавляя note к первичному исключению; `ValueError` + `secondary_error_count=1` в существующем `verification.failed.json` согласуются с этой цепочкой. Поскольку сам failed receipt намеренно скрывает сообщение, это не восстановленный traceback actual запуска; это детерминированно воспроизведённый запрещённый side effect неизбежного call path. Никакого Observer.run replay либо переписывания failed attempt не было.

Нужна узкая prospective zero-fit коррекция **после отдельного policy review**. Сохранить no-subprocess guard; убрать subprocess-producing environment derivation именно из observer plan rederivation. Возможный seam: независимая in-process проверка Python/loaded+installed locked package versions и OS/runtime полей, затем механическое использование уже закреплённого environment при identity reconstruction. Нельзя просто довериться platform-строке из проверяемого manifest, подменить произвольный environment без независимых проверок, разрешить любые descendants или обнулить CHILDREN counters. Альтернатива — маленький reviewed subprocess-free environment adapter с явно определённым отображением на существующий canonical snapshot; его совместимость со старым identity должна проверяться cheap fixtures до любого повторного observer запуска. Frozen production prepare_plan identity нельзя молча изменить задним числом.

Отдельное решение требуется для нового zero-fit verification invocation: старый failed receipt/attempt остаётся immutable, весь уже потраченный CPU остаётся charged, новый observer allowance ограничен остатком исходного outer deadline/3600 CPU и прежним максимальным 300 CPU; новый fit budget не возникает. Без этого решения исправленный код сам по себе не разрешает replay и не превращает producer outputs в accepted result.
