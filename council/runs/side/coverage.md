# H13: покрытие кандидатов REES46 2020 — prereg

Записано 22.10.2026, до любого запуска `council/side/coverage.py`. План — гипотеза 7, строка 08:30–09:45 и E4 в
`council/runs/night/2026-10-22-plan.md`; отчёт, разделы «Кандидаты» и «Следующие шаги» п. 1.

## Гипотеза

Около половины целей вне шести источников кандидатов. Гипотеза: **новый источник даёт цели, которых нет в объединении
текущих, дешевле (на 1000 добавленных кандидатов), чем самый слабый текущий источник своими уникальными
кандидатами**.

## Вход

- Якоря: хвост T_fit, 2020-01-29..02-02 (5 дней, все до S0). Метки дня — новые пары с корзиной/покупкой за 24 ч после
  якоря (SQL сборки), то есть train-метки; S0, val и test не читаются.
- База `data/processed/rees46-2020.duckdb` (`task1.period.DB` при `TASK1_PERIOD=2020`): сессия DuckDB в памяти,
  threads 4, memory_limit 4GB, сброс в `/tmp/tlab-side-coverage-duckdb`; база подключается `ATTACH … (READ_ONLY)` и
  проверяется `duckdb_databases().readonly`. `duckdb.connect(db, read_only=True)` не годится: DuckDB не даёт рядом
  с ним записываемого каталога для временных таблиц сборки; гарантия та же, запись в `src` падает (тест).
- Текущие источники 1–6 (pop, cat, brand, coview, coview_agg, transition) — SQL сборки `task1.build.set_anchor`
  (импорт, без правки). Новые, по тому же 14-дневному окну, без тронутых товаров, топ-200 на пользователя:
  - **i2v** — item2vec по сессиям: PPMI (сглаживание контекста 0.75) совместных просмотров в сессиях 2–50 товаров,
    словарь ≤ 100 000 товаров из ≥ 5 сессий, пары n ≥ 2, усечённый SVD до 64 (gensim не установлен; SVD PPMI — матричная
    форма SGNS, Levy & Goldberg 2014). Вектор пользователя — сумма векторов 20 последних просмотров с весом
    exp(−возраст/1 сут), скор — косинус.
  - **cp1** — совместные корзины/покупки: P(B|A) = n_AB/(n_A + 5) по пользователям с 2–50 такими товарами, топ-20 на A;
    скор — сумма по 10 последним просмотрам A с весом exp(−возраст/1 сут).
  - **cp2** — второй шаг того же графа: Σ_A w_A Σ_B P(B|A)·P(C|B).
- Сверка: попадания объединения и цели запросов с кандидатами равны таблице `days6` того же дня (вывод сборки), если
  файл есть (`build_match`).

## Выход

Только `artifacts/side/coverage/per_query.parquet` (на запрос: цели, попадания и строки каждого источника, уникальные,
объединение; для новых при K ∈ {10, 20, 50, 100, 200} — попадания, строки, вне объединения) и
`council/runs/side/coverage.json`; журнал — `council/runs/side/queue.jsonl`. Снимок листинга и mtime
`artifacts/xfer`, `artifacts/task1` (каталоги `sealed` — записью, без захода внутрь) снимается после первого
прохода ворот и сверяется после последнего чтения; изменение — `status: refused`, код 3.

## Правило решения

e = цели на 1000 добавленных кандидатов. Слабейший текущий источник — с наименьшим e своих уникальных кандидатов
(попадания, которых нет у других пяти, на его уникальные строки). Для N ∈ {i2v, cp2} при K = 50:
Δe = e(N@50 вне объединения) − e(слабейшего), CI — бутстрап по запросам пяти дней (2000, `default_rng(2026)`).

- **окупается**: CI выше 0;
- **не окупается**: CI ниже 0;
- **не различено**: иначе.

cp1 и остальные K — описательно.

## Что считается результатом

Recall@K по источникам и объединению, размеры на запрос, уникальный вклад, добавленный recall новых источников по K,
вердикт для i2v и cp2, `build_match`. Recall источника вне объединения не равен приросту NDCG: вывод только о
покрытии; в ранкер ничего не добавляется. Итог — в «Следующие шаги» п. 1 отчёта.

## Лёгкий шаг и соседство с тяжёлыми

Тяжёлого замка шаг не берёт. Перед стартом и перед каждым якорем — `council.xfer.queue.light_wait('probe', …)` по
журналам xfer и `council/runs/side/queue.jsonl`: ждёт рядом с подгонками REES46 full_val/full_test,
`council.memory`, `council.agents … compute` и рядом с тяжёлым шагом с неизвестным или > 20 ГБ пиком; затем ждёт,
пока жив любой чужой процесс `-m council.(queue|fit|memory)` (`queue.foreign()` с этим фильтром: очереди плана и
C_val REES46 замка не берут). `light-wait`/`light-start`/`light-end` с пиком — в журнал. Тяжёлые шаги REES46 видят
прогон через ПРОВЕРКА-HEAVY плана `! pgrep -fl '[c]ouncil/xfer/run.py.*(queue|compute|fit-one)|[c]ouncil\.(fit|queue|memory)|[c]ouncil[./]side'`: последняя альтернатива ловит путь скрипта, поэтому запуск —
только скриптом `-I council/side/coverage.py`, не `-m council.side.coverage` (строку 08:30 плана поправить).
